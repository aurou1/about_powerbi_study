## 二、为什么要先花一章讲环境

这一章看起来是「装软件」，但它是**交付现场最容易翻车的地方**。

在客户现场做实施（FDE 的日常）时，你面对的通常不是本机干净的 localhost，而是：

- 数据库在客户内网，你只能拿到一个只读账号
- 客户 IT 只给你一张 Excel，说「先看着办」
- 换台电脑打开报表，刷新全部失败
- 数据导进来了，但行数对不上，你却没发现 —— 后面所有分析全是错的

所以本章要养成两个**终身受用的习惯**：

> **习惯 1：数据导入后的第一件事，永远是数行数。**
> **习惯 2：任何数字，都要能用 SQL 独立算一遍来对拍。**

## 三、概念：Power BI 的三种存储模式

导入数据时你会被问到选哪种模式，先搞清楚区别。

| 模式 | 数据在哪 | 优点 | 缺点 | 什么时候用 |
|---|---|---|---|---|
| **导入（Import）** | 复制进 Power BI 内存（VertiPaq 引擎） | 极快、DAX 全功能可用 | 数据不是实时的，要刷新 | **绝大多数场景**，尤其数据量 ≤ 几百万行 |
| **DirectQuery** | 留在源数据库，每次交互实时查库 | 数据实时 | 慢、很多 DAX 函数受限、依赖数据库性能 | 实时性要求极高、数据量极大 |
| 复合模型 | 部分导入 + 部分直连 | 折中 | 复杂，维护成本高 | 大事实表直连 + 小维度导入 |

**我们的选择：导入。**

理由很简单：本库只有 15,780 行（事实表 11,974 行），全部进内存毫无压力，而且 DAX 的全部能力都能用。等你要处理千万行级数据时再考虑 DirectQuery。

> ⚠️ **踩坑提醒**：DirectQuery 模式下，很多时间智能函数和迭代函数要么报错要么极慢。新手不要一上来就选它。

## 四、实操：四步把数据接进来

### 4.1 第一步：装 ODBC 驱动（最容易出错）

Power BI 连 MySQL 走的是 ODBC 通道，必须先装驱动。

1. 打开 <https://dev.mysql.com/downloads/connector/odbc/>
2. 下载 **MySQL Connector/ODBC，64 位**（Windows (x86, 64-bit), MSI Installer）
3. 一路默认安装

**为什么强调 64 位**：Power BI Desktop 现在是 64 位程序，如果你装了 32 位驱动，Power BI 会**完全看不见**这个驱动，报错信息还特别含糊（只说"需要 ODBC 驱动"）。

验证是否装对：

1. Windows 搜索栏输入 `ODBC` → 打开 **ODBC 数据源(64 位)**
2. 切到「驱动程序」页签
3. 应该能看到 `MySQL ODBC 8.x Unicode Driver`

### 4.2 第二步：获取数据

1. 打开 Power BI Desktop，跳过启动页
2. 顶部「主页」功能区 → **获取数据** → 在搜索框输入 `MySQL` → 选 **MySQL 数据库** → 连接
3. 填写连接信息：

| 字段 | 填什么 | 说明 |
|---|---|---|
| 服务器 | `localhost` 或 `127.0.0.1` | 如果 MySQL 在别的机器，填 `IP:端口`，如 `192.168.1.10:3306` |
| 数据库 | `study_powerbi_demodata` | 可留空，下一步在导航器里选 |

4. 点「确定」

### 4.3 第三步：身份验证

弹窗会让你选身份验证方式，这里**选「数据库」**，然后填：

- 用户名：`root`
- 密码：`root`
- 勾选「保存密码」（否则每次刷新都要你输）

> ⚠️ **踩坑提醒**：**不要选 Windows 身份验证**。MySQL 一般不认 Windows 账号，选了会直接连不上。

连接成功后会弹出「加密支持」警告，点是即可（本地环境无 SSL）。

### 4.4 第四步：选择并加载表

弹出的**导航器**窗口，左侧列出库里所有表。勾选这 6 张：

- `dim_region`
- `dim_product`
- `dim_customer`
- `dim_date`
- `fact_order`
- `fact_order_item`

勾选后右侧会预览数据。此时你有两个选择：

| 按钮 | 行为 | 什么时候点 |
|---|---|---|
| **加载** | 直接把数据导入模型 | 数据干净、不需要清洗 |
| **转换数据** | 先进 Power Query 编辑器处理 | 需要改类型、删列、合并表 |

**本章点「加载」**（清洗留到 ch03）。

等待导入完成，左侧「数据」面板会出现 6 张表，每张表前面有个小表格图标。

## 五、验证：数行数（你必须做的这一步）

数据进来了，但**你还没确认它是对的**。现在数行数。

### 5.1 用卡片图核对

1. 在报表画布上，从「可视化」面板选 **卡片图**
2. 从右侧「数据」面板把 `fact_order` → `order_id` 拖到卡片的「字段」
3. 点击字段旁边的下拉箭头 → 把汇总方式从「求和」改成 **计数**
4. 重复 6 次，或复制粘贴卡片，分别为每张表设一个计数卡片

**预期结果（必须一字不差）**：

| 表 | 预期行数 |
|---|---:|
| dim_region | 10 |
| dim_product | 200 |
| dim_customer | 500 |
| dim_date | 1,096 |
| fact_order | 3,529 |
| fact_order_item | 8,445 |
| **合计** | **15,780** |

### 5.2 用 SQL 对拍

打开 PyCharm 的 Database 面板（或任何 MySQL 客户端），跑一遍：

```sql
SELECT 'dim_region' AS 表, COUNT(*) AS 行数 FROM dim_region
UNION ALL SELECT 'dim_product',  COUNT(*) FROM dim_product
UNION ALL SELECT 'dim_customer', COUNT(*) FROM dim_customer
UNION ALL SELECT 'dim_date',     COUNT(*) FROM dim_date
UNION ALL SELECT 'fact_order',   COUNT(*) FROM fact_order
UNION ALL SELECT 'fact_order_item', COUNT(*) FROM fact_order_item;
```

结果应与上面表格完全一致。**任何一张表对不上，立刻停下排查，不要继续往下做。**

> **FDE 视角**：这一步叫「数据完整性校验」。在客户现场，我通常会把这 6 个数字截图发给客户确认，拿到一句"对，就是这个数"再开工。这样做的好处是：后面如果客户说"你这数字不对"，你可以立刻证明是口径问题而���是数据问题 —— 保护自己。

### 5.3 顺手看一眼全局金额

再跑一条，记住这个数，后面会反复用到：

```sql
-- 全部订单（含已取消、退款）
SELECT COUNT(*) AS 订单数, ROUND(SUM(order_amount),2) AS 销售额
FROM fact_order;
-- 预期：3529 | 10689549.70

-- 有效订单（仅已完成）★ 这才是真实成交
SELECT COUNT(*) AS 有效订单数, ROUND(SUM(order_amount),2) AS 有效销售额
FROM fact_order WHERE status = '已完成';
-- 预期：2366 | 7195492.73
```

**注意这两个数字差了 349 万（约 47%）**。这就是本教程反复强调的「有效销售」口径 —— 后面 ch04 会专门讲它。

## 六、认识 Power BI 的三大视图

界面最左侧有一条竖着的图标栏，三个最重要的视图：

| 视图 | 图标位置 | 干什么 | 什么时候用 |
|---|---|---|---|
| **报表视图** | 第一个（柱状图图标） | 拖字段、做图表 | 90% 的时间在这 |
| **模型视图** | 第三个（关系图图标） | 看表结构、建关系、管理度量值 | ch02 的主战场 |
| **数据视图** | 第二个（表格图标） | 像 Excel 一样逐行看数据 | 抽查某几行数据对不对 |

现在点开**数据视图**，选 `fact_order` 表，往下翻几行，感受一下真实数据长什么样：

- `order_id`：1、2、3…… 主键
- `status`：`已完成` / `已取消` / `退款`
- `order_amount`：如 1267.16、722.41

再看 `fact_order_item`，注意 `order_id = 2` 出现了多行 —— 说明**一个订单可以包含多个商品**。这个「一对多」关系，是 ch02 建模型的核心。

## 七、保存：.pbix 里到底存了什么

`文件 → 保存`，起个名字比如 `study_powerbi_demo.pbx`，保存。

`.pbix` 文件是一个压缩包，里面包含：

| 内容 | 说明 |
|---|---|
| 数据（压缩后） | 6 张表的数据被 VertiPaq 列式压缩存进来，所以文件可能几 MB |
| 数据模型 | 表关系、度量值、层级、格式设置 |
| 报表页面 | 你画的所有图表和布局 |
| Power Query 查询 | 数据是怎么取出来的（ch03 会看到） |

**因此：`.pbix` 可以整个拷走，换台电脑打开图表照样在。** 但要注意：

- 想**刷新**数据 → 目标电脑必须能连上 MySQL，且装了同样的 ODBC 驱动
- 换机器后刷新失败 → ch01 的常见故障：驱动没装 / 数据源凭据要重填

## 八、FDE 现场场景：客户不给你直连怎么办

真实交付里，你很少能拿到 `root/root` 这么痛快的权限。几种常见情况和应对：

| 客户给你的东西 | 怎么做 | 代价 |
|---|---|---|
| 只读账号 | 直接连，和本章一样 | 最理想 |
| 只有内网机器能连库 | 在那台机器上装**网关**（ch11 详讲） | 需要装软件、配凭据 |
| 只有 Excel / CSV 导出 | 获取数据 → Excel/CSV，导入 | 每次更新要手工换文件，无法自动刷新 |
| 只给了一张大宽表（没有维度表） | 自己在 Power Query 里拆成事实表 + 维度表 | 需要 ch03 的清洗能力 |
| 只让查视图，不给表 | 连视图，或让 IT 给你建视图 | 视图性能可能很差 |

> **核心心法**：Power BI 这头的难度，80% 取决于**源数据给你什么形态**。数据给得好，建模就是拖几下；数据给得烂，你一半时间在做清洗。所以接到需求第一句应该问：**"数据从哪来？能给我什么形式的访问权限？"**

## 十、练习题

### 练习 1：验证数据可复现（考：固定随机种子）

**题目**：回到上层目录重跑建库脚本，然后在 Power BI 里点「刷新」，观察 6 张表行数是否变化。

<details>
<summary>Hint</summary>
脚本里有 `random.seed(20260903)`。固定种子意味着什么？
</details>

**答案与解析**：

行数**完全不变**，仍是 10/200/500/1096/3529/8445。

**解析**：脚本第 26 行 `random.seed(20260903)` 固定了随机数种子。Python 的 `random` 是伪随机 —— 同一个种子、同一段代码，产生的「随机」序列完全一样。所以每次重建都得到同一份数据。

**这对你很重要**：意味着本教程里所有数字（比如「广东有效销售额 1,078,152.70」）你在任何机器上都能复现，方便对拍验证。

**预期结果**：6 张表行数与首次导入完全一致。

### 练习 2：故意制造连接失败（考：排错能力）

**题目**：把连接端口改成 `3307`，观察报错信息；再改回 `3306` 恢复。

<details>
<summary>Hint</summary>
在「主页 → 转换数据 → 数据源设置」里改。
</details>

**答案与解析**：

会看到类似 `Unable to connect` 或 `无法连接到数据库` 的报错，提示端口无响应。

**排错四步法**（FDE 常用）：

1. **MySQL 活着吗**：命令行 `mysql -uroot -proot -e "SELECT 1"`，能返回 1 说明库没问题
2. **端口对吗**：`SHOW VARIABLES LIKE 'port';` 确认是 3306
3. **账号密码对吗**：用同一套账号在命令行连一次
4. **驱动装了吗**：ODBC 数据源(64 位) → 驱动程序页签里找 MySQL

**预期结果**：改成 3307 报错；改回 3306 后刷新成功，行数不变。

### 练习 3：清除凭据后刷新（考：凭据机制）

**题目**：`文件 → 选项和设置 → 数据源设置` → 选中你的 MySQL 数据源 → 「删除权限」→ 回报表点「刷新」，观察现象，然后重新填密码。

**答案与解析**：

刷新会弹窗要求你重新输入凭据，或者直接报「凭据无效」。填入 `root/root` 后恢复正常。

**为什么重要**：这是**发布到 Service 后刷新失败的第一大原因**（ch11 会再遇到）。桌面端你填的密码存在本机，发布到云端它不会自动带过去，必须在云端重新配一次凭据 —— 很多人第一次发布都栽在这。

**预期结果**：删除权限 → 刷新要求重填 → 填对后恢复正常，行数不变。

---

### 练习 4：认识状态分布（考：预热 GROUP BY，为 ch04 口径做准备）

**题目**：在 MySQL 里查三种 status 各有多少订单、各占多少金额。

```sql
SELECT status,
       COUNT(*) AS 订单数,
       ROUND(SUM(order_amount),2) AS 金额,
       ROUND(COUNT(*)*100.0/(SELECT COUNT(*) FROM fact_order),1) AS 占比pct
FROM fact_order
GROUP BY status
ORDER BY 订单数 DESC;
```

**预期结果**：

| status | 订单数 | 金额 | 占比 |
|---|---:|---:|---:|
| 已完成 | 2,366 | 7,195,492.73 | 67.0% |
| 已取消 | 591 | 1,748,440.63 | 16.7% |
| 退款 | 572 | 1,745,616.34 | 16.2% |

**解析**：**只有 67% 的订单是真实成交**，剩下 33%（1,163 单、约 349 万）是作废的，但金额仍老老实实躺在表里。

记住这个比例：**以后凡是你算出「销售额 1,069 万」，就要立刻警觉 —— 你大概率忘了过滤状态。** 正确数字是 **719 万**。

### 练习 5：抽查明细行（考：理解一对多）

**题目**：在「数据」视图打开 `fact_order_item`，找到 `order_id = 2` 的所有行，把它们的 `line_amount` 手工加起来，看是否等于 `fact_order` 里 `order_id = 2` 的 `order_amount`。

**预期结果**：`fact_order` 中 order_id=2 的 order_amount = **722.41**；`fact_order_item` 中该订单有 2 行明细：303.13 + 419.28 = **722.41**。完全一致。

**解析**：这就是数据字典里说的「**表头金额恒等于明细汇总**」（建库时特意保证，误差为 0）。

**但要注意**：正因为如此，如果你在 Power BI 里同时把 `fact_order.order_amount` 和 `fact_order_item.line_amount` 都拖进同一个卡片求和，就会得到 **722.41 + 722.41 = 1444.82**，金额翻倍 —— 这是新手最常犯的错，ch04 会专门拆开讲。
