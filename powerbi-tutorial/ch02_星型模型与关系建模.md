# ch02 星型模型与关系建模 🔗

> 本章目标：把 6 张互不相识的表连成一个**能正确回答业务问题的模型**。
> 这一步做错，后面所有数字都是错的 —— 而且错得很隐蔽。

## 一、本章学习目标

学完本章你应该能：

1. 分清**事实表**和**维度表**，说出本库 6 张表各属哪类
2. 独立搭出 5 条关系，并解释每条关系的**基数**和**筛选方向**
3. 正确**标记日期表**（时间智能的唯一前提）
4. 建出「品类 → 品牌 → 商品」和「年 → 季 → 月」两个层级
5. 说出双向筛选的风险，以及为什么默认不该开

## 二、为什么模型比图表重要

新手最常见的学习路径是：导入数据 → 立刻拖图表 → 发现数字怪怪的 → 到处找「哪个图表设置错了」。

但真相是：**数字错的根因 90% 在模型层，不在图表层。**

模型的角色好比一栋楼的地基：

| 层 | 出问题时的表现 | 排查成本 |
|---|---|---|
| 图表层 | 图不好看、颜色不对 | 低，一眼能看出来 |
| 度量值层 | 某个指标数字不对 | 中，要读 DAX |
| **模型层（本章）** | **所有数字都不对，而且看起来"挺合理"** | **高，要推倒重来** |

> **FDE 视角**：在客户现场，我接手别人做的报表，第一件事永远是打开模型视图看关系图。关系图乱的模型（一堆双向箭头、雪花型乱连、缺日期表），报表数字基本不可信。而一个干净的星型模型，即使度量值写得糙，方向也不会偏。

## 三、概念：事实表 vs 维度表

这是维度建模最基础的一对概念。

| | 事实表（Fact） | 维度表（Dimension） |
|---|---|---|
| 记录什么 | **发生了什么事**（动作、交易） | **谁、什么、在哪、什么时候**（描述） |
| 特点 | 行数多、持续增长 | 行数少、相对稳定 |
| 核心内容 | 外键 + **可度量的数值** | 主键 + 描述性属性 |
| 本库 | `fact_order`（3,529 行）、`fact_order_item`（8,445 行） | `dim_region`(10)、`dim_product`(200)、`dim_customer`(500)、`dim_date`(1,096) |

快速判断口诀：

> **能被"数"和"加"的字段放在事实表，被用来"分组"和"筛选"的字段放在维度表。**

看 `fact_order_item` 的字段：`quantity`（数量）、`line_amount`（金额）、`line_profit`（利润）—— 这些可以求和，是**度量**。
看 `dim_product` 的字段：`category`、`brand`、`product_name` —— 这些用来分组（按品类看销售额），是**维度属性**。

### 两种事实表的粒度差异

本库有两张事实表，粒度不同：

| 表 | 一行代表 | 行数 | 度量 |
|---|---|---:|---|
| `fact_order` | **一张订单** | 3,529 | `order_amount` / `order_profit` |
| `fact_order_item` | **订单里的一个商品** | 8,445 | `line_amount` / `line_profit` / `quantity` |

`fact_order_item` 粒度更细（一单多品）。这就是为什么**写 DAX 度量值要用 `line_amount`** —— 只有最细粒度的表才能和 `dim_product` 正确关联（你想按品类看销售额，必须走明细表）。

> ⚠️ **踩坑提醒**：`fact_order.order_amount` 和 `fact_order_item.line_amount` 都含订单金额。**同一个度量值里绝不能同时求和这两列**，否则金额翻倍。详见 ch04 练习 2。

## 四、概念：星型模型

**星型模型（Star Schema）** 长这样：一张事实表在中间，多张维度表围着它，像一颗星。

```
                    dim_date (1,096)
                         │
                         ▼
 dim_customer ──▶  fact_order  ◀── dim_region
   (500)            (3,529)          (10)
                         │
                         ▼
                  fact_order_item (8,445)
                         │
                         ▼
                  dim_product (200)
```

**对比另一种常见错误：雪花模型** —— 维度表再连维度表（比如 `dim_customer` 再连一张 `dim_city` 表）。

| | 星型 | 雪花 |
|---|---|---|
| 结构 | 维度直接连事实 | 维度再分多层 |
| Power BI 表现 | **快、简单、推荐** | 慢、关系复杂、容易出错 |
| 什么时候用雪花 | — | 几乎不用，除非维度极多且要复用 |

**Power BI 的最佳实践：永远把模型拍平成星型。** 如果源数据是雪花型（比如客户表连地区表），用 Power Query 把它们合并成一张宽维度表（ch03 会做）。

### 我们这套库的 5 条关系

| # | 从（一端） | 到（多端） | 关系字段 | 类型 |
|---:|---|---|---|---|
| 1 | `dim_customer` | `fact_order` | `customer_id` | 一对多 |
| 2 | `dim_region` | `fact_order` | `region_id` | 一对多 |
| 3 | `dim_date` | `fact_order` | `date_key` → `order_date` | 一对多 |
| 4 | `fact_order` | `fact_order_item` | `order_id` | **一对多**（订单头 → 明细） |
| 5 | `dim_product` | `fact_order_item` | `product_id` | 一对多 |

注意第 4 条：`fact_order` 在这里是**一端**，`fact_order_item` 是**多端**。一张表可以在不同关系里扮演不同角色。

## 五、概念：基数与筛选方向（本章重点）

### 5.1 基数（Cardinality）

就是「一边一个，对应另一边几个」：

| 基数 | 含义 | 例子 |
|---|---|---|
| 一对多（1:*） | 维度表里 1 行 → 事实表里多行 | 1 个客户 → 多张订单 |
| 一对一（1:1） | 两边都唯一 | 少见，通常是该合并的表 |
| 多对多（*:*） | 两边都可重复 | **危险信号**，见第 10 节 |

`dim_customer` → `fact_order` 是一对多：一个客户（1）可以下很多单（多）。

### 5.2 筛选方向（Cross filter direction）—— 数据流动的方向

这是最容易被忽视、也最关键的概念。

**默认规则：筛选从「一端」流向「多端」。**

比如 `dim_region`（一端）→ `fact_order`（多端）：

- 你在报表上放一个切片器选「广东」
- 筛选沿着箭头从 `dim_region` 流到 `fact_order`
- `fact_order` 只剩广东的订单
- 于是 `SUM(order_amount)` 算出来就是广东的销售额

```
    dim_region                fact_order
   ┌──────────┐              ┌─────────────┐
   │ 广东  ●  │──── 筛选 ───▶│ 只留广东订单 │
   └──────────┘              └─────────────┘
      (一端)                     (多端)
```

**再往下传**：`fact_order` 又是 `fact_order_item` 的一端，所以筛选会继续流到明细表 —— 这就是「选广东 → 能看到广东卖了哪些商品」的原理。**筛选可以沿着关系链一路向下传递。**

### 5.3 双向筛选（Both / 双向）是什么

默认箭头是单向的（一端 → 多端）。如果你把它改成**双向**，那么多端也能反向筛选一端。

听起来很方便（比如「选了商品A，自动筛出买过A的客户」），但代价很大：

| 风险 | 说明 |
|---|---|
| **歧义** | 模型里出现多条路径时，Power BI 不知道该走哪条，结果随机 |
| **性能** | 每次查询要多算一遍反向传播，大表上明显变慢 |
| **扇出错误** | 多对多关系下会产生重复计算 |

> ⚠️ **踩坑提醒**：**除非你明确知道自己在做什么，否则永远保持单向筛选。** 需要处理多对多时，用 ch06 的 `TREATAS` 或度量值里的 `CROSSFILTER` 临时打开，而不是在模型里全局开双向。

## 六、实操：建立 5 条关系

Power BI 通常会自动检测关系（因为字段名对得上，如 `customer_id`）。但你**必须逐个检查**，不能盲目信任自动检测。

### 6.1 检查自动创建的关系

1. 点左侧 **模型视图**（第三个图标）
2. 会看到 6 张表的卡片，中间有连线

如果 Power BI 已经自动连好了，你会看到 5 条线。**逐条点开验证**：

双击任意一条关系线，打开「编辑关系」窗口：

| 设置项 | 检查什么 |
|---|---|
| 表（多端） | 是不是事实表 |
| 相关表（一端） | 是不是维度表 |
| 基数 | 应为 **一对多** |
| 交叉筛选方向 | 应为 **单一** |
| 使此关系可用 | 应**勾选**（不勾就是"非活动关系"，不参与计算） |

### 6.2 手工创建缺失的关系

如果有关系没自动建（比如 `dim_date` → `fact_order`），手工建：

1. 在模型视图，从 `dim_date` 表的 `date_key` 字段**按住拖到** `fact_order` 表的 `order_date` 字段
2. 松开鼠标，关系建立
3. 双击关系线确认：基数一对多、方向单一

**逐条核对这 5 条**：

| # | 拖拽方向（从 → 到） | 字段 |
|---:|---|---|
| 1 | `dim_customer` → `fact_order` | `customer_id` |
| 2 | `dim_region` → `fact_order` | `region_id` |
| 3 | `dim_date` → `fact_order` | `date_key` → `order_date` |
| 4 | `fact_order` → `fact_order_item` | `order_id` |
| 5 | `dim_product` → `fact_order_item` | `product_id` |

> **注意方向**：拖拽时从**一端（维度）拖到多端（事实）**。如果拖反了，Power BI 会自动纠正基数，但最好一次拖对。

### 6.3 关于 dim_customer 的 region_id

`dim_customer` 也有 `region_id`（客户所属地区），也可以连到 `dim_region`。但**本库不要连**，原因：

- `fact_order.region_id` 已经连了 `dim_region`（订单收货地区）
- 如果再连 `dim_customer.region_id`，模型里就出现**两条路径**到 `dim_region`，产生歧义

> **数据局限提醒**：本库 `dim_customer.region_id` 与 `fact_order.region_id` 是**同一个值**（造数据时客户在哪省就下哪省的单），所以**没有"跨省下单"场景**。真实电商里客户可能在 A 省注册、在 B 省收货，那时就需要两个角色（role-playing dimension）分别连接，并用 `USERELATIONSHIP` 激活。

## 七、实操：标记日期表（时间智能的唯一前提）

**这一步不做，ch08 的所有时间智能函数都会返回空白或错误结果。**

### 7.1 为什么需要

DAX 的时间智能函数（`DATESYTD`、`SAMEPERIODLASTYEAR`、`DATEADD` 等）要求日期表满足三个条件：

| 条件 | 要求 | 本库情况 |
|---|---|---|
| **唯一** | 日期列无重复值 | ✅ `date_key` 是主键 |
| **连续** | 日期不能断档（缺某天） | ✅ 2023-01-01 ~ 2025-12-31 连续 1,096 天 |
| **整年** | 覆盖完整年度（从 1月1日 到 12月31日） | ✅ 完整三个自然年 |

三点都满足，但 Power BI 不知道，你必须**显式告诉它**。

### 7.2 操作步骤

1. 在模型视图或数据视图，选中 `dim_date` 表
2. 顶部功能区出现「表工具」上下文选项卡 → 点 **标记为日期表**
3. 在下拉里选 `date_key` 作为日期列
4. 点确定

验证：选中 `dim_date` 后，`date_key` 字段前面会出现一个**小日历图标** 🎯，说明标记成功。

> ⚠️ **踩坑提醒**：有人习惯直接用事实表里的 `order_date` 当日期用，不建日期表。小数据看起来没事，但一旦算同比/累计就会错 —— 因为订单日期有断档（某些天没订单），不符合"连续"要求。

### 7.3 顺手关掉自动日期/时间

Power BI 默认会给每个日期字段偷偷建一个隐藏的日期表（叫"自动日期/时间"），这会白白增大文件、还可能造成混淆。

关掉它：

`文件 → 选项和设置 → 选项 → 当前文件 → 数据加载` → 取消勾选 **「自动日期/时间」**

## 八、实操：建层级 + 整理模型

模型建完，还要「收拾干净」，让用的人（和你未来的自己）看得懂。

### 8.1 建两个层级

**层级**让你在图表里能下钻（点一下从年钻到季再到月）。

**层级 1：商品层级**

1. 在模型视图右侧「数据」面板，找到 `dim_product` 表
2. 右键 `category` → **创建层级**，命名为「商品层级」
3. 依次右键 `brand` → 添加到层级 → 商品层级
4. 再右键 `product_name` → 添加到层级 → 商品层级

最终顺序：`category`（品类）> `brand`（品牌）> `product_name`（商品）

**层级 2：时间层级**

1. 在 `dim_date` 表，右键 `year` → 创建层级，命名「时间层级」
2. 依次把 `quarter`、`month` 加进去

最终顺序：`year`（年）> `quarter`（季）> `month`（月）

### 8.2 隐藏不需要的键列

模型视图里，右键这些字段 → **隐藏**：

- `fact_order.customer_id`、`region_id`、`order_date`、`order_id`
- `fact_order_item.order_id`、`product_id`
- `dim_product.product_id`
- `dim_customer.customer_id`、`region_id`

**为什么**：这些是关联用的「键」，业务用户不该直接拖它们做分析（拖 `customer_id` 求和毫无意义）。隐藏后模型视图更清爽，字段列表也更好找。

> 注意：**隐藏不等于删除**，关系和计算照常工作。

### 8.3 按列排序（一个非常实用的小技巧）

默认 `category` 按拼音排序。但你更想让它**按毛利率从低到高**排（数码 → 食品 → 家居 → 服饰 → 美妆），这样图表里颜色顺序就有业务含义了。

做法：

1. 选中 `dim_product` 表的 `category` 字段
2. 顶部「列工具」→ **按列排序** → 选一个数值列（比如 `cost_price` 或你新建的排序辅助列）

> **局限性提醒**：「按列排序」要求排序列与排序列**一一对应**（一个品类只能对应一个排序值）。但毛利率是**计算出来的、随筛选变化的**，不能直接做排序列。
>
> **现实做法**：在数据源里加一张「品类维表」，含 `category` 和 `sort_order`（固定值 1-5）两列，用它做排序列。本库为了保持简洁没加这一列；你在实际项目里应该加。
>
> 想在本库体验这个功能，可以用 `dim_product` 的 `cost_price`（成本价）做排序列 —— 成本价高低和毛利率大致相关（数码成本最高、食品最低），虽不精确但能看到效果。

## 九、验证：用矩阵确认关系生效

模型搭好了，现在**用真实数字验证**它是否正确。

1. 回到报表视图，拖一个**矩阵**到画布

| 北京 | 761,942.54 | 180,732.58 | 23.72% |
| 湖北 | 700,373.18 | 152,976.13 | 21.84% |
| 山东 | 672,082.30 | 161,882.24 | 24.09% |
| 四川 | 562,613.26 | 122,344.89 | 21.75% |

| 现象 | 原因 |
|---|---|
| 合计是 10,689,549.70 | 忘了筛 `status='已完成'` |
| 每行数字都一样 | 关系没建，或建错了字段 |
| 某些省是空白 | 该省订单全是已取消/退款，被筛掉了（正常） |
| 数字明显偏大（约 2 倍） | 值里同时放了 `order_amount` 和 `line_amount` |

### 9.2 再用 SQL 对拍一次

```sql
SELECT r.province_name AS 省,
       ROUND(SUM(o.order_amount),2) AS 销售额,
       ROUND(SUM(o.order_profit),2) AS 利润,
       ROUND(SUM(o.order_profit)/SUM(o.order_amount)*100,2) AS 毛利率pct
FROM fact_order o
JOIN dim_region r ON o.region_id = r.region_id
WHERE o.status = '已完成'
GROUP BY r.province_name
ORDER BY 销售额 DESC;
```

结果应与上表**逐行一致**。

> **这个"SQL 算一遍 → Power BI 复现 → 对拍"的动作，本教程每章都会做。** 它是你唯一能确信报表数字正确的办法。

### 9.3 验证筛选能穿透两层

再拖一个矩阵：「行」放 `dim_product[category]`，「值」放 `fact_order_item[line_amount]`，同样筛 `status='已完成'`。

**预期结果**：

| 品类 | 销售额 | 利润 | 成交毛利率 |
|---|---:|---:|---:|
| 数码 | 2,612,383.09 | 30,291.28 | 1.16% |
| 食品 | 441,341.24 | 95,995.03 | 21.75% |
| 家居 | 1,408,258.89 | 383,334.76 | 27.22% |
| 服饰 | 1,351,789.04 | 513,684.38 | 38.00% |
| 美妆 | 1,381,720.47 | 683,559.33 | 49.47% |

**注意这张表有两个学习点**：

1. **筛选穿透了两层**：`status` 筛的是 `fact_order`（第 1 层），却影响到了 `fact_order_item`（第 2 层）的汇总 —— 证明第 4 条关系（订单头 → 明细）方向正确。
2. **数码是最大品类（261 万）却几乎不赚钱（毛利率 1.16%）**，美妆销售额只有它一半，利润却是它的 22 倍。这是一个非常典型的业务洞察 —— 建模正确才能看到它。

## 十、进阶：双向筛选与多对多的风险

前面说过默认单向。这里把风险讲透。

### 10.1 双向筛选什么时候真的需要

典型场景：**多对多关系**。比如一个订单可以有多个销售员，一个销售员跟多个订单。

本库没有这种场景，但你在真实项目里会遇到。正确解法：

| 解法 | 做法 | 推荐度 |
|---|---|---|
| 桥接表 | 建一张中间表存（订单ID, 销售员ID）组合 | ⭐⭐⭐ 最规范 |
| 临时双向 | 度量值里用 `CROSSFILTER(..., BOTH)` 临时开 | ⭐⭐ 局部可控 |
| 全局双向 | 在模型里把关系改成双向 | ❌ 别用 |

### 10.2 扇出（Fan-out）错误长什么样

如果 `fact_order` 和 `fact_order_item` 之间你误开了双向，会发生：

- 明细表反向筛选订单表
- 而订单表又筛选明细表
- 形成循环，Power BI 会报错或产生重复计数

**症状**：数字比 SQL 算出来的大很多，而且怎么调都不对。

**排查**：模型视图里数一数双向箭头（线两端都有箭头），超过必要的就关掉。

> **一句话原则**：**关系图里应该只有单向箭头，从维度指向事实。** 看到双向箭头，先问一句"为什么"。

## 十一、FDE 现场场景

### 场景 1：客户给的是一张大宽表

客户 IT 导出一张 Excel，所有字段挤在一张表里：订单号、客户名、省、商品名、品类、金额、日期……

**怎么办**：不要直接拿它当事实表用。在 Power Query 里（ch03）把它**拆成星型**：

1. 用「引用查询」复制几份
2. 一份只留客户相关列 → 删除重复项 → 加索引列 → 得到 `dim_customer`
3. 同理得到 `dim_product`、`dim_region`
4. 原表删掉描述列、只留键和金额 → 得到 `fact_order_item`

**为什么要这么麻烦**：星型模型文件更小、算得更快、切片器不会列出几万个重复值。

### 场景 2：客户系统里日期是文本

有些老系统把日期存成 `20240615` 这种数字，或者 `2024/6/15` 文本。

**怎么办**：在 Power Query 里转成日期类型。如果转不了（比如有脏数据），先在 SQL 里用 `STR_TO_DATE` 处理，或者干脆**自己用 DAX 的 `CALENDAR` 生成一张日期表**（ch03 会做），不依赖源数据。

### 场景 3：客户库里有 200 张表，你只需要 6 张

**别全导进来**。每多一张表，模型就复杂一分、刷新慢一分。

按「我要回答什么业务问题」倒推需要哪些表，只导必需的。本教程能用 6 张表讲完所有知识点，就是因为它们刚好覆盖「谁、买什么、在哪、什么时候、多少钱」五个维度。

## 十二、本章小结

| 你学到了 | 关键点 |
|---|---|
| 事实 vs 维度 | 能求和的放事实，用来分组的放维度 |
| 星型模型 | 事实在中间、维度围一圈；**不要雪花** |
| 5 条关系 | customer/region/date → fact_order；order → item；product → item |
| 基数 | 全部是**一对多** |
| 筛选方向 | 默认**单向**（维度 → 事实），筛选沿关系链向下传递 |
| 双向筛选 | **别开**，除非明确知道在做什么 |
| 日期表 | 唯一 + 连续 + 整年，且必须**手动标记** |
| 层级 | 商品层级（品类>品牌>商品）、时间层级（年>季>月） |
| 验证基准 | 各省合计 = **7,195,492.73**；数码毛利率 **1.16%** vs 美妆 **49.47%** |

## 十三、练习题

### 练习 1：验证筛选方向（考：理解一端 → 多端）

**题目**：在报表上放一个切片器，选 `dim_customer[tier]`（客户等级），再放一个卡片显示 `fact_order[order_amount]` 的总和（记得筛 status=已完成）。选「钻石」，看卡片数字是多少？

<details>
<summary>Hint</summary>
钻石客户只有 27 人，但每人下单很多。
</details>

**答案与解析**：

卡片显示 **1,293,617.21**。

**解析**：筛选从 `dim_customer`（一端）流到 `fact_order`（多端），只保留钻石客户的订���，然后求和。

对照 SQL：

```sql
SELECT ROUND(SUM(o.order_amount),2) AS 钻石客户销售额
FROM fact_order o
JOIN dim_customer d ON o.customer_id = d.customer_id
WHERE o.status='已完成' AND d.tier='钻石';
-- 预期：1293617.21
```

**延伸观察**：钻石客户只有 27 人（占 5.4%），却贡献了 1,293,617.21（占有效总额 18.0%）。这就是数据里埋的「客户消费分层」差异 —— 后面 ch07 学 `RANKX` / `TOPN` 时会再用到。

**预期结果**：1,293,617.21

### 练习 2：不标记日期表会怎样（考：时间智能的前提）

**题目**：先临时取消 `dim_date` 的「标记为日期表」（表工具 → 标记为日期表 → 选"无"），然后新建一个度量值：

```dax
测试YTD = TOTALYTD(SUM('fact_order'[order_amount]), 'dim_date'[date_key])
```

拖到卡片上看结果；再把日期表标记回来，看结果如何变化。

<details>
<summary>Hint</summary>
注意观察是"报错"还是"返回数字"。
</details>

**答案与解析**：

- **未标记日期表**：返回**空白**，或者提示缺少日期表（不同版本表现不同，但一定不是正确数字）
- **标记后**：返回正确数字

**解析**：时间智能函数内部依赖日期表的元数据（它要知道哪列是日期、是否连续）。没标记，Power BI 就当它是普通表，函数无法工作。

> 这是 Power BI 排名前三的新手问题：**"我的 YTD 怎么是空的？"** —— 答案 90% 是没标记日期表。

**预期结果**：未标记 → 空白；标记后 → 正常返回年度累计值。

### 练习 3：找出模型的隐藏问题（考：综合排查）

**题目**：假设你接手一个报表，业务方说"数字不对"。你在模型视图看到这些情况，分别会导致什么问题？

| 现象 | 后果 |
|---|---|
| `dim_date` 没有标记日期表 | ？ |
| `fact_order` → `fact_order_item` 是双向 | ？ |
| `fact_order[status]` 从没被任何人过滤过 | ？ |
| 同时有 `dim_region → fact_order` 和 `dim_region → dim_customer → fact_order` 两条路径 | ？ |

**答案与解析**：

| 现象 | 后果 |
|---|---|
| `dim_date` 没有标记日期表 | 所有时间智能函数（YTD/同比/环比）返回空白 |
| `fact_order` → `fact_order_item` 是双向 | 可能产生循环依赖或重复计数；数字虚高且难排查 |
| `fact_order[status]` 从没被过滤 | **销售额虚高 47%**（1,069 万 vs 正确的 719 万），已取消和退款被算进业绩 |
| 有两条路径到 `dim_region` | **筛选歧义**，Power BI 会随机选一条或禁用其中一条，结果不可预测 |

**解析**：第 3 条是本库最隐蔽的坑 —— 报表"看起来完全正常"，只是数字大了 47%。这就是为什么你要**养成 SQL 对拍的习惯**：不对比，你根本发现不了。

### 练习 4：手工重建一条关系（考：动手能力）

**题目**：删除 `dim_product` 与 `fact_order_item` 的关系，然后手工重建，并验证品类矩阵数字不变。

**答案与解析**：

操作：
1. 模型视图 → 右键 `dim_product` 和 `fact_order_item` 之间的连线 → 删除
2. 从 `dim_product[product_id]` 拖到 `fact_order_item[product_id]`
3. 双击新关系确认：一对多、单一方向、已启用
4. 回到报表，检查品类矩阵

**预期结果**：品类矩阵数字**完全不变**（数码 2,612,383.09 / 食品 441,341.24 / 家居 1,408,258.89 / 服饰 1,351,789.04 / 美妆 1,381,720.47）。

**解析**：如果变了，说明你拖反了方向（把事实表当一端了）。检查「编辑关系」窗口里的「表」应该是 `fact_order_item`（多端），「相关表」应该是 `dim_product`（一端）。

### 练习 5：思考题 —— 该不该隐藏键列（考：模型设计规范）

**题目**：有人说"把 `fact_order_item[order_id]` 隐藏了，我就没法按订单号筛选了，不该隐藏"。你怎么看？

**答案与解析**：

**该隐藏，但不影响使用。** 关键点在于：**隐藏的是字段在字段列表里的显示，不是它的功能。**

- 隐藏后，你在「数据」面板看不到 `order_id`，不能在图表里拖它
- 但关系照常工作，度量值照样能引用它（`DISTINCTCOUNT('fact_order_item'[order_id])` 完全有效）
- 如果真要让用户在报表里按订单号筛选，正确做法是**建一个显式的维度表**（订单维表），而不是把事实表的键列暴露出来

**延伸原则**：事实表里**只留两类字段** —— 外键（隐藏）和可聚合的数值（可见）。任何描述性文字（比如订单状态、客户名）都应该在维度表里。本库的 `fact_order[status]` 是个例外（为了教学方便放在事实表），严格规范下它应该进一张「订单状态维表」。
