## 三、Power Query 编辑器界面

打开方式：主页功能区 → **转换数据**（或点「转换数据」下拉 → 转换数据）。

打开后是一个独立窗口，分五个区域：

| 区域 | 位置 | 作用 |
|---|---|---|
| **查询列表** | 最左侧 | 所有表（查询）的列表 |
| **数据预览** | 中间 | 当前查询的前 1000 行（注意：**只是预览，不是全部数据**） |
| **功能区** | 顶部 | 「开始 / 转换 / 添加列 / 视图」四大选项卡，几百个按钮 |
| **应用步骤** | 最右侧 | **本章核心**，记录你对数据做的每一步操作 |
| **公式栏** | 中间上方 | 显示/编辑当前步骤的 M 代码（没有就：视图 → 勾选「公式栏」） |

> 数据预览只显示前 1000 行，且**不会自动加载全部**。所以你在预览里看着"没问题的列"，可能在第 50 万行有个脏值。真正要检查数据质量，得靠类型转换时的报错提示。

## 四、核心概念：应用步骤（Applied Steps）

这是 Power Query 最反直觉、也最重要的设计。

**你点的每一个按钮，都会被记录成右侧「应用步骤」里的一步，背后是一行 M 代码。** 它不是"直接改数据"，而是"记下一份操作配方"，刷新时重放。

### 4.1 看一个真实例子

选中 `fact_order` 查询，右侧应用步骤通常是：

| 步骤名 | 对应的 M（简化） |
|---|---|
| 源 | `MySQL.Database("localhost", "study_powerbi_demodata")` |
| 导航 | `= 源{[Schema="study_powerbi_demodata",Item="fact_order"]}[Data]` |
| 更改的类型 | `Table.TransformColumnTypes(导航, {...})` |

点任一步骤，中间预览就会**回到那一步执行完的状态**。这让调试变得极其方便 —— 你可以一步步回退，找出是哪一步把数据弄坏的。

### 4.2 步骤的三个操作

| 操作 | 做法 | 效果 |
|---|---|---|
| **查看** | 点步骤名 | 预览回到该步骤 |
| **删除** | 点步骤右边的 × | 撤销该步（后面的步骤也可能跟着报错） |
| **插入** | 选中某步 → 再做新操作 | 新步骤插在选中步骤之后 |

> ⚠️ **踩坑提醒**：删除中间步骤常常导致后续步骤报错（因为后续步骤引用了被删步骤产出的列名）。报错了别慌，看错误提示里说"找不到 XX 列"，就是断在这里。

### 4.3 重命名步骤（好习惯）

默认步骤名是中文的「更改的类型」「筛选的行」，但当你有 20 步时根本分不清。

右键步骤 → **重命名**，改成有意义的名字，比如：

- 「源」→「源-MySQL订单表」
- 「更改的类型」→「转换-金额转decimal日期转date」
- 「筛选的行」→「过滤-排除测试数据」

> **FDE 视角**：你写的查询，三个月后客户要改需求，或者交接给同事。清晰命名的步骤 = 自解释的文档。**这是专业性最便宜的体现方式。**

## 五、常用转换操作（按使用频率排序）

### 5.1 更改类型（最高频，也是报错之王）

每列右上角有个图标（`ABC` = 文本，`123` = 数字，日历 = 日期），点击可改类型。

**必须做的原因**：从数据库/Excel 导入时，Power Query 会"猜"类型。猜错了后面全错（日期当文本 → 时间智能全废；金额当文本 → 不能求和）。

**正确做法**：

1. 选中要改的列（Ctrl 多选）
2. 开始 → 数据类型 → 选正确类型
3. **一定要用「替换当前转换」**，不要用「添加为新步骤」

`fact_order` 的正确类型：

| 列 | 类型 |
|---|---|
| `order_id` / `customer_id` / `region_id` | 整数 |
| `order_date` | 日期 |
| `status` / `payment_method` | 文本 |
| `order_amount` / `order_profit` | 定点小数（Decimal） |

> ⚠️ **踩坑提醒**：金额**不要用"小数"而要用"定点小数（Decimal）"**。浮点数在累加时会有精度误差（0.1+0.2=0.30000000000000004），财务数据用定点小数才安全。MySQL 的 `DECIMAL(12,2)` 对应这里就是定点小数。

### 5.2 删除列 / 选择列

- **删除列**：选中列 → 右键 → 删除列
- **反向选择**：「选择列」→ 勾选要保留的（列很多时更快）

**原则**：**不用的列全部删掉。** 每留一列，模型和文件就大一分，刷新就慢一分。本库 6 张表的字段都是必需的，不用删；但客户给你的 200 列大表，你可能只用 30 列。

### 5.3 筛选行

点列头的下拉箭头，和 Excel 一样。

进阶：筛选后可以在公式栏看到 M 代码，比如：

```m
= Table.SelectRows(更改的类型, each ([status] = "已完成"))
```

手工改这段代码就能实现复杂筛选，比如排除多个值：

```m
= Table.SelectRows(更改的类型, each ([status] = "已完成" or [status] = "退款"))
```

### 5.4 添加自定义列（用公式造新列）

「添加列」→ 自定义列，可以写 M 表达式。

**例子：给 `fact_order_item` 加一列"行毛利率"**

```m
= [line_profit] / [line_amount]
```

**例子：加一列"是否大额订单"**

```m
= if [line_amount] >= 1000 then "大额" else "普通"
```

> **重要提醒**：能在**度量值**里算的，就不要在这里加列。
>
> 判断标准：**这个值是"每一行固定不变的"还是"会随筛选聚合而变的"？**
>
> - 行毛利率（`line_profit / line_amount`）→ 每行固定 → 可以加列... 但**别加**，因为一旦按品类聚合，你要的是 `SUM(利润)/SUM(金额)`（加权），而不是各行毛利率的平均。这是 ch05 的核心陷阱。
> - 金额区间标签（大额/普通）→ 每行固定 → **适合**加列，因为它只是个分组标签。

### 5.5 拆分列 / 合并列

- **拆分列**：按分隔符拆（如 `"广东-深圳"` 拆成两列），或按字符数拆
- **合并列**：选中多列 → 合并列 → 选分隔符

典型场景：客户导出的 `"2024-06-15 00:00:00"` 要拆出日期部分。

### 5.6 逆透视（Unpivot）—— 处理"宽表"的杀手锏

这是很多人不会、但一旦会了就离不开的功能。

**问题**：客户给你的表长这样（**宽表**，月份做列头）：

| 省份 | 1月 | 2月 | 3月 |
|---|---:|---:|---:|
| 广东 | 100 | 120 | 90 |
| 浙江 | 80 | 95 | 110 |

这种表 Power BI 极难分析（你没法把"月份"拖到轴上，因为月份是列名不是数据）。

**解法：逆透视列**，变成（**长表**）：

| 省份 | 月份 | 值 |
|---|---:|---:|
| 广东 | 1月 | 100 |
| 广东 | 2月 | 120 |
| 浙江 | 1月 | 80 |

**操作**：

1. 选中「省份」列（**不参与逆透视的列**）
2. 右键 → **逆透视其他列**
3. 完成，重命名「属性」→ 月份，「值」→ 销售额

**口诀**：

> **宽表变长表 = 逆透视（Unpivot）**
> **长表变宽表 = 透视列（Pivot）**
> Power BI 喜欢**长表**（因为长表才符合"事实表"的形态）。

### 5.7 合并查询 vs 追加查询（极易混淆）

| | 合并查询（Merge） | 追加查询（Append） |
|---|---|---|
| 方向 | **横向**加列 | **纵向**加行 |
| 类比 | SQL 的 `JOIN` | SQL 的 `UNION ALL` |
| 用途 | 给事实表补上维度属性 | 把 12 个月的 12 个文件合成一张表 |
| 操作 | 选匹配列 + 联接种类 | 选要追加的表（≥2 张） |

**合并查询的联接种类**（和 SQL 一一对应）：

| Power Query | SQL |
|---|---|
| 内部 | `INNER JOIN` |
| 左外部 | `LEFT JOIN` |
| 右外部 | `RIGHT JOIN` |
| 完全外部 | `FULL OUTER JOIN` |
| 左反 | `... WHERE id NOT IN (...)` |

典型用法：**用合并查询把维度表的属性拉进事实表**（相当于在 Power Query 层做 denormalize）。但注意 —— **本库不要这么做**，因为我们已经用关系建模了（ch02），在 Power Query 里重复拉列会让模型变大且失去星型优势。

**追加查询**的典型场景：客户给了 `2024Q1.xlsx`、`2024Q2.xlsx`、`2024Q3.xlsx`、`2024Q4.xlsx` 四个结构相同的文件 → 追加成一张表。

## 六、M 语言基础

你不需要成为 M 专家，但要**能看懂、能改**。

### 6.1 最小结构：let ... in

```m
let
    源 = MySQL.Database("localhost", "study_powerbi_demodata"),
    订单表 = 源{[Schema="study_powerbi_demodata",Item="fact_order"]}[Data],
    改类型 = Table.TransformColumnTypes(订单表, {{"order_amount", type number}})
in
    改类型
```

读法：

- `let` 后面是一系列**赋值语句**（每一步起个名字）
- 每个步骤用**逗号**结尾（最后一步前）
- `in` 后面是**最终输出**（通常是最后一个步骤名）
- 步骤之间用**名字**互相引用（`订单表` 是上一步的名字）

**这就是"应用步骤"的本质** —— 右侧面板里你看到的每一步，就是 `let` 里的一行。

### 6.2 三种数据类型

M 有三种容器，理解它们就理解了 80% 的 M：

| 类型 | 写法 | 类比 | 例子 |
|---|---|---|---|
| **值（Value）** | `123`、`"文本"`、`#date(2024,6,15)` | 单个单元格 | `[line_amount]` |
| **列表（List）** | `{1, 2, 3}` | 一列 | `{1..12}` 生成 1 到 12 |
| **记录（Record）** | `[姓名="张三", 年龄=30]` | 一行 | `[product_id=1, name="耳机"]` |
| **表（Table）** | `{[...], [...]}` 或用函数生成 | 多行列 | 整个查询 |

**访问方式**：

| 写法 | 含义 |
|---|---|
| `[列名]` | 当前行的某列（在 `each` 里用） |
| `表[列名]` | 取出整列，返回一个 List |
| `表{0}` | 取第 1 行，返回一个 Record（**从 0 开始计数**） |
| `表{0}[列名]` | 第 1 行的某列 |

### 6.3 each 和 _（下划线）

这是 M 里最让人困惑的语法，其实很简单。

`each` = "对每一行"，`_` = "当前这一行"。

```m
// 每一行 → 取 line_profit 除以 line_amount
= Table.AddColumn(源, "行毛利率", each [line_profit] / [line_amount])

// 等价于（完整写法，_ 就是当前行）
= Table.AddColumn(源, "行毛利率", (_) => _[line_profit] / _[line_amount])
```

两种写法完全等价，`each` 是简写。看到 `_[...]` 时，心里读成"当前行的 XX 列"。

**练习一下**：

```m
// 生成 1 到 5，每个乘 2，得到 {2,4,6,8,10}
let
    源 = {1..5},
    翻倍 = List.Transform(源, each _ * 2)
in
    翻倍
```

这里 `_` 是列表里的每个元素（不是行），因为 `List.Transform` 传的是值而不是记录。

### 6.4 常用函数速查

| 函数 | 作用 | 例子 |
|---|---|---|
| `Table.SelectRows` | 筛选行 | `Table.SelectRows(源, each [status]="已完成")` |
| `Table.SelectColumns` | 选列 | `Table.SelectColumns(源, {"order_id","order_amount"})` |
| `Table.AddColumn` | 加列 | `Table.AddColumn(源, "毛利率", each [利润]/[金额])` |
| `Table.TransformColumnTypes` | 改类型 | `Table.TransformColumnTypes(源, {{"金额", type number}})` |
| `Table.Group` | 分组聚合 | `Table.Group(源, {"省"}, {{"总额", each List.Sum([金额]), type number}})` |
| `Table.Sort` | 排序 | `Table.Sort(源, {{"金额", Order.Descending}})` |
| `Table.Distinct` | 去重 | `Table.Distinct(源, {"customer_id"})` |
| `Table.UnpivotOtherColumns` | 逆透视 | 见 5.6 |
| `Table.NestedJoin` | 合并查询 | 复杂，一般用界面操作 |
| `Table.Combine` | 追加查询 | `Table.Combine({表1, 表2, 表3})` |
| `List.Dates` | 生成日期列表 | `List.Dates(#date(2023,1,1), 1096, #duration(1,0,0,0))` |
| `Date.Year` / `Date.Month` | 取年/月 | `Date.Year([date_key])` |

## 七、进阶：参数化数据源

**场景**：你在本机开发好了报表，现在要部署到客户服务器。数据库地址从 `localhost` 变成 `192.168.1.100`，你要改几个地方？

如果不做参数化：`源` 步骤里硬编码了地址，你要改 6 张表的 6 个查询 —— 而且容易漏。

**参数化解法**：

### 7.1 创建参数

1. Power Query 编辑器 → 开始 → 管理参数 → 新建参数
2. 建两个参数：

| 名称 | 类型 | 当前值 |
|---|---|---|
| `pServer` | 文本 | `localhost` |
| `pDatabase` | 文本 | `study_powerbi_demodata` |

### 7.2 在查询里引用参数

选中 `fact_order` 查询的第一个步骤「源」，把公式栏里的：

```m
= MySQL.Database("localhost", "study_powerbi_demodata")
```

改成：

```m
= MySQL.Database(pServer, pDatabase)
```

**改完点"确定"，如果提示需要权限，点"编辑权限 → 确定"。**

对 6 个查询重复这个操作。

### 7.3 切换环境

以后要换服务器，只需：主页 → 转换数据下拉 → **编辑参数** → 改 `pServer` 的值 → 刷新。

**一处修改，全局生效。**

> ⚠️ **踩坑提醒**：改参数后必须**刷新**才生效。而且如果新服务器的表结构不同，可能报错 —— 这是好事，早点发现比上线后崩掉强。
>
> **FDE 视角**：参数化 + 后面 ch11 的网关配置，是"开发/测试/生产"三环境切换的基础。客户一定会问你"测试库和生产库怎么切"，答案就在这里。

## 八、进阶：查询折叠（性能命门）

这是本章**最有价值**的知识点，也是区分新手和老手的分水岭。

### 8.1 什么是查询折叠

当你在 Power Query 里做筛选、改类型、分组时，Power Query **并不自己算**，而是把这些操作**翻译成 SQL 发给源数据库执行**。

```
你的操作                Power Query 翻译成            数据库执行
筛选 status='已完成'  ──▶  SELECT ... WHERE status='已完成'  ──▶  返回 2366 行
```

这个「把操作翻译成原生 SQL」的过程叫 **查询折叠（Query Folding）**。

### 8.2 为什么它决定性能

| | 折叠生效 ✅ | 折叠断裂 ❌ |
|---|---|---|
| 谁在算 | **数据库**（有索引、有多核、有优化器） | Power Query 引擎（单线程、内存里逐行算） |
| 传输量 | 只传结果（2,366 行） | 先全量拉回（3,529 行甚至整表） |
| 100 万行表耗时 | 秒级 | 分钟级甚至超时 |

**数据量越大，差距越夸张。** 在千万行级的表上，折叠断裂意味着刷新从 30 秒变成 30 分钟。

### 8.3 怎么判断折叠是否断裂

**方法**：在应用步骤里，**右键最后一步** → 看「**查看本机查询**」（View Native Query）这个选项：

- **可点击（黑色）** → 折叠生效 ✅，点开能看到生成的 SQL
- **灰色不可点** → 折叠断裂 ❌

**逐个步骤右键检查，就能定位是哪一步断的。**

### 8.4 什么会导致折叠断裂

| 会断的操作 | 不断的操作 |
|---|---|
| 加自定义列（用了复杂 M 函数） | 筛选行 |
| 加索引列 | 选择/删除列 |
| 对日期做本地化转换（如取中文星期名） | 更改类型（简单类型） |
| 合并查询（部分情况） | 分组聚合（部分情况） |
| 使用只有 Power Query 有的函数 | 排序（部分情况） |
| **在中间步骤用了 Excel/CSV 源** | 逆透视（部分情况） |

**最保险的做法**：**把会断折叠的操作放到最后。**

比如你要加一个自定义列（会断），又要在前面筛选（能折叠）：

✅ 正确顺序：`源 → 筛选行（折叠）→ 加自定义列（这里开始断）`
❌ 错误顺序：`源 → 加自定义列（立刻断）→ 筛选行（再也无法折叠，全表拉回内存筛）`

### 8.5 本库验证

选中 `fact_order`，在最后一步右键「查看本机查询」，你会看到类似：

```sql
select `order_id`, `customer_id`, `region_id`, `order_date`,
       `status`, `payment_method`, `order_amount`, `order_profit`
from `study_powerbi_demodata`.`fact_order`
```

**说明折叠生效** —— Power Query 把整个查询翻译成了一条 SQL 发给 MySQL。

现在试着加一个自定义列（添加列 → 自定义列，随便写 `[order_amount] * 1`），再右键最后一步看「查看本机查询」：**变灰了**，折叠断裂。

删掉这个自定义列，折叠恢复。

> **这个实验一定要亲手做一次**，比读十遍文档都管用。

## 九、实操：用 M 独立生成一张日期表

ch02 说日期表要满足「唯一 + 连续 + 整年」。如果客户系统里没有日期表，你可以**完全用 M 生成一张**，不依赖任何源数据。

### 9.1 建一个空白查询

1. Power Query 编辑器 → 主页 → 新建源 → **空白查询**
2. 选中新查询，打开「高级编辑器」（开始 → 高级编辑器）
3. 粘贴以下代码：

```m
let
    // 起止日期
    开始日期 = #date(2023, 1, 1),
    结束日期 = #date(2025, 12, 31),
    天数 = Duration.Days(结束日期 - 开始日期) + 1,

    // 生成连续日期列表
    日期列表 = List.Dates(开始日期, 天数, #duration(1, 0, 0, 0)),

    // 列表转表
    转表 = Table.FromList(日期列表, Splitter.SplitByNothing(), {"date_key"}),
    改类型 = Table.TransformColumnTypes(转表, {{"date_key", type date}}),

    // 派生各列
    加年 = Table.AddColumn(改类型, "year", each Date.Year([date_key]), Int64.Type),
    加季 = Table.AddColumn(加年, "quarter", each Date.QuarterOfYear([date_key]), Int64.Type),
    加月 = Table.AddColumn(加季, "month", each Date.Month([date_key]), Int64.Type),
    加月名 = Table.AddColumn(加月, "month_name",
              each Date.ToText([date_key], [Format="yyyy年M月"]), type text),
    加周序 = Table.AddColumn(加月名, "week_of_year",
              each Date.WeekOfYear([date_key]), Int64.Type),
    加星期 = Table.AddColumn(加周序, "day_of_week",
              each Date.DayOfWeek([date_key], Day.Monday) + 1, Int64.Type),
    加星期名 = Table.AddColumn(加星期, "weekday_name",
              each Date.ToText([date_key], [Format="ddd"]), type text),
    加周末 = Table.AddColumn(加星期名, "is_weekend",
              each if Date.DayOfWeek([date_key], Day.Monday) >= 5 then 1 else 0, Int64.Type),
    加假日 = Table.AddColumn(加周末, "is_holiday",
              each if Date.Month([date_key]) = 1 and Date.Day([date_key]) = 1 then 1
              else if Date.Month([date_key]) = 5 and Date.Day([date_key]) = 1 then 1
              else if Date.Month([date_key]) = 10 and Date.Day([date_key]) = 1 then 1
              else 0, Int64.Type)
in
    加假日
```

4. 点「完成」，把查询重命名为 `dim_date_m`
5. 关闭并应用

**预期结果**：生成 **1,096 行**，与导入的 `dim_date` 完全一致。

### 9.2 用它替换原日期表（可选练习）

1. 删除 `dim_date` 与 `fact_order` 的旧关系
2. 建新关系：`dim_date_m[date_key]` → `fact_order[order_date]`
3. 标记 `dim_date_m` 为日期表
4. 验证 ch02 的各省矩阵数字**完全不变**

**为什么这招很实用**：客户数据库里经常没有日期表，或者日期表只有工作日（缺周末，不连续）。自己生成 = 完全可控。

> **注意**：用 M 生成的日期表**没有折叠问题**（它不查数据库，纯本地计算），所以对刷新性能几乎无影响。

## 十、FDE 现场场景

### 场景 1：客户只给 Excel，每月发一次

**痛点**：每月手动换文件，容易漏、容易错。

**解法**：

1. 让客户把文件放到**固定的文件夹**，文件名带年月（如 `sales_202406.xlsx`）
2. Power Query 用「**从文件夹**」获取数据
3. 它会自动读取文件夹里所有文件并追加（ch03 的「追加查询」）
4. 以后客户只要把新文件丢进文件夹，你点刷新就行

**这一步能把你从"每月手工处理 2 小时"解放成"点一下刷新"。**

### 场景 2：数据里有测试单/内部单

**常见情况**：客户系统里混着 `status='测试'` 的订单，或者金额是 0.01 的内部测试单。

**解法**：在 Power Query 最前面加筛选步骤排除掉。

**但要小心** —— 这一步会让业务方看到的数字和他们系统里的"总单数"对不上。**一定要先跟客户确认"排除测试单"是他们要的口径**，并且最好在报表上标注"数据已排除测试单"。

> **口径确认比技术实现重要得多。** 我见过太多报表上线后被质疑"你这数跟我们系统不一样"，最后发现是清洗时悄悄排除了某些数据却没说。**凡是你在清洗层做的过滤，都要在需求确认时讲出来。**

### 场景 3：刷新太慢

**排查顺序**：

1. **先看折叠**：每个查询最后一步右键「查看本机查询」，灰了就是断了
2. **检查是不是拉了整张表**：在筛选步骤之前有没有断折叠的操作
3. **删掉不用的列**：列越少传输越快
4. **减少步骤**：有些步骤可以合并
5. **最后才考虑增量刷新**（ch11）

### 练习 2：在 M 里过滤已取消，观察口径变化（考：清洗位置影响口径）

**题目**：在 `fact_order` 查询里加一步筛选，排除 `status = "已取消"`。然后看报表上「订单数」和「销售额」的变化。

**预期结果**：

| 指标 | 过滤前 | 过滤「已取消」后 |
|---|---:|---:|
| 订单数 | 3,529 | **2,938**（3,529 - 591） |
| 销售额 | 10,689,549.70 | **8,941,109.07**（10,689,549.70 - 1,748,440.63） |
| 有效销售额（再筛已完成） | 7,195,492.73 | **7,195,492.73（不变）** |

**解析**（本题的精髓）：

- 排除「已取消」后，**总销售额降了 1,748,440.63**
- 但**有效销售额完全不变**（还是 7,195,492.73）—— 因为有效销售本来就只算「已完成」，跟「已取消」无关

**这说明了什么**：

在 Power Query 里过滤 ≠ 在 DAX 里过滤，两者**作用层级完全不同**：

| 位置 | 影响范围 | 能否被用户改回 |
|---|---|---|
| **Power Query 过滤** | 数据根本没进模型，**永久删除** | ❌ 用户无法在报表里看到被过滤的数据 |
| **DAX 度量值过滤**（`CALCULATE` + status） | 只影响这一个度量值 | ✅ 用户可以用切片器切换 |
| **报表筛选器** | 只影响当前页 | ✅ 用户可改 |

**决策原则**：

> **属于"脏数据/不该进分析"的（测试数据、作废记录）→ 在 Power Query 过滤。**
> **属于"业务口径可切换"的（订单状态）→ 留在 DAX 里过滤，交给用户选。**

本库的「已取消/退款」属于后者 —— 因为业务方可能想看"取消率"，你把它删了就看不到了。**所以正确做法是不在 Power Query 过滤，而在度量值里筛。**

**验证 SQL**：

```sql
SELECT COUNT(*) AS 订单数, ROUND(SUM(order_amount),2) AS 销售额
FROM fact_order WHERE status <> '已取消';
-- 预期：2938 | 8941109.07
```

### 练习 3：找出折叠断裂点（考：查询折叠）

**题目**：在 `fact_order_item` 查询上依次做三个操作，每做一步就右键最后一步看「查看本机查询」是否可点：

1. 筛选 `quantity >= 1`
2. 添加自定义列 `测试 = [line_amount] * 1`
3. 再筛选 `discount_rate > 0`

记录每一步的折叠状态。

**答案与解析**：

| 步骤 | 折叠状态 | 原因 |
|---|---|---|
| 筛选 `quantity >= 1` | ✅ 生效 | 简单筛选，能翻译成 `WHERE quantity >= 1` |
| 加自定义列 `测试` | ❌ **断裂** | 自定义列用了 M 表达式，MySQL 没有对应函数 |
| 再筛选（第 3 步） | ❌ 仍然断 | **一旦断了，后面的步骤再也折叠不回去** |

**关键结论**：**折叠是"一断全断，不可逆"的。** 只要在中间某步断了，后面所有步骤都只能在 Power Query 内存里算。

**所以操作顺序原则是**：

```
✅ 源 → 筛选（折叠）→ 选列（折叠）→ 简单改类型（折叠）→ 加自定义列（这里才开始断）
❌ 源 → 加自定义列（立刻断）→ 筛选（无法折叠，全表拉回内存）
```

**验证方法**：点开「查看本机查询」，你会看到生成的 SQL 里包含了你所有的折叠步骤。做完第 1 步时看，应该能看到 `WHERE quantity >= 1` 被翻译进去了。

### 练习 4：用 M 生成日期表（考：动手能力）

**题目**：按第 9 节生成 `dim_date_m`，验证行数，并用它替换原 `dim_date` 后验证数字不变。

**预期结果**：

| 检查项 | 预期 |
|---|---:|
| `dim_date_m` 行数 | **1,096** |
| 首行日期 | 2023-01-01 |
| 末行日期 | 2025-12-31 |
| 周六周日总行数（`is_weekend=1`） | **313** |
| 法定假日行数（`is_holiday=1`） | **9**（3 年 × 3 天：元旦/五一/国庆） |
| 替换后广东有效销售额 | **1,078,152.70（不变）** |

**解析**：

- 周末天数：2023-2025 共 1,096 天，其中周末约 313 天
- 本库 `is_holiday` 只标记元旦(1-1)、劳动节(5-1)、国庆(10-1) 三天，3 年 = 9 天
- **注意**：这是简化处理，真实节假日要调休、连休，需要用完整节日历表

**验证 SQL**：

```sql
SELECT COUNT(*) AS 总天数,
       SUM(is_weekend) AS 周末天数,
       SUM(is_holiday) AS 假日天数
FROM dim_date;
-- 预期：1096 | 313 | 9
```

### 练习 5：逆透视实战（考：宽表处理）

**题目**：假设客户给你这样一张宽表（用「输入数据」手工建一个查询）：

| 省份 | 2023 | 2024 | 2025 |
|---|---:|---:|---:|
| 广东 | 800000 | 850000 | 900000 |
| 浙江 | 600000 | 700000 | 750000 |

把它逆透视成三列（省份 / 年份 / 销售额），并说出逆透视后有几行。

<details>
<summary>Hint</summary>
选中「省份」列 → 右键 → 逆透视其他列。
</details>

**答案与解析**：

**操作**：选中「省份」列 → 右键 → **逆透视其他列** → 把「属性」重命名为「年份」，「值」重命名为「销售额」。

**结果（6 行）**：

| 省份 | 年份 | 销售额 |
|---|---|---:|
| 广东 | 2023 | 800000 |
| 广东 | 2024 | 850000 |
| 广东 | 2025 | 900000 |
| 浙江 | 2023 | 600000 |
| 浙江 | 2024 | 700000 |
| 浙江 | 2025 | 750000 |

**解析**：2 省 × 3 年 = **6 行**。逆透视的本质是「把列头变成数据」。

**为什么必须这么做**：Power BI 里"年份"要能拖到 X 轴、能做切片器，它必须是**一列数据**，而不是三个列名。宽表做不到，长表可以。

**反过来想**：如果你想把长表变回宽表（比如做交叉表展示），用「透视列」，或者直接在矩阵视觉对象里把年份拖到「列」区域 —— **后者更推荐**，因为不需要动数据。
