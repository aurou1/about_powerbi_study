## 二、核心概念：三种 DAX 对象

同样是写一个公式，放在三个不同地方，行为完全不同。

| | **度量值（Measure）** | **计算列（Calculated Column）** | **计算表（Calculated Table）** |
|---|---|---|---|
| 建在哪 | 建模 → 新建度量值 | 表工具 → 新建列 | 建模 → 新建表 |
| **什么时候算** | **查询时**（用户每次交互） | **刷新时**（加载完就算好） | **刷新时** |
| **存在哪** | **不占内存**（只存公式） | **占内存**（每行存一个值） | **占内存**（整张表） |
| **随筛选变化吗** | ✅ **会**（核心能力） | ❌ 不会（值已固定） | ❌ 不会 |
| 能做聚合吗 | ✅ 天然就是聚合 | ❌ 只能算单行 | ✅ |
| 典型用途 | 销售额、利润、占比、排名 | 分组标签、行级固定属性 | 日期表、辅助表、桥接表 |

### 2.1 直观对比

`fact_order_item` 有 8,445 行。

**度量值**：

```dax
总销售额 = SUM('fact_order_item'[line_amount])
```

- 存的只是**一行公式**，几乎不占空间
- 按品类切片 → 算品类的；按年份切片 → 算年份的
- **同一个公式，在不同筛选下给出不同答案** ← 这就是 DAX 的威力

**计算列**：

```dax
行毛利率 = 'fact_order_item'[line_profit] / 'fact_order_item'[line_amount]
```

- 刷新时计算，**每行存一个值**（8,445 个数）
- 值**永久固定**，不随切片器变化
- 文件变大，刷新变慢

### 2.2 什么时候该用计算列

判断标准只有一条：

> **这个值是否"每一行都固定不变"？**

| 场景 | 用计算列？ | 理由 |
|---|---|---|
| 行毛利率（`利润/金额`） | ❌ 不该 | 每行虽固定，但你要的是**聚合后的加权毛利率**（`SUM(利润)/SUM(金额)`），两者不同（ch05 详解） |
| 金额区间标签（大额/普通） | ✅ 该 | 只是分组标签，用来做坐标轴/图例 |
| 客户姓+名拼接 | ✅ 该 | 每行固定的文本 |
| 「该客户的总消费」 | ❌ 不该 | 这是聚合，用度量值 |
| 日期表里的年/季/月 | ✅ 该（或 Power Query 做） | 每行固定 |

> ⚠️ **踩坑提醒**：新手最爱用计算列，因为它"像 Excel"。**但计算列是 Power BI 性能问题的头号来源之一。** 能用度量值就用度量值，能用 Power Query 就在 Power Query 做（ch03），计算列是最后选择。

### 2.3 计算表

```dax
日期表 = CALENDAR(DATE(2023,1,1), DATE(2025,12,31))
```

生成 1,096 行的表。主要用途：造日期表、造辅助表（Top N 参数表）、造桥接表。本教程用得少。

## 三、DAX 语法基础

### 3.1 引用规则

```dax
'表名'[列名]     -- 完整写法（表名含空格或中文时必须加单引号）
[列名]           -- 简写（同一表的计算列里可用）
```

**建议：永远写全 `'表名'[列名]`**，避免歧义。本库写法：

```dax
'fact_order_item'[line_amount]     -- ✅
'fact_order'[status]               -- ✅
```

### 3.2 运算符

| 类型 | 运算符 | 说明 |
|---|---|---|
| 算术 | `+` `-` `*` `/` `^` | 除法建议用 `DIVIDE()` |
| 比较 | `=` `<>` `>` `<` `>=` `<=` | **等于用单个 `=`**，不是 `==` |
| 逻辑 | `&&`（且）`\|\|`（或）`NOT()` | 也可用 `AND()` / `OR()` |
| 文本连接 | `&` | `"广东" & "-" & "深圳"` |

> ⚠️ **常见错误**：DAX 里判断相等是**一个** `=`。写 `==` 会报错。

### 3.3 常用聚合函数

| 函数 | 作用 |
|---|---|
| `SUM(列)` / `AVERAGE(列)` / `MIN()` / `MAX()` | 求和/平均/最小/最大 |
| `COUNT(列)` | 计数（非空值） |
| `COUNTROWS(表)` | 数表的行数 |
| `DISTINCTCOUNT(列)` | 去重计数 |
| `COUNTBLANK(列)` | 数空值 |

**本库最常用**：

```dax
SUM('fact_order_item'[line_amount])        -- 销售额
DISTINCTCOUNT('fact_order'[order_id])      -- 订单数
COUNTROWS('fact_order')                    -- 订单数（一行一单，等价且更快）
```

> **小技巧**：`COUNTROWS(表)` 比 `COUNT(列)` 快（不用扫描具体列）。

## 四、DIVIDE vs /（除零保护）

```dax
毛利率 = [有效利润] / [有效销售额]        -- 分母为 0 时报 #DIV/0! 或 Infinity
毛利率 = DIVIDE([有效利润], [有效销售额]) -- 分母为 0 时返回空白 ✅
```

完整语法：`DIVIDE(分子, 分母, [替代值])`

```dax
DIVIDE([有效利润], [有效销售额], 0)       -- 分母为 0 时返回 0
DIVIDE([有效利润], [有效销售额], BLANK()) -- 返回空白（默认）
```

**为什么重要**：报表中冒出 `#DIV/0!` 会让人觉得"这报表是坏的"。切片器随便一点，某个组合没数据就冒出一片错误。

> **FDE 视角**：业务方对错误的容忍度极低。偶尔冒 `#DIV/0!` 的报表会被认为"不稳定"而弃用，哪怕 99% 时间是对的。**所有除法都用 `DIVIDE`，成本为零，收益很大。**

## 五、VAR / RETURN（变量）

**不用 VAR（重复计算）**：

```dax
销售额同比% =
DIVIDE(
    [有效销售额] - CALCULATE([有效销售额], SAMEPERIODLASTYEAR('dim_date'[date_key])),
    CALCULATE([有效销售额], SAMEPERIODLASTYEAR('dim_date'[date_key]))
)
```

`CALCULATE(...)` 写了两遍 → 算两遍。

**用 VAR（清晰 + 高效）**：

```dax
销售额同比% =
VAR 今年 = [有效销售额]
VAR 去年 = CALCULATE([有效销售额], SAMEPERIODLASTYEAR('dim_date'[date_key]))
RETURN
    DIVIDE(今年 - 去年, 去年)
```

**规则**：

1. `VAR` 必须在 `RETURN` 之前声明
2. 变量名**不能和表名/列名相同**
3. 变量一旦赋值就**不可变**
4. 后面的变量可以引用前面的变量

> **重要**：VAR 的值在**声明时的筛选上下文**里计算，之后不再改变。这个特性在 ch05 讲上下文时非常关键。

## 六、隐式度量值 vs 显式度量值

### 6.1 什么是隐式度量值

你直接把 `fact_order_item[line_amount]` 拖进卡片，Power BI 自动套一个 `SUM`。这个自动生成的聚合叫**隐式度量值**。

**三个问题**：

| 问题 | 说明 |
|---|---|
| 不能复用 | 别的图表想用同一逻辑，得重新拖 |
| 不能引用 | 度量值里没法引用它（没有名字） |
| 行为不可控 | 不知道默认用了 SUM 还是 COUNT |

### 6.2 正确做法：建显式度量值

```dax
有效销售额 =
CALCULATE(
    SUM('fact_order_item'[line_amount]),
    'fact_order'[status] = "已完成"
)
```

建好后，**所有图表都拖这个度量值**。

### 6.3 建议：隐藏原始金额列

建完度量值后，把 `line_amount`、`line_profit`、`order_amount` **隐藏**（模型视图 → 右键列 → 隐藏）。

**好处**：

- 强制只能用度量值（避免口径不一致）
- 字段列表清爽
- 从源头杜绝"两张表金额同时求和"的翻倍错误

> **这是专业模型和业余模型的分界线。** 打开模型，如果事实表所有数值列都可见，说明作者没建度量值体系。

## 七、实操：建 8 个基础度量值

全部建在 `fact_order_item` 表上（选中该表 → 新建度量值）。

### 7.1 总销售额（全部订单，含作废）

```dax
总销售额 = SUM('fact_order_item'[line_amount])
```

**预期：10,689,549.70**

> 这不是真实业绩（含已取消和退款），仅用于演示口径差异。

### 7.2 有效销售额 ★

```dax
有效销售额 =
CALCULATE(
    SUM('fact_order_item'[line_amount]),
    'fact_order'[status] = "已完成"
)
```

**预期：7,195,492.73**

**为什么用 `fact_order_item` 而不是 `fact_order`？**
`line_amount` 在明细表（最细粒度），能和 `dim_product` 正确关联 —— 按品类/品牌/商品分析必须走明细表。

**为什么筛选条件写 `'fact_order'[status]`？**
`status` 在订单头表。由于 `fact_order`（一端）→ `fact_order_item`（多端），筛选会**自动从订单头流到明细**，所以完全有效。

### 7.3 有效利润

```dax
有效利润 =
CALCULATE(
    SUM('fact_order_item'[line_profit]),
    'fact_order'[status] = "已完成"
)
```

**预期：1,706,864.78**

### 7.4 有效销量

```dax
有效销量 =
CALCULATE(
    SUM('fact_order_item'[quantity]),
    'fact_order'[status] = "已完成"
)
```

**预期：8,626**

### 7.5 有效订单数

```dax
有效订单数 =
CALCULATE(
    DISTINCTCOUNT('fact_order'[order_id]),
    'fact_order'[status] = "已完成"
)
```

**预期：2,366**

> 用 `fact_order[order_id]`（订单号在头表唯一），直接 `DISTINCTCOUNT`。

### 7.6 客单价

```dax
客单价 = DIVIDE([有效销售额], [有效订单数])
```

**预期：3,041.21**（7,195,492.73 ÷ 2,366）

### 7.7 毛利率

```dax
毛利率 = DIVIDE([有效利润], [有效销售额])
```

**预期：23.72%**

### 7.8 单件利润

```dax
单件利润 = DIVIDE([有效利润], [有效销量])
```

**预期：197.87**（1,706,864.78 ÷ 8,626）

### 7.9 汇总核对表

把 8 个度量值拖进一个**表**视觉对象，逐项核对：

| 度量值 | 预期值 |
|---|---:|
| 总销售额 | 10,689,549.70 |
| **有效销售额** | **7,195,492.73** |
| 有效利润 | 1,706,864.78 |
| 有效销量 | 8,626 |
| 有效订单数 | 2,366 |
| 客单价 | 3,041.21 |
| 毛利率 | 23.72% |
| 单件利润 | 197.87 |

**对不上时按顺序排查**：

1. 漏了 `status = "已完成"`（会得到 10,689,549.70 系列）
2. 同时引用了 `order_amount` 和 `line_amount`（翻倍）
3. 毛利率用了 `/` 且分母为 0（报错）

## 九、进阶坑：JOIN 之后 SUM 头表金额会膨胀

这是准备本教程时**真实踩到的坑**，很典型。

### 9.1 现象

算客单价，先写 SQL 验证：

```sql
-- 写法 A（正确）
SELECT ROUND(SUM(order_amount)/COUNT(*),2) AS 客单价
FROM fact_order WHERE status='已完成';
-- 结果：3041.21

-- 写法 B（错误：JOIN 了明细表）
SELECT ROUND(SUM(o.order_amount)/COUNT(DISTINCT o.order_id),2) AS 客单价
FROM fact_order o
JOIN fact_order_item i ON o.order_id = i.order_id
WHERE o.status='已完成';
-- 结果：9192.99  ← 虚高 3.02 倍！
```

**为什么？**

`fact_order` 一行 = 一张订单。JOIN 明细表后，**一张订单被复制成 N 行**（N = 该单商品数）。

```
JOIN 前：order_id=2, order_amount=722.41     （1 行）
JOIN 后：order_id=2, order_amount=722.41     （2 行，因有 2 个商品）
         order_id=2, order_amount=722.41
```

于是 `SUM(order_amount)` 把同一订单金额**重复加了 N 次**。

### 9.2 在 Power BI 里的对应表现

| 场景 | 是否安全 |
|---|---|
| `SUM('fact_order_item'[line_amount])` | ✅ 安全 |
| `SUM('fact_order'[order_amount])` 且**不碰商品维** | ✅ 安全 |
| `SUM('fact_order'[order_amount])` 且**按品类切片** | ❌ **危险**（金额按明细行数重复计） |
| 同时把两列金额拖进同一卡片 | ❌ **必错**（翻倍） |

### 9.3 防御规则

> **规则 1**：只要报表可能按**商品维度**切片，金额一律用 `fact_order_item[line_amount]`。
> **规则 2**：算"订单数"用 `fact_order` 的 `DISTINCTCOUNT(order_id)`，不要用明细表数。
> **规则 3**：**任一度量值只引用一张事实表的金额列**，绝不混用。

### 9.4 怎么发现这类错误

**唯一办法：SQL 对拍。**

```sql
SELECT COUNT(*) AS 订单数, ROUND(SUM(order_amount),2) AS 有效销售额,
       ROUND(SUM(order_amount)/COUNT(*),2) AS 客单价
FROM fact_order WHERE status='已完成';
-- 2366 | 7195492.73 | 3041.21
```

记住这个基准。Power BI 里怎么摆弄都必须等于它，**变了就说明度量值或模型有问题**。

## 十、FDE 现场场景

### 场景 1：客户问"你这客单价跟我们系统不一样"

最高频质疑。原因排序：

| 排名 | 原因 | 排查方法 |
|---:|---|---|
| 1 | **口径不同**（含不含取消单/运费/税） | 问清客户公式，逐项对比 |
| 2 | **去重逻辑不同**（按订单数还是客户数） | 确认分母 |
| 3 | **JOIN 膨胀**（本章第 9 节） | SQL 不 JOIN 重算一遍 |
| 4 | **时间口径不同**（下单 vs 支付 vs 完成时间） | 确认用哪个日期字段 |

**应对话术**：

> "我们的客单价 = 已完成订单金额 ÷ 已完成订单数。您系统里是多少？我们拿同一天的数对一下，看差在哪一项。"

**永远不要说"应该是对的"**，要说"我们对一下"。

### 场景 2：客户要"毛利"，但算法很怪

真实客户算毛利可能扣运费、扣促销、按含税价算……

**做法**：

1. 让客户**写出计算公式**（最好给 Excel 例子）
2. 你在 SQL 里按他们的公式算一次，得到基准
3. 再在 Power BI 复现
4. 把「客户算法」和「你的实现」的差异写进交付文档

> **口径文档比技术本身重要。** 见过太多因为没写清口径，三个月后双方各执一词、返工重做的项目。

### 场景 3：度量值要不要建很多

**建议**：按需求建，但**基础度量值要建全**（本章 8 个）。因为：

- 基础度量值是其他度量值的积木（客单价 = 销售额 ÷ 订单数）
- 业务方加需求时只需组合，不用重写
- 建太多没人用的度量值会让模型难维护

**判断标准**：业务方问过一次的问题就建一个；没问过的等问了再建。

## 十二、练习题

### 练习 1：`/` vs `DIVIDE`（考：除零保护）

**题目**：建两个度量值，一个用 `/` 一个用 `DIVIDE`，然后在报表上用一个切片器筛到某个没有数据的品类，观察两者差异。

```dax
毛利率_斜杠 = [有效利润] / [有效销售额]
毛利率_DIVIDE = DIVIDE([有效利润], [有效销售额])
```

<details>
<summary>Hint</summary>
本库所有品类都有数据。你可以用「品牌 + 省份」两个切片器组合出一个空集，或者临时把某品类的订单在 Power Query 里过滤掉再造场景。
</details>

**答案与解析**：

- `/` 版本：显示 **`#DIV/0!`** 或 `Infinity`（红色错误）
- `DIVIDE` 版本：显示**空白**（很干净）

**解析**：当筛选后没有任何订单时，销售额 = 空白（BLANK），`利润 / 空白` 在 DAX 里会触发除零错误路径；`DIVIDE` 内置了判断，直接返回第三个参数（默认 BLANK）。

**为什么这在生产环境很重要**：报表上线后，业务方会用切片器做各种组合（比如"陕西 + 数码 + 2023年Q1"）。某些组合下确实没有数据。用 `/` 会冒出一片错误，用 `DIVIDE` 只是空白 —— 后者看起来像"这个组合没数据"，前者看起来像"报表坏了"。

**预期结果**：`/` → 错误；`DIVIDE` → 空白。

### 练习 2：故意做错 —— 让金额翻倍（考：口径 5，必做）

**题目**：建一个错误度量值，看看会得到什么：

```dax
错误_销售额翻倍 = SUM('fact_order'[order_amount]) + SUM('fact_order_item'[line_amount])
```

拖到卡片上，看数字是多少。

<details>
<summary>Hint</summary>
两张表都含订单金额：fact_order 是一单一行，fact_order_item 是一单一品一行，但 line_amount 加总 = order_amount 加总（数据字典保证）。
</details>

**答案与解析**：

**预期结果：14,391,809.86**（= 7,195,492.73 × 2）

**解析**：

- `SUM('fact_order'[order_amount])` 未过滤状态 = 10,689,549.70
- `SUM('fact_order_item'[line_amount])` 未过滤状态 = 10,689,549.70（两者恒等）
- 如果都加了 status 过滤，就是 7,195,492.73 + 7,195,492.73 = **14,391,809.86**

**这个数字看起来"完全合理"**（就是个销售额数量级），**不会报错、不会变红**，所以极难发现 —— 只有 SQL 对拍才能抓出来。

**再进一步**，如果只写 `SUM('fact_order'[order_amount])` 但报表按品类切片，会怎样？

- 品类维度在 `fact_order_item` 上 → 筛选从 `dim_product` 流到 `fact_order_item`
- 再沿 `fact_order_item` → `fact_order`（多端 → 一端，这是**反向**）
- 默认情况下（单向关系）**筛选不回流**，所以 `SUM('fact_order'[order_amount])` 会显示**每个品类都是全表总额 10,689,549.70**（不随品类变化！）

**这个现象本身就是诊断信号**：如果你看到矩阵里每一行数字都一模一样，就是筛选没传过来 —— 检查关系方向。

**预期结果**：翻倍 = 14,391,809.86；按品类切片时每行都相同（筛选未回流）。

### 练习 3：用 VAR 重写毛利率（考：VAR）

**题目**：把毛利率改成用 VAR 写，并额外算出「利润额」和「利润率排名提示」两个中间值。

**答案与解析**：

```dax
毛利率_VAR =
VAR 销售额 = [有效销售额]
VAR 利润额 = [有效利润]
VAR 利润率 = DIVIDE(利润额, 销售额)
RETURN
    利润率
```

**预期结果：23.72%**（与不用 VAR 的版本一致）

**解析**：本例中 VAR 没有性能收益（每个变量只用一次），但**可读性提升明显**。真正的性能收益出现在：

```dax
-- 好：去年同期只算一次
销售额同比% =
VAR 今年 = [有效销售额]
VAR 去年 = CALCULATE([有效销售额], SAMEPERIODLASTYEAR('dim_date'[date_key]))
RETURN DIVIDE(今年 - 去年, 去年)

-- 差：去年同期算了两次
销售额同比% =
DIVIDE(
    [有效销售额] - CALCULATE([有效销售额], SAMEPERIODLASTYEAR('dim_date'[date_key])),
    CALCULATE([有效销售额], SAMEPERIODLASTYEAR('dim_date'[date_key]))
)
```

**规则**：**同一个表达式出现两次以上，就该用 VAR 提取。**

### 练习 4：找出度量值里的三处错误（考：综合排查）

**题目**：下面这个度量值有三处问题，找出来并改正。

```dax
平均订单金额 =
AVERAGEX('fact_order_item', SUM('fact_order_item'[line_amount]))
```

<details>
<summary>Hint</summary>
想想：AVERAGEX 是逐行迭代的，它迭代的"每一行"是什么粒度？
</details>

**答案与解析**：

原式的三个问题：

| # | 问题 | 说明 |
|---:|---|---|
| 1 | **粒度错了** | `AVERAGEX` 迭代 `fact_order_item` 的每一行 = **每个商品行**，算的是"平均每个商品行的金额"，不是"平均每单金额" |
| 2 | **没有过滤状态** | 未加 `status='已完成'`，含已取消/退款 |
| 3 | **聚合嵌套错误** | `AVERAGEX(表, SUM(列))` 里 `SUM` 会返回全表总计（不受行上下文影响），导致每行都等于同一个值，平均下来还是那个值 |

**正确写法一**（用现成度量值，最推荐）：

```dax
客单价 = DIVIDE([有效销售额], [有效订单数])
```

**正确写法二**（显式迭代订单表）：

```dax
平均订单金额 =
AVERAGEX(
    FILTER('fact_order', 'fact_order'[status] = "已完成"),
    'fact_order'[order_amount]
)
```

**预期结果（两种写法都应为）**：**3,041.21**

**对照**：如果按错误写法（迭代明细行）算，得到的是 `7,195,492.73 ÷ 5,686 = 1,265.28`（有效明细行数 5,686），这是"平均每个商品行金额"，不是客单价。

**验证 SQL**：

```sql
-- 客单价（正确）
SELECT ROUND(SUM(order_amount)/COUNT(*),2) FROM fact_order WHERE status='已完成';
-- 3041.21

-- 平均商品行金额（错误口径）
SELECT ROUND(SUM(i.line_amount)/COUNT(*),2)
FROM fact_order_item i JOIN fact_order o ON i.order_id=o.order_id
WHERE o.status='已完成';
-- 1265.28
```

### 练习 5：客单价的两种算法（考：JOIN 膨胀意识）

**题目**：业务方要「客单价」，但没说清楚定义。给出两种算法的结果，并说明你会用哪个、为什么。

**答案与解析**：

| 算法 | 公式 | 结果 |
|---|---|---:|
| A：按订单 | 有效销售额 ÷ 有效订单数 | **3,041.21** |
| B：按商品行（错误） | 有效销售额 ÷ 有效商品行数 | 1,265.28 |

**我会用 A（3,041.21）**，理由：

1. **符合业务语义**："客单价"问的是"一位顾客一次下单平均花多少钱"，分母应该是**订单数**，不是商品行数
2. **业界通用**：绝大多数电商系统的客单价 = GMV ÷ 订单数
3. **不受拆单影响**：按商品行算会因为一单买得多就"变便宜"，逻辑上讲不通

**但关键是**：**要跟客户确认**。

> **FDE 视角**：这一题的考点不是 SQL 能力，而是**发现需求歧义的能力**。
> 业务方说"客单价"时，脑子里想的是 A，但你如果不问就实现，万一他们系统里是 B，报表就会被质疑。
>
> 正确做法：**把两种算法和对应数字都发给客户，让他选，并把选择结果写进口径文档。** 这花不了 10 分钟，但能省掉后面几周的返工。
