# ch05 行上下文 vs 筛选上下文（DAX 核心） 🧠

> 本章目标：彻底搞清 DAX 里**两种上下文**的区别与相互作用。
> 这是整个 DAX 的分水岭 —— 跨过去，后面所有函数一点就通；跨不过去，你写的每个度量值都在碰运气。

---

## 一、本章学习目标

学完本章你应该能：

1. 用自己的话说出**行上下文**和**筛选上下文**分别是什么、从哪来
2. 解释「为什么 `AVERAGE(毛利率列)` 算出来的毛利率是错的」，并给出正确写法
3. 说出**上下文转换（Context Transition）**是什么、哪两种情况会触发它
4. 解释「计算列里写 `SUM(...)`，为什么每一行都等于全表总计」
5. 看懂并预测矩阵里每个格子的数字

## 二、先看一个真实事故

假设你按 ch04 建好了度量值，现在业务方要「各品类毛利率」。你写了两个版本：

```dax
-- 版本 A：先加计算列，再平均
行毛利率 = 'fact_order_item'[line_profit] / 'fact_order_item'[line_amount]   -- 计算列
品类毛利率_A = AVERAGE('fact_order_item'[行毛利率])                          -- 度量值

-- 版本 B：直接除
品类毛利率_B = DIVIDE([有效利润], [有效销售额])                              -- 度量值
```

拖进矩阵，按品类看：

| 品类 | 版本 A（平均行毛利率） | 版本 B（`SUM` 相除） | 差多少 |
|---|---:|---:|---:|
| 数码 | 0.78% | **1.16%** | +0.38 |
| 食品 | 21.20% | **21.75%** | +0.55 |
| 家居 | 26.80% | **27.22%** | +0.42 |
| 服饰 | 37.75% | **38.00%** | +0.25 |
| 美妆 | 49.25% | **49.47%** | +0.22 |
| **全库合计** | **28.41%** | **23.72%** | **-4.69** |

**两个版本都对不上，而且全库级别差了 4.69 个百分点！**

业务方问你「我们毛利率到底是多少」，你答 23.72% 还是 28.41%？

**正确答案是 23.72%（版本 B）**，因为毛利率的正确算法是「总利润 ÷ 总销售额」，不是「各行毛利率的平均」。

这一章就把这个问题彻底讲透。

## 三、两种上下文的定义

| | **行上下文（Row Context）** | **筛选上下文（Filter Context）** |
|---|---|---|
| 一句话 | **"现在是第几行"** | **"现在看的是哪部分数据"** |
| 作用 | 让你能取到**当前行的某一列** | 决定聚合函数**汇总哪些行** |
| 产生方式 | 计算列、迭代函数（`X` 结尾的函数、`FILTER`） | 矩阵的行/列、切片器、筛选器窗格、其他视觉对象、`CALCULATE` |
| 类比 Excel | 在某行写公式，往下填充 | 对一列做筛选后再求和 |

### 3.1 行上下文：现在是第几行

当你在计算列里写 `[line_profit] / [line_amount]`，Power BI 必须知道：

- 用**哪一行的** `line_profit`？
- 用**哪一行的** `line_amount`？

答案由**行上下文**提供。Power BI 逐行计算，**算第 N 行时，行上下文就是第 N 行**。

```
行上下文 = 当前正在计算的这一行
```

所以计算列 `行毛利率` 在每一行都算出一个值，8,445 行就有 8,445 个值。

### 3.2 筛选上下文：现在看哪部分数据

当你在矩阵里放「品类（行）× 有效销售额（值）」：

```
               有效销售额
数码          2,612,383.09     ← 这个格子的筛选上下文 = "品类 = 数码"
食品            441,341.24     ← = "品类 = 食品"
家居          1,408,258.89     ← = "品类 = 家居"
```

**每个格子的筛选上下文不同**，所以同一个度量值 `有效销售额` 在不同格子给出不同答案。

这就是 DAX 最强大也最容易搞混的地方：**同一个公式，在不同筛选上下文里给出不同结果。**

## 四、行上下文的两个来源

### 4.1 来源一：计算列

在计算列里，**行上下文自动存在**。你可以直接引用当前行的任何列：

```dax
行毛利率 = 'fact_order_item'[line_profit] / 'fact_order_item'[line_amount]
```

### 4.2 来源二：迭代函数（`X` 函数）

所有以 **X 结尾**的函数都是迭代器，它们会**逐行遍历**一张表，并在遍历时为每行创建行上下文：

| 函数 | 作用 |
|---|---|
| `SUMX(表, 表达式)` | 逐行算表达式，再求和 |
| `AVERAGEX(表, 表达式)` | 逐行算表达式，再平均 |
| `MAXX` / `MINX` / `COUNTX` | 同理 |
| `FILTER(表, 条件)` | 逐行判断条件，返回满足条件的行 |
| `RANKX` / `TOPN` / `ADDCOLUMNS` | 也创建行上下文 |

**例子**：

```dax
-- 逐行算「数量 × 单价」，再求和
手动销售额 = SUMX('fact_order_item', 'fact_order_item'[quantity] * 'fact_order_item'[unit_price])
```

`SUMX` 遍历 `fact_order_item` 的每一行，在**行上下文**里计算 `quantity * unit_price`，最后把 8,445 个结果加起来。

> **注意**：这里的 `[quantity]` 能取值，靠的就是 `SUMX` 创建的行上下文。

## 五、筛选上下文的五个来源

一个格子的筛选上下文，由以下五部分**叠加**而成：

| # | 来源 | 例子 |
|---:|---|---|
| 1 | **视觉对象的行/列** | 矩阵行 = 品类 → 筛选"品类 = 美妆" |
| 2 | **切片器** | 年份切片器选 2024 → 筛选"年 = 2024" |
| 3 | **筛选器窗格** | 「此页上的筛选器」里设了 status = 已完成 |
| 4 | **其他视觉对象的交叉筛选** | 点柱状图里"广东"那根柱子 → 其他图也只剩广东 |
| 5 | **`CALCULATE` 函数** | 度量值内部主动修改筛选（ch06 核心） |

**它们同时生效，是"与"的关系。**

比如你设了「年份 = 2024」＋「status = 已完成」＋ 矩阵行是「广东」，那么格子的筛选上下文就是：

```
年 = 2024  AND  status = 已完成  AND  省份 = 广东
```

## 六、核心陷阱：加权平均 vs 简单平均

回到本章开头的事故。现在你能解释它了。

### 6.1 为什么两个数不一样

**版本 A：`AVERAGE(行毛利率列)` = 28.41%**

它做的是：**把 5,686 个行毛利率加起来，除以 5,686**。

每一行**权重相同** —— 一笔 12 元的零食订单，和一笔 12,649 元的数码订单，**对结果的影响一样大**。

**版本 B：`DIVIDE(SUM(利润), SUM(金额))` = 23.72%**

它做的是：**总利润 ÷ 总销售额**。

每一行的**权重 = 它的金额占比** —— 12,649 元的订单影响力是 12 元订单的一千倍。

### 6.2 权重差异在哪 —— 看数据

看看金额最大的三行（有效订单）：

| 明细 ID | 金额 | 利润 | 行毛利率 | 品类 |
|---:|---:|---:|---:|---|
| 5270 | 12,649.21 | 932.05 | 7.37% | 数码 |
| 8315 | 12,516.06 | 798.90 | 6.38% | 数码 |
| 6567 | 12,458.20 | 795.22 | 6.38% | 数码 |

**规律极其明显**：金额越大的订单，**毛利率越低**（因为大额订单集中在低毛利的数码品类）。

所以在加权平均里：

- 低毛利（6-7%）的大额订单 → **权重极高** → 把整体毛利率往下拽
- 高毛利（49%）的小额美妆订单 → **权重很低** → 拉不动整体

结果：加权 23.72% < 简单平均 28.41%。

### 6.3 再验证一次：看亏损行

有效订单里有 **489 行是亏损的**（`line_profit < 0`，占 5,686 行的 8.6%），最低行毛利率 **-14.29%**。

这些亏损行在简单平均里只占 1/5686 的权重，但在加权平均里，如果它们金额很大，就会显著拉低整体毛利 —— 事实正是如此。

### 6.4 结论与规则

> **规则：凡是"比率"类的指标（毛利率、均价、完成率、转化率），一律用「分子求和 ÷ 分母求和」，绝不能对"比率列"直接平均。**

| 指标 | ❌ 错误写法 | ✅ 正确写法 |
|---|---|---|
| 毛利率 | `AVERAGE([行毛利率])` | `DIVIDE(SUM([利润]), SUM([金额]))` |
| 平均单价 | `AVERAGE([单价])`（若各行数量不同） | `DIVIDE(SUM([金额]), SUM([数量]))` |
| 折扣率 | `AVERAGE([折扣率])` | `DIVIDE(SUM([折扣额]), SUM([原价额]))` |

**唯一的例外**：当你**确实**想知道"典型的一行是什么样"（比如"平均每笔订单的毛利率是多少"），才用简单平均 —— 但这时你必须在报表上明确标注，避免误解。

> **FDE 视角**：这是财务类报表最高频的口径争议。业务方系统里算的通常是加权口径，如果你用简单平均，数字永远对不上。**遇到"率"就先问："您这个是整体算的，还是各单平均的？"**

## 七、为什么聚合函数"看不见"行上下文

这是第二个经典困惑。

### 7.1 现象

在计算列里写：

```dax
全表销售额 = SUM('fact_order_item'[line_amount])
```

**预期**：每行显示不同的值？
**实际**：**每一行都是同一个数字**（全表总计）。

### 7.2 原因

`SUM` 这类**聚合函数**的工作方式是：

1. 查看**当前的筛选上下文**
2. 按筛选上下文取出数据子集
3. 对子集求和

**它完全不看行上下文。** 计算列虽然有行上下文（知道自己在第几行），但 `SUM` 无视它，只按筛选上下文算。

而在计算列里，**筛选上下文是空的**（没有任何筛选），所以 `SUM` 就汇总了整张表 —— 于是每行都等于全表总计。

```
聚合函数 SUM / AVERAGE / COUNT  →  只看筛选上下文，忽略行上下文
行上下文里的 [列名]            →  取当前行的值
```

### 7.3 想让聚合函数"看见"当前行，怎么办？

用 `CALCULATE` 触发**上下文转换**（下一节），或直接用 `X` 迭代函数。

## 八、上下文转换（Context Transition）

这是本章最难、也最关键的概念。

### 8.1 是什么

**上下文转换 = 把行上下文"变成"筛选上下文。**

当发生上下文转换时，DAX 会：

1. 取出当前行的所有列值
2. 把它们当作筛选条件（等价于"这一行的每一列都等于它的值"）
3. 在这个新筛选下计算表达式

### 8.2 触发方式一：在计算列里引用度量值

```dax
-- 计算列
每单销售额 = [有效销售额]      -- 引用一个度量值
```

**预期**：每行都等于全表总额（因为度量值只看筛选上下文）？
**实际**：**每行等于"该订单的销售额"**！

**为什么**：因为你引用的是**度量值**，度量值会自动被 `CALCULATE` 包裹（隐式转换）。`CALCULATE` 触发上下文转换，把当前行的所有列值变成筛选条件。

于是：

- 第 1 行（order_id=1）→ 筛选出 order_id=1 的所有明细 → 求和 → 该单金额 1,267.16
- 第 2 行（order_id=2）→ 筛选出 order_id=2 → 722.41

**验证**：这个计算列的结果应该等于同行的 `order_amount`（因为表头金额 = 明细汇总）。

### 8.3 触发方式二：显式使用 `CALCULATE`

```dax
-- 计算列：每行显示"该商品所属品类的总销售额"
品类总销售额 = CALCULATE(SUM('fact_order_item'[line_amount]), ALLEXCEPT('fact_order_item', 'fact_order_item'[category]))
```

或在度量值里：

```dax
-- 逐行计算，每行按该行的条件筛选
按行筛选求和 = SUMX(VALUES('dim_product'[category]), CALCULATE(SUM('fact_order_item'[line_amount])))
```

这里 `SUMX` 提供行上下文，`CALCULATE` 把行上下文转成筛选上下文。

### 8.4 记忆口诀

```
有行上下文，想让聚合函数"看见"当前行 → 用 CALCULATE 包一下
迭代函数（SUMX 等）里写 CALCULATE    → 每行都会被转换一次（性能注意）
```

> ⚠️ **性能提醒**：在 `SUMX` 里对大表逐行 `CALCULATE`，意味着每行都触发一次上下文转换 + 一次查询。8,445 行就是 8,445 次。小表无感，大表会明显变慢（ch10 详讲）。

## 九、实战：在矩阵里观察两种上下文

现在亲手验证。建三个对象：

```dax
-- 计算列（存在 fact_order_item 里）
行毛利率 = DIVIDE('fact_order_item'[line_profit], 'fact_order_item'[line_amount])

-- 度量值 A：简单平均
品类毛利率_简单平均 =
CALCULATE(AVERAGE('fact_order_item'[行毛利率]), 'fact_order'[status] = "已完成")

-- 度量值 B：加权（正确）
品类毛利率_加权 = DIVIDE([有效利润], [有效销售额])
```

拖一个矩阵：行 = `dim_product[category]`，值 = 三个度量值 + 有效销售额。

**预期结果**：

| 品类 | 有效销售额 | 加权毛利率 | 简单平均毛利率 | 差 |
|---|---:|---:|---:|---:|
| 数码 | 2,612,383.09 | 1.16% | 0.78% | +0.38 |
| 食品 | 441,341.24 | 21.75% | 21.20% | +0.55 |
| 家居 | 1,408,258.89 | 27.22% | 26.80% | +0.42 |
| 服饰 | 1,351,789.04 | 38.00% | 37.75% | +0.25 |
| 美妆 | 1,381,720.47 | 49.47% | 49.25% | +0.22 |
| **合计** | **7,195,492.73** | **23.72%** | **28.41%** | **-4.69** |

**注意「合计」行的反常现象**：

- 各品类的两个版本**差距都很小**（0.2-0.6 个百分点）
- 但**合计行差了 4.69 个百分点**，而且是**反方向**（加权 < 简单平均）

**为什么**？

在**品类内部**，各行金额相近、毛利率也相近，所以两种算法差别不大。

但在**全库级别**，金额分布极度不均（数码单品均价 1,993.66，食品只有 219.84），高金额低毛利的数码权重被放大，于是加权平均被显著拉低。

> **这正是"辛普森悖论"的一个实例**：分组看一致，合并看反转。它提醒你 —— **永远不要默认"各组的平均"等于"整体的平均"。**

### 9.1 再用 SQL 对拍

```sql
SELECT ROUND(SUM(i.line_profit)/SUM(i.line_amount)*100,2) AS 加权毛利率,
       ROUND(AVG(i.line_profit/i.line_amount)*100,2) AS 各行简单平均,
       COUNT(*) AS 行数
FROM fact_order_item i
JOIN fact_order o ON i.order_id = o.order_id
WHERE o.status = '已完成';
-- 预期：23.72 | 28.41 | 5686
```

按品类：

```sql
SELECT p.category AS 品类,
       ROUND(SUM(i.line_profit)/SUM(i.line_amount)*100,2) AS 加权,
       ROUND(AVG(i.line_profit/i.line_amount)*100,2) AS 简单平均
FROM fact_order_item i
JOIN dim_product p ON i.product_id = p.product_id
JOIN fact_order o ON i.order_id = o.order_id
WHERE o.status = '已完成'
GROUP BY p.category
ORDER BY 加权;
```

## 十、FDE 现场场景

### 场景 1：业务方坚持"两种算法都可以"

**常见对话**：

> 业务方：「我不管你怎么算，给我一个数就行。」
> 你：「这两个数差 4.69 个百分点，按 719 万销售额算就是差 33.7 万毛利。得先定一个。」

**话术技巧**：把**百分比差异翻译成金额**，业务方立刻就有感觉了。4.69% 听着不大，33.7 万就很有分量。

**然后给建议**：

> "财务口径一般用加权（总利润÷总销售额），因为这样才能和总账对上。如果您系统里是各单平均，我们也可以做，但报表上要标注清楚。您看哪个？"

### 场景 2：客户的历史报表在用错误算法

这是最棘手的情况 —— 客户已经用简单平均做了三年报表，你现在告诉他错了。

**做法**：

1. **不要直接说"你们错了"**（会引发防御心理）
2. 拿出两种算法的数字，说明差异和原因
3. 给出建议：**新报表用加权**，同时**保留旧算法一个口径**做对比，让业务方平滑过渡
4. 把差异写进交付文档，让客户**自己决定**是否追溯修正历史数据

> **核心原则**：你的职责是**揭示差异并说明后果**，不是替业务方做决策。

### 场景 3：什么时候简单平均才是对的

| 场景 | 用哪个 | 理由 |
|---|---|---|
| 公司整体毛利率 | 加权 | 要和总账对上 |
| 「典型一笔订单的毛利率是多少」 | 简单平均 | 问的是"典型值"，不是"整体" |
| 「各品类的盈利水平排名」 | 加权 | 排名要反映真实贡献 |
| 「有多少比例的订单是亏损的」 | 计数，不是平均 | 完全不同的指标 |
| 客户满意度平均分 | 简单平均 | 每个客户权重相同（合理） |

**判断方法**：问自己"**每行的权重应该相同吗？**"

- 金额、数量相关的 → 权重应该不同 → 用加权
- 满意度、评分、天数 → 权重可以相同 → 用简单平均

## 十一、本章小结

| 你学到了 | 关键点 |
|---|---|
| 行上下文 | "现在是第几行"，来源：**计算列** + **迭代函数（X 函数、FILTER）** |
| 筛选上下文 | "现在看哪部分数据"，来源：行列/切片器/筛选器窗格/交叉筛选/`CALCULATE` |
| **聚合函数忽视行上下文** | `SUM` 在计算列里每行都等于全表总计 |
| **率的计算** | **必须 `SUM(分子)/SUM(分母)`**，不能对比率列求平均 |
| 本库证据 | 加权 **23.72%** vs 简单平均 **28.41%**，差 4.69（约 33.7 万毛利） |
| 差异根源 | 大额订单集中在低毛利数码（前三行均 1.2 万+，毛利率仅 6-7%） |
| 上下文转换 | 行上下文 → 筛选上下文；触发：计算列引用度量值、显式 `CALCULATE` |
| 辛普森悖论 | 分组看差 0.2-0.6，合并看差 4.69 且方向相反 |

## 十二、练习题

### 练习 1：解释两个毛利率的差值（考：加权 vs 简单平均）

**题目**：按省份看，两种算法的差值比按品类看**大得多**：

| 省份 | 加权毛利率 | 简单平均 | 差值 |
|---|---:|---:|---:|
| 四川 | 21.75% | 27.23% | -5.49 |
| 湖北 | 21.84% | 27.64% | -5.80 |
| 广东 | 22.05% | 27.07% | -5.02 |
| 辽宁 | 23.03% | 27.97% | -4.94 |
| 北京 | 23.72% | 27.08% | -3.36 |

**问题**：为什么按省份看，两个算法的差距（3-6 个百分点）比按品类看（0.2-0.6 个百分点）大这么多？

<details>
<summary>Hint</summary>
想想：同一个省份内部，订单的品类构成是不是混杂的？
</details>

**答案与解析**：

**因为分组的"同质性"不同。**

- **按品类分组**：同一品类内，各行毛利率非常接近（都是数码 ≈ 0-2%，或都是美妆 ≈ 48-50%）。组内差异小 → 加权和简单平均差别小（0.2-0.6）。
- **按省份分组**：同一个省内，数码、食品、家居、服饰、美妆**全都混在一起**，各行毛利率从 -14% 到 55% 都有。组内差异极大 → 大额低毛利的数码订单权重被放大，加权结果被显著拉低（3-6 个百分点）。

**一般规律**：

> **分组内数据越同质，两种算法越接近；分组内差异越大，两种算法差距越大。**

这也解释了为什么**全库级别差最多（4.69）** —— 全库是最"混杂"的分组。

**验证 SQL**：

```sql
SELECT r.province_name AS 省,
       ROUND(SUM(i.line_profit)/SUM(i.line_amount)*100,2) AS 加权,
       ROUND(AVG(i.line_profit/i.line_amount)*100,2) AS 简单平均
FROM fact_order_item i
JOIN fact_order o ON i.order_id=o.order_id
JOIN dim_region r ON o.region_id=r.region_id
WHERE o.status='已完成'
GROUP BY r.province_name
ORDER BY 加权 LIMIT 5;
```

### 练习 2：计算列里写 SUM 会怎样（考：行上下文 vs 聚合函数）

**题目**：在 `fact_order_item` 里新建计算列：

```dax
测试_全表求和 = SUM('fact_order_item'[line_amount])
```

看结果，并解释。然后改成这样，再看：

```dax
测试_上下文转换 = CALCULATE(SUM('fact_order_item'[line_amount]))
```

**答案与解析**：

| 版本 | 结果 | 原因 |
|---|---|---|
| `SUM(...)` | **每行都等于 10,689,545... 全表总计**（实际为 10,689,549.70） | `SUM` 只看筛选上下文，计算列里筛选上下文为空 → 汇总整张表 |
| `CALCULATE(SUM(...))` | **每行等于"当前行的 line_amount"** | `CALCULATE` 触发**上下文转换**，把当前行所有列变成筛选条件，筛选出"这一行" → 求和就是它自己 |

**预期结果**：

- 第一个计算列：所有 8,445 行都是 **10,689,549.70**
- 第二个计算列：每行是各自的 `line_amount`（如第 1 行 = 1,267.16）

**解析**（第二个为什么是它自己）：

`CALCULATE` 发生上下文转换时，会把当前行的**每一列**都变成筛选条件。而明细表有主键 `order_item_id`，所以筛选出"order_item_id = 当前行的值" → 只剩 1 行 → 求和就是那一行自己的 `line_amount`。

**延伸**：如果你用 `ALLEXCEPT` 保留部分列，就能得到"按某维度汇总"的效果：

```dax
-- 每行显示"该商品所属品类的总销售额"
品类销售额 = CALCULATE(SUM('fact_order_item'[line_amount]),
                       ALLEXCEPT('fact_order_item', 'fact_order_item'[product_id]))
```

### 练习 3：找出亏损订单（考：行上下文的实际应用）

**题目**：有效订单里有 489 行是亏损的（`line_profit < 0`）。建一个度量值数出亏损行数，并算出"亏损订单占总订单的比例"。

**答案与解析**：

```dax
亏损行数 =
CALCULATE(
    COUNTROWS('fact_order_item'),
    'fact_order'[status] = "已完成",
    'fact_order_item'[line_profit] < 0
)

亏损行占比 = DIVIDE([亏损行数], COUNTROWS('fact_order_item'))
```

**预期结果**：

| 指标 | 值 |
|---|---:|
| 亏损行数（有效） | **489** |
| 有效明细总行数 | 5,686 |
| 亏损行占比 | **8.60%** |

**解析**：这里 `CALCULATE` 有两个筛选条件，它们是"与"关系：

```
status = "已完成"  AND  line_profit < 0
```

注意 `line_profit < 0` 这种**布尔筛选**—— 它会被内部转成 `FILTER(ALL(line_profit), line_profit < 0)`（ch06 会讲这背后的机制）。

**延伸思考（业务价值）**：

489 行亏损单，最低毛利率 **-14.29%**。这些是怎么产生的？

看数据生成逻辑：**折扣率最高 20%（钻石客户）+ 3% 随机抖动**，而**数码品类吊牌毛利只有 12%**。

```
吊牌毛利 12% - 折扣 20% - 抖动 3% = -11%  →  负毛利！
```

**这就是一个真实的业务洞察**：给钻石客户的 20% 折扣，在数码品类上会**卖一单亏一单**。

> **FDE 视角**：这是你能给客户的最有价值的那类发现 —— 不是"你们毛利 23.72%"，而是"**你们的钻石客户折扣政策在数码品类上是亏损的**"。前者是数据，后者是洞察。

**验证 SQL**：

```sql
SELECT COUNT(*) AS 亏损行数,
       ROUND(COUNT(*)*100.0/(SELECT COUNT(*) FROM fact_order_item i2
             JOIN fact_order o2 ON i2.order_id=o2.order_id WHERE o2.status='已完成'),2) AS 占比
FROM fact_order_item i
JOIN fact_order o ON i.order_id=o.order_id
WHERE o.status='已完成' AND i.line_profit < 0;
-- 预期：489 | 8.60
```

### 练习 4：预测矩阵里的数字（考：筛选上下文叠加）

**题目**：报表上有这些设置：

- 切片器：年份 = 2024
- 筛选器窗格：status = 已完成
- 矩阵行：`dim_region[province_name]`
- 矩阵列：`dim_product[category]`
- 值：`[有效销售额]`

那么「广东 × 数码」这个格子，它的筛选上下文是什么？用 SQL 算出这个数字。

**答案与解析**：

**筛选上下文**（四个条件叠加）：

```
年 = 2024  AND  status = '已完成'  AND  省份 = '广东'  AND  品类 = '数码'
```

**SQL 验证**：

```sql
SELECT ROUND(SUM(i.line_amount),2) AS 销售额
FROM fact_order_item i
JOIN fact_order o ON i.order_id = o.order_id
JOIN dim_region r ON o.region_id = r.region_id
JOIN dim_product p ON i.product_id = p.product_id
WHERE YEAR(o.order_date) = 2024
  AND o.status = '已完成'
  AND r.province_name = '广东'
  AND p.category = '数码';
```

**要点**：这道题的考点不是数字本身（每次跑可能不同），而是理解**多条件叠加**。

**关键提醒**：矩阵的行和列**都**产生筛选上下文，而且**同时生效**。很多人以为只有"行"起作用，其实"列"也一样。

**常见错误**：如果 Power BI 里的数字和 SQL 不一致，检查：

1. 年份切片器用的是 `dim_date[year]` 还是 `fact_order[order_date]` 的年份？（应该一致）
2. 有没有漏掉 status 过滤？
3. 关系是否正确（`dim_product` → `fact_order_item`）

### 练习 5：为什么合计不等于各行之和（考：度量值的聚合行为）

**题目**：这是一个 Power BI 里让人抓狂的经典现象。

建一个度量值：

```dax
客户数 = DISTINCTCOUNT('fact_order'[customer_id])
```

拖进按省份的矩阵，得到：

| 省份 | 客户数 |
|---|---:|
| 广东 | 98 |
| 浙江 | 76 |
| … | … |
| **合计** | **？** |

**问题**：合计行的数字，等于上面各行相加吗？

<details>
<summary>Hint</summary>
想一个客户会不会在多个省下单？本库的数据局限是什么？
</details>

**答案与解析**：

**本库情况**：**等于各行之和**（因为每个客户只属于一个省，且本库无跨省下单 —— 见数据局限说明）。

**但真实场景：不等于。**

原因：`DISTINCTCOUNT` 是**去重计数**。如果一个客户在广东和浙江都下过单：

- 广东行：+1
- 浙江行：+1
- 各行之和：2
- **合计行：1**（去重后只有 1 个客户）

这就是著名的「**合计不等于明细之和**」问题。

**它不是 bug，是正确行为** —— 去重计数本来就不能简单相加。

**怎么处理**：

| 需求 | 做法 |
|---|---|
| 想让合计 = 各行之和 | 说明你要的不是去重计数，改用 `COUNTROWS` 数订单 |
| 就是想要去重，但要能解释 | 在报表上标注"客户数为去重统计，合计不等于分行之和" |
| 想强制合计 = 分行之和 | 用 `SUMX(VALUES(维度), [度量值])` 强制逐行相加（但要确认业务上合理） |

**验证（真实跨省场景的模拟）**：

```sql
-- 本库：客户数合计 = 各省之和（无跨省）
SELECT COUNT(DISTINCT customer_id) AS 全库客户数 FROM fact_order WHERE status='已完成';
-- 与各省去重计数之和比较
SELECT SUM(cnt) FROM (
  SELECT r.province_name, COUNT(DISTINCT o.customer_id) cnt
  FROM fact_order o JOIN dim_region r ON o.region_id=r.region_id
  WHERE o.status='已完成' GROUP BY r.province_name
) t;
-- 本库两个数字相等（因为无跨省下单）
```

> **FDE 视角**：业务方发现"合计对不上"时，通常会认为"你报表算错了"。这时你要能**立刻解释这是去重的正确行为**，并给出替代方案。**能解释清楚，才是专业性的体现。**
