# ch07 迭代函数与表函数 🔁

> 本章目标：掌握**逐行遍历**的能力（迭代函数）和**操作表**的能力（表函数）。
> 学完你就能做「TOP N」「排名」「各品类内的前三名」这类分析。

---

## 一、本章学习目标

学完本章你应该能：

1. 判断什么时候**必须**用迭代函数（聚合函数做不到时）
2. 熟练使用 `SUMX` / `AVERAGEX` / `COUNTX` / `MAXX`
3. 用 `RANKX` 做排名，并解释「为什么不加 `ALL` 全是 1」
4. 用 `TOPN` + `SUMMARIZE` 做 TOP N 分析
5. 用 `CONCATENATEX` 把多行文本合并到一个格子里
6. 知道迭代的**性能代价**，避免踩坑

## 二、为什么需要迭代函数

聚合函数（`SUM` / `AVERAGE` / `COUNT`）只能做一件事：**把一列压缩成一个值**。

但有些需求它做不到：

| 需求 | 聚合函数能做吗 | 为什么 |
|---|---|---|
| 销售额 = Σ（数量 × 单价 × (1-折扣)） | ❌ | 要先**逐行相乘**再求和 |
| 每个品类里销量前三的商品 | ❌ | 要先**按品类分组**，再组内排序 |
| 各省份销售额排名 | ❌ | 要**对所有省份排序** |
| 毛利率 > 40% 的商品有多少个 | ❌ | 要**逐行判断条件**再计数 |

这些需求的共同点：**需要先逐行处理，再聚合**。这就是迭代函数的用武之地。

### 2.1 迭代函数的标志：以 X 结尾

```
SUM     → SUMX      求和
AVERAGE → AVERAGEX  平均
MIN/MAX → MINX/MAXX 最小/最大
COUNT   → COUNTX    计数
```

**语法**：

```dax
SUMX(要遍历的表, 每行要计算的表达式)
```

### 2.2 第一个例子：手算销售额

```dax
-- 用 SUM：做不到（因为要先算 数量×单价×(1-折扣)）
-- 用 SUMX：
手算销售额 =
SUMX(
    'fact_order_item',
    'fact_order_item'[quantity] * 'fact_order_item'[unit_price] * (1 - 'fact_order_item'[discount_rate])
)
```

**执行过程**：

1. `SUMX` 遍历 `fact_order_item` 的 8,445 行
2. **逐行**创建行上下文，算 `quantity × unit_price × (1-discount_rate)`
3. 把 8,445 个结果加起来

**预期结果**：应该等于 `SUM(line_amount)` = **10,689,549.70**（含全部状态）

> **验证**：这正是数据字典里 `line_amount = quantity × unit_price × (1 - discount_rate)` 的公式。用 `SUMX` 手算一遍，能验证数据是否自洽。

## 三、迭代器家族

| 函数 | 作用 | 例子 |
|---|---|---|
| `SUMX(表, 表达式)` | 逐行算，再求和 | 手算销售额 |
| `AVERAGEX(表, 表达式)` | 逐行算，再平均 | 平均每单金额 |
| `MAXX(表, 表达式)` | 逐行算，取最大 | 最大单笔订单 |
| `MINX(表, 表达式)` | 逐行算，取最小 | 最小单笔订单 |
| `COUNTX(表, 表达式)` | 逐行算，数非空值 | 数有多少行满足条件 |

### 3.1 实战：最大单笔订单金额

```dax
最大单笔订单 =
MAXX(
    VALUES('fact_order'[order_id]),
    CALCULATE(SUM('fact_order'[order_amount]))
)
```

**解析**：

1. `VALUES('fact_order'[order_id])` 得到一个**订单号列表**（虚拟表）
2. `MAXX` 遍历每个订单号，逐行算该订单的金额
3. 取最大值

> 注意这里的 `CALCULATE` —— 它触发**上下文转换**（ch05），把"当前订单号"变成筛选条件。没有它，`SUM` 会返回全表总计。

### 3.2 实战：平均每单金额（正确写法）

```dax
-- 正确：逐单算金额，再平均
平均每单金额 =
AVERAGEX(
    FILTER(VALUES('fact_order'[order_id]), CALCULATE(SELECTEDVALUE('fact_order'[status])) = "已完成"),
    CALCULATE(SUM('fact_order'[order_amount]))
)
```

**但这写法太绕了。** 更简单的做法：

```dax
客单价 = DIVIDE([有效销售额], [有效订单数])   -- 预期 3,041.21
```

> **原则**：**能用简单度量值解决的，不要用迭代。** 迭代函数更灵活但更慢、更难读。
> 只有当你需要"逐行做不同的计算"时才用迭代。

## 四、表函数：操作"虚拟表"

迭代函数遍历表，那表从哪来？**表函数**用来生成和变换表。

| 函数 | 作用 | 返回 |
|---|---|---|
| `VALUES(列)` | 该列的**去重值**（含空白行） | 单列表 |
| `DISTINCT(列)` | 该列的去重值（不含空白行） | 单列表 |
| `FILTER(表, 条件)` | 按条件筛选行 | 表 |
| `ALL(表/列)` | 返回所有行（忽略筛选） | 表 |
| `SUMMARIZE(表, 分组列, "名称", 表达式)` | 分组聚合 | 表 |
| `ADDCOLUMNS(表, "列名", 表达式)` | 给表加列 | 表 |
| `TOPN(N, 表, 排序列, [顺序])` | 取前 N 行 | 表 |
| `SELECTCOLUMNS(表, "列名", 表达式)` | 只保留指定列 | 表 |

### 4.1 SUMMARIZE：DAX 里的 GROUP BY

```dax
品类汇总表 =
SUMMARIZE(
    'fact_order_item',
    'dim_product'[category],
    "销售额", [有效销售额],
    "利润", [有效利润]
)
```

等价于 SQL：

```sql
SELECT category, SUM(line_amount) AS 销售额, SUM(line_profit) AS 利润
FROM fact_order_item JOIN dim_product USING(product_id)
JOIN fact_order USING(order_id)
WHERE status='已完成'
GROUP BY category;
```

**预期结果**：

| 品类 | 销售额 | 利润 |
|---|---:|---:|
| 数码 | 2,612,383.09 | 30,291.28 |
| 家居 | 1,408,258.89 | 383,334.76 |
| 美妆 | 1,381,720.47 | 683,559.33 |
| 服饰 | 1,351,789.04 | 513,684.38 |
| 食品 | 441,341.24 | 95,995.03 |

> **SUMMARIZE 通常不直接放进报表**，而是作为 `TOPN` / `RANKX` / `ADDCOLUMNS` 的**中间表**使用。

### 4.2 ADDCOLUMNS：给表加计算列

```dax
带毛利率的品类表 =
ADDCOLUMNS(
    VALUES('dim_product'[category]),
    "销售额", [有效销售额],
    "毛利率", [毛利率]
)
```

`ADDCOLUMNS` 会遍历第一参数的表（创建行上下文），然后逐行计算后面的表达式。

## 五、RANKX：排名（本章重点）

### 5.1 语法

```dax
RANKX(要排名的表, 每行的排名依据, [值], [顺序], [并列方式])
```

| 参数 | 说明 |
|---|---|
| 表 | 在哪些行之间排名（**关键参数**） |
| 表达式 | 每行的排名依据（通常是度量值） |
| 值 | 可选，一般省略 |
| 顺序 | `DESC`（大的是第1，默认）或 `ASC` |
| 并列方式 | `DENSE`（密集排名，1-2-2-3）或 `SKIP`（跳跃排名，1-2-2-4，默认） |

### 5.2 正确写法

```dax
省份销售排名 =
RANKX(
    ALL('dim_region'[province_name]),   -- 在所有省份之间排名
    [有效销售额],                        -- 按有效销售额
    ,
    DESC,
    DENSE
)
```

**预期结果**：

| 省份 | 有效销售额 | 排名 |
|---|---:|---:|
| 广东 | 1,078,152.70 | 1 |
| 浙江 | 849,660.63 | 2 |
| 上海 | 816,614.17 | 3 |
| 江苏 | 800,322.96 | 4 |
| 北京 | 761,942.54 | 5 |
| 湖北 | 700,373.18 | 6 |
| 山东 | 672,082.30 | 7 |
| 四川 | 562,613.26 | 8 |
| 辽宁 | 517,676.34 | 9 |
| 陕西 | 436,054.65 | 10 |

### 5.3 头号错误：忘记 ALL，结果全是 1

```dax
-- 错误写法
错误排名 = RANKX('dim_region', [有效销售额])
```

**现象：每一行排名都是 1。**

**原因（非常关键，务必理解）**：

1. `RANKX` 遍历第一参数的表，为每行创建行上下文
2. 计算 `[有效销售额]` 时，由于引用了**度量值**，会发生**上下文转换**（ch05）
3. 上下文转换把当前行的所有列变成筛选条件
4. 于是每行的筛选上下文是"省份 = 当前行省份"
5. 每行只跟自己比 → **永远是第 1 名**

```
广东行：筛选"广东" → 销售额 1,078,152.70 → 在 {广东} 里排第 1
浙江行：筛选"浙江" → 销售额   849,660.63 → 在 {浙江} 里排第 1
```

**解决**：第一参数用 `ALL(...)` 或 `ALLSELECTED(...)`，让排名范围包含**所有**候选行。

| 第一参数写法 | 排名范围 | 用途 |
|---|---|---|
| `ALL('dim_region'[province_name])` | 所有省份 | 全国排名 |
| `ALLSELECTED('dim_region'[province_name])` | 当前切片器选中的省份 | 所选范围内排名 |
| `VALUES('dim_region'[province_name])` | 当前可见的省份 | 跟随筛选 |
| `'dim_region'`（整表） | 表中所有行 | 通常不这么用 |

> ⚠️ **记忆口诀**：**RANKX 的第一参数决定"跟谁比"，忘记 ALL 就是跟自己比。**

### 5.4 分组内排名：`PARTITION BY` 的 DAX 实现

SQL 里 `ROW_NUMBER() OVER (PARTITION BY category ORDER BY ...)` 的 DAX 等价写法：

```dax
品类内商品排名 =
RANKX(
    ALLEXCEPT('fact_order_item', 'dim_product'[category]),  -- 在"同一品类内"的商品之间排
    [有效销售额],
    ,
    DESC,
    DENSE
)
```

用 `ALLEXCEPT` 保留品类筛选、清除商品筛选 → 排名范围 = 当前品类内的所有商品。

## 六、TOPN：取前 N 名

### 6.1 语法

```dax
TOPN(N, 表, 排序依据, [顺序])
```

### 6.2 实战：TOP 10 客户

```dax
TOP10客户 =
TOPN(
    10,
    SUMMARIZE(
        'fact_order',
        'dim_customer'[customer_name],
        'dim_customer'[tier],
        "销售额", [有效销售额],
        "订单数", [有效订单数]
    ),
    [有效销售额],
    DESC
)
```

**预期结果**：

| 客户 | 等级 | 销售额 | 排名 |
|---|---|---:|---:|
| 梁诗 | 钻石 | 70,022.89 | 1 |
| 唐宇伟 | 钻石 | 67,890.55 | 2 |
| 马晨博 | 钻石 | 66,012.90 | 3 |
| 吴涛 | 钻石 | 65,767.42 | 4 |
| 彭艳鑫 | 钻石 | 61,699.01 | 5 |
| 王浩娜 | 钻石 | 59,117.77 | 6 |
| 郑娟 | 钻石 | 58,829.93 | 7 |
| 郭晨桂 | 钻石 | 54,739.69 | 8 |
| 黄桂 | 钻石 | 54,715.65 | 9 |
| 何静文 | 钻石 | 51,408.67 | 10 |

**重要发现：TOP 10 客户全是钻石客户！**

这印证了数据设计（钻石客户订单数是普通客户的 6 倍多），也是一个真实的业务洞察：**高价值客户贡献了绝大部分头部销售额**。

**验证 SQL**：

```sql
SELECT d.customer_name AS 客户, d.tier AS 等级,
       ROUND(SUM(o.order_amount),2) AS 销售额,
       RANK() OVER (ORDER BY SUM(o.order_amount) DESC) AS 排名
FROM fact_order o JOIN dim_customer d ON o.customer_id=d.customer_id
WHERE o.status='已完成'
GROUP BY d.customer_id, d.customer_name, d.tier
ORDER BY 销售额 DESC LIMIT 10;
```

### 6.3 TOPN 用来做筛选（更常见用法）

`TOPN` 返回的**表**可以直接塞进 `CALCULATE`：

```dax
TOP10客户销售额 =
CALCULATE(
    [有效销售额],
    TOPN(10, ALL('dim_customer'[customer_name]), [有效销售额], DESC)
)
```

这个度量值算出"销售额最高的 10 个客户贡献了多少"。

### 6.4 用表格视觉对象展示 TOPN

1. 拖一个**表**到画布
2. 行：`dim_customer[customer_name]`
3. 值：`[有效销售额]`
4. 「筛选器」面板 → 该视觉对象的筛选器 → 选「customer_name」→ 筛选类型选 **前 N 个** → 按 `[有效销售额]` 输入 10

> **这比写 TOPN 度量值更简单**，Power BI 内置了这个功能。**能用内置功能就别写代码。**

## 七、CONCATENATEX：把多行文本合并成一行

一个很实用、很多人不知道的函数。

**需求**：在一个格子里显示"该品类销售额前三的商品名"。

```dax
品类TOP3商品 =
CONCATENATEX(
    TOPN(
        3,
        VALUES('dim_product'[product_name]),
        [有效销售额],
        DESC
    ),
    'dim_product'[product_name],
    "、"
)
```

**预期结果**：

| 品类 | TOP3 商品（按销售额） |
|---|---|
| 数码 | 极光智能手表、云米无线蓝牙耳机、极光电竞鼠标 |
| 家居 | 木语陶瓷餐具、木语收纳箱、简一记忆棉枕 |
| 美妆 | 琉光丝绒口红、花漾保湿面霜、琉光气垫BB |
| 服饰 | 素白纯棉T恤、素白牛仔裤、素白牛仔裤 |
| 食品 | 鲜踪挂耳咖啡、鲜踪椴树蜂蜜、鲜踪手工饼干 |

**注意服饰那一行出现了两次"素白牛仔裤"** —— 这不是 bug，是数据特性：

> **数据提醒**：本库 `product_name` **不唯一**（商品名 = 品牌 + 品类词随机组合，200 个商品里会有重名）。
> 严格做 TOP N 时应该用 `product_id` 分组。这个现象本身是个好的教学案例 —— 它提醒你**永远先确认"用来分组的列是否唯一"**。

### 7.1 带排名的写法

```dax
品类TOP3商品_带排名 =
CONCATENATEX(
    TOPN(3, VALUES('dim_product'[product_id]), [有效销售额], DESC),
    'dim_product'[product_name] & "(" & FORMAT([有效销售额], "#,##0") & ")",
    "、" & UNICHAR(10)   -- 换行分隔
)
```

## 八、性能：迭代的代价

迭代函数很强大，但有代价。

### 8.1 代价一：逐行计算

```dax
-- 慢：遍历 8,445 行，每行算一次乘法
手算销售额 = SUMX('fact_order_item', [quantity] * [unit_price] * (1-[discount_rate]))

-- 快：存储引擎直接扫描一列
直接求和 = SUM('fact_order_item'[line_amount])
```

两者结果相同，但前者慢得多（本库数据量小，感觉不出来；千万行时差距是秒级 vs 分钟级）。

> **原则**：**能用 `SUM(列)` 就不要用 `SUMX(表, 表达式)`。**

### 8.2 代价二：迭代里套 CALCULATE（上下文转换）

```dax
-- 很慢：8,445 行 × 每行一次上下文转换
慢 = SUMX('fact_order_item', CALCULATE(SUM('fact_order_item'[line_amount])))
```

每行都触发一次上下文转换 + 一次查询。**这是最常见的性能杀手之一。**

### 8.3 代价三：FILTER 整张事实表

```dax
-- 慢：遍历 8,445 行判断条件
慢 = CALCULATE([有效销售额], FILTER('fact_order_item', 'fact_order_item'[line_amount] > 1000))

-- 快：布尔筛选（内部优化）
快 = CALCULATE([有效销售额], 'fact_order_item'[line_amount] > 1000)
```

> **规则**：`FILTER` 的**第一参数尽量放维度表**（行数少），不要放事实表。
> ch10 会用 DAX Studio 实测这些差异。

## 九、FDE 现场场景

### 场景 1：客户要"各区域 TOP 10 商品"

**朴素做法**：写个 TOPN 度量值，但只能显示全局 TOP 10。

**客户真实需求**：**每个区域各自的前 10 名**（华东 10 个 + 华南 10 个...）。

**做法**：

| 方案 | 实现 | 优劣 |
|---|---|---|
| 方案 A：矩阵 + 前 N 筛选 | 矩阵行放「区域 + 商品」，值放销售额，筛选器设"每个区域显示前 10" | ⭐ 简单，但 Power BI 的"前 N"是**全局**的，不是分组的 |
| 方案 B：RANKX + 筛选 | 建 `区域内排名` 度量值，然后在视觉对象筛选器里设 `排名 <= 10` | ⭐⭐⭐ 正确做法 |
| 方案 C：DAX 表 | 用 `GENERATE` + `TOPN` 生成完整表 | 复杂，灵活性最高 |

**推荐方案 B**：

```dax
区域内商品排名 =
RANKX(
    ALLEXCEPT('fact_order_item', 'dim_region'[province_name]),
    [有效销售额],
    ,
    DESC,
    DENSE
)
```

然后在视觉对象的筛选器里设：`区域内商品排名 <= 10`。

### 场景 2：客户要"去年同期 TOP 10 客户"做对比

这是**双重难度**：时间智能 + TOPN。

**关键问题**：TOP 10 是按今年排的，还是按去年排的？

```dax
-- 按去年销售额选出的 TOP10，再看他们今年的表现
去年TOP10客户今年销售额 =
CALCULATE(
    [有效销售额],
    TOPN(10, ALL('dim_customer'[customer_name]), CALCULATE([有效销售额], SAMEPERIODLASTYEAR('dim_date'[date_key])), DESC)
)
```

> **FDE 视角**：这类需求一定要**先确认排名基准**（"TOP 10"是按哪个时期排的）。
> 客户往往自己也没想清楚，你一问，他们会觉得你专业。

### 场景 3：报表上标题要显示"当前筛选的省份"

用 `CONCATENATEX` + `VALUES`：

```dax
当前筛选省份 =
IF(
    ISFILTERED('dim_region'[province_name]),
    "当前筛选：" & CONCATENATEX(VALUES('dim_region'[province_name]), 'dim_region'[province_name], "、"),
    "全部省份"
)
```

把这个度量值放进**卡片**或**文本框标题**，报表就能动态显示筛选状态 —— 用户截图发给别人时，一眼能看出数据范围。

> **这是提升报表专业度的小技巧**，成本极低但很显眼。

## 十、本章小结

| 你学到了 | 关键点 |
|---|---|
| 何时用迭代 | 需要**逐行处理再聚合**时（先乘后加、分组内排序） |
| X 函数 | `SUMX`/`AVERAGEX`/`MAXX`/`COUNTX`，语法 `X(表, 表达式)` |
| 表函数 | `VALUES`/`FILTER`/`SUMMARIZE`/`ADDCOLUMNS`/`TOPN` |
| **RANKX** | 第一参数决定**跟谁比**；**忘记 `ALL` 全是 1**（上下文转换导致） |
| RANKX 分组排名 | 用 `ALLEXCEPT` 实现 SQL 的 `PARTITION BY` |
| TOPN | 可返回表，也可直接塞进 `CALCULATE` 做筛选 |
| CONCATENATEX | 多行文本合并到一格；注意本库 `product_name` **不唯一** |
| 性能 | 能用 `SUM` 别用 `SUMX`；`FILTER` 第一参数放维度表 |
| 实战数据 | 省份排名 广东1…陕西10；**TOP10 客户全是钻石等级** |

## 十一、练习题

### 练习 1：RANKX 忘记 ALL 会怎样（考：排名范围，必做）

**题目**：建两个度量值，拖进按省份的矩阵，观察差异：

```dax
排名_错误 = RANKX('dim_region', [有效销售额])

排名_正确 = RANKX(ALL('dim_region'[province_name]), [有效销售额], , DESC, DENSE)
```

**预期结果**：

| 省份 | 有效销售额 | 排名_错误 | 排名_正确 |
|---|---:|---:|---:|
| 广东 | 1,078,152.70 | **1** | 1 |
| 浙江 | 849,660.63 | **1** | 2 |
| 上海 | 816,614.17 | **1** | 3 |
| … | … | **全部是 1** | 依次递增 |

**解析**（三步理解）：

1. `RANKX('dim_region', ...)` 直接传**整张表** → 遍历 `dim_region` 的每一行，每行创建行上下文
2. 计算 `[有效销售额]`（这是个**度量值**）→ 触发**上下文转换** → 当前行的所有列（包括 `province_name`）变成筛选条件
3. 于是"广东"这一行，排名范围是**只包含广东的集合** → 广东在自己里面当然排第 1

**关键认知**：

> `RANKX` 第一参数如果是**原始表**，会因为上下文转换导致"每行只跟自己比"。
> 必须用 `ALL(列)` 或 `ALLSELECTED(列)` 构造一个**不受当前行影响的候选集合**。

**修正后的预期**：广东 1、浙江 2、上海 3、江苏 4、北京 5、湖北 6、山东 7、四川 8、辽宁 9、陕西 10。

### 练习 2：各品类内销量 TOP3（考：分组内排名）

**题目**：找出每个品类里**销量**（quantity 之和）前三的商品。

<details>
<summary>Hint</summary>
先用 SQL 想清楚：ROW_NUMBER() OVER (PARTITION BY category ORDER BY SUM(quantity) DESC)。
DAX 里用 RANKX + ALLEXCEPT。
</details>

**答案与解析**：

**SQL 版**（先跑出基准）：

```sql
SELECT 品类, 商品, 销量 FROM (
  SELECT p.category AS 品类, p.product_name AS 商品, SUM(i.quantity) AS 销量,
         ROW_NUMBER() OVER (PARTITION BY p.category ORDER BY SUM(i.quantity) DESC) AS rn
  FROM fact_order_item i
  JOIN dim_product p ON i.product_id=p.product_id
  JOIN fact_order o ON i.order_id=o.order_id
  WHERE o.status='已完成'
  GROUP BY p.category, p.product_id, p.product_name
) t WHERE rn <= 3 ORDER BY 品类, rn;
```

**DAX 版**：

```dax
品类内销量排名 =
RANKX(
    ALLEXCEPT('fact_order_item', 'dim_product'[category]),
    [有效销量],
    ,
    DESC,
    DENSE
)
```

然后在表格视觉对象里：行 = `category` + `product_name`，值 = `[有效销量]` + `[品类内销量排名]`，筛选器设 `排名 <= 3`。

**预期结果**：

| 品类 | 商品 | 销量 |
|---|---|---:|
| 家居 | 暖居加湿器 | 85 |
| 家居 | 木语羊毛毯 | 60 |
| 家居 | 木语陶瓷餐具 | 58 |
| 数码 | 星河蓝牙音箱 | 61 |
| 数码 | 极光智能手表 | 51 |
| 数码 | 极光蓝牙音箱 | 51 |
| 服饰 | 素白牛仔裤 | 60 |
| 服饰 | 素白纯棉T恤 | 54 |
| 服饰 | 素白羽绒服 | 52 |
| 美妆 | 肌研丝绒口红 | 66 |
| 美妆 | 花漾防晒乳 | 63 |
| 美妆 | 琉光补水面膜 | 57 |
| 食品 | 鲜踪果干混合 | 78 |
| 食品 | 鲜踪黑巧克力 | 77 |
| 食品 | 田园挂耳咖啡 | 77 |

**解析**：`ALLEXCEPT('fact_order_item', 'dim_product'[category])` 的含义是"清除 `fact_order_item` 上所有筛选，**但保留品类的筛选**" —— 于是排名范围 = 当前品类内的所有商品，实现了 SQL 的 `PARTITION BY category`。

### 练习 3：用 SUMX 重写销售额，并比较性能（考：迭代代价）

**题目**：建两个度量值，结果应该相同：

```dax
销售额_直接 = SUM('fact_order_item'[line_amount])

销售额_SUMX = SUMX('fact_order_item',
                   'fact_order_item'[quantity] * 'fact_order_item'[unit_price]
                   * (1 - 'fact_order_item'[discount_rate]))
```

**问题**：两者结果相同吗？哪个更快？为什么？

**答案与解析**：

**结果：相同，都等于 10,689,549.70**（未过滤状态）。

**性能：`销售额_直接` 快得多。**

| | `SUM(列)` | `SUMX(表, 表达式)` |
|---|---|---|
| 执行层 | **存储引擎**（VertiPaq，列式压缩、多核并行） | **公式引擎**（逐行计算，单线程为主） |
| 扫描方式 | 直接扫一列 | 遍历每行，取多列，算表达式 |
| 大数据表现 | 快 | 慢（可能慢 10-100 倍） |

**结论**：

> 本例中 `SUMX` 手算**只是为了验证数据公式自洽**（证明 `line_amount = qty × price × (1-disc)`），**实际建模不要这么写**。

**什么时候必须用 SUMX**：

- 表里没有现成的金额列（只有数量、单价，要现场乘）
- 需要逐行做条件判断（`IF` 分支）
- 需要跨表逐行计算

**验证 SQL**（手算一遍核对）：

```sql
SELECT ROUND(SUM(quantity*unit_price*(1-discount_rate)),2) AS 手算销售额,
       ROUND(SUM(line_amount),2) AS 直接求和
FROM fact_order_item;
-- 预期两者相等：10689549.70
```

### 练习 4：CONCATENATEX 显示 TOP3 商品（考：表函数实战）

**题目**：建一个度量值，在每个品类的格子里显示"销售额前三的商品名"。

```dax
品类TOP3商品 =
CONCATENATEX(
    TOPN(3, VALUES('dim_product'[product_name]), [有效销售额], DESC),
    'dim_product'[product_name],
    "、"
)
```

**预期结果**：

| 品类 | TOP3 商品 |
|---|---|
| 数码 | 极光智能手表、云米无线蓝牙耳机、极光电竞鼠标 |
| 家居 | 木语陶瓷餐具、木语收纳箱、简一记忆棉枕 |
| 美妆 | 琉光丝绒口红、花漾保湿面霜、琉光气垫BB |
| 服饰 | 素白纯棉T恤、素白牛仔裤、素白牛仔裤 |
| 食品 | 鲜踪挂耳咖啡、鲜踪椴树蜂蜜、鲜踪手工饼干 |

**解析**：

1. `VALUES('dim_product'[product_name])` 得到当前筛选下的商品名列表
2. `TOPN(3, ..., [有效销售额], DESC)` 取销售额前三
3. `CONCATENATEX` 遍历这 3 行，把商品名用"、"连起来

**注意服饰品类的重复项**：出现两次"素白牛仔裤"。

**这是数据特性不是 bug** —— `product_name` 由「品牌 + 品类词」随机组合生成，200 个商品里存在重名（不同 `product_id` 同名）。

**给你的提醒**：

> 真实项目里做 TOP N 前，**先确认用来分组的列是否唯一**。如果不唯一，要用 ID 分组、用名称显示：
>
> ```dax
> CONCATENATEX(
>     TOPN(3, VALUES('dim_product'[product_id]), [有效销售额], DESC),
>     'dim_product'[product_name], "、"
> )
> ```

**验证 SQL**：

```sql
SELECT 品类, 商品, 销售额 FROM (
  SELECT p.category AS 品类, p.product_name AS 商品,
         ROUND(SUM(i.line_amount),2) AS 销售额,
         ROW_NUMBER() OVER (PARTITION BY p.category ORDER BY SUM(i.line_amount) DESC) AS rn
  FROM fact_order_item i
  JOIN dim_product p ON i.product_id=p.product_id
  JOIN fact_order o ON i.order_id=o.order_id
  WHERE o.status='已完成'
  GROUP BY p.category, p.product_id, p.product_name
) t WHERE rn<=3 ORDER BY 品类, rn;
```

### 练习 5：数一数高毛利商品（考：COUNTX + FILTER）

**题目**：按品类统计「吊牌毛利率 > 40%」的商品有多少个。

<details>
<summary>Hint</summary>
商品维度行数是 200，在维度表上迭代很便宜。
</details>

**答案与解析**：

```dax
高毛利商品数 =
COUNTROWS(
    FILTER(
        'dim_product',
        DIVIDE('dim_product'[list_price] - 'dim_product'[cost_price], 'dim_product'[list_price]) > 0.40
    )
)
```

或用 `COUNTX`：

```dax
高毛利商品数_COUNTX =
COUNTX(
    FILTER('dim_product',
           DIVIDE('dim_product'[list_price] - 'dim_product'[cost_price], 'dim_product'[list_price]) > 0.40),
    'dim_product'[product_id]
)
```

**预期结果**：

| 品类 | 商品总数 | 高毛利商品数（吊牌>40%） |
|---|---:|---:|
| 美妆 | 50 | **50** |
| 服饰 | 34 | **34** |
| 家居 | 39 | **0** |
| 数码 | 38 | **0** |
| 食品 | 39 | **0** |

**解析**：

结果很"整齐" —— 因为数据生成时，**每个品类的吊牌毛利率是固定值**（美妆 55%、服饰 45%、家居 35%、数码 12%、食品 30%），所以只有美妆和服饰两个品类全部商品都超过 40%。

**这正是 ch03 讲的"吊牌口径"** —— 注意这是**商品的定价属性**，不是实际成交毛利率。实际成交后（含折扣），美妆只有 49.47%、服饰 38.00%。

**所以这个指标的业务含义是**：

> "我们有多少商品的**定价策略**是高毛利的？" —— 而不是"我们赚了多少"。

**性能提示**：这里 `FILTER` 的第一参数是 `dim_product`（200 行），非常快。**如果换成 `fact_order_item`（8,445 行）就会慢很多**，因为要逐行判断。

**验证 SQL**：

```sql
SELECT category AS 品类,
       COUNT(*) AS 商品总数,
       SUM(CASE WHEN (list_price-cost_price)/list_price > 0.40 THEN 1 ELSE 0 END) AS 高毛利商品数
FROM dim_product GROUP BY category ORDER BY 高毛利商品数 DESC;
```
