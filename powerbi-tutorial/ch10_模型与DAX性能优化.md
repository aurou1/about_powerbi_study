## 二、VertiPaq：Power BI 为什么这么快

Power BI 的数据引擎叫 **VertiPaq**（也叫 xVelocity / 内存中分析引擎）。它快的核心原因是**列式存储 + 字典压缩**。

### 2.1 行式 vs 列式

传统数据库（MySQL）是**行式存储**：

```
第1行: [1, 104, 1, 1267.16, 696.94, 0.00, 1267.16, 570.22]
第2行: [2, 68,  1, 312.51,  140.63, 0.03, 303.13,  162.50]
```

VertiPaq 是**列式存储**：

```
order_item_id 列: [1, 2, 3, ...]
product_id 列:    [104, 68, 140, ...]
quantity 列:      [1, 1, 1, ...]
line_amount 列:   [1267.16, 312.51, 427.84, ...]
```

**好处**：算 `SUM(line_amount)` 时，只需读一列，不用把整行都读出来。

### 2.2 字典压缩（关键）

每列会被建立**字典**，用短整数代替原始值：

```
原始 quantity 列: [1, 1, 2, 1, 3, 1, 2, ...]   (8445 个值)
字典: {1 → 0, 2 → 1, 3 → 2}                    (只有 3 个不同值)
存储: [0, 0, 1, 0, 2, 0, 1, ...]               (每个只占 2 bit)
```

**列中不同值越少（基数越低），压缩率越高，占内存越少，算得越快。**

### 2.3 看本库的真实基数

| 列 | 不同值个数 | 总行数 | 唯一值占比 | 压缩效果 |
|---|---:|---:|---:|---|
| `fact_order_item[quantity]` | **4** | 8,445 | **0.0%** | ⭐⭐⭐⭐⭐ 极好 |
| `fact_order_item[discount_rate]` | **24** | 8,445 | 0.3% | ⭐⭐⭐⭐⭐ 极好 |
| `dim_product[category]` | **5** | 200 | 2.5% | ⭐⭐⭐⭐⭐ 极好 |
| `dim_customer[tier]` | **4** | 500 | 0.8% | ⭐⭐⭐⭐⭐ 极好 |
| `fact_order[status]` | **3** | 3,529 | 0.1% | ⭐⭐⭐⭐⭐ 极好 |
| `fact_order[order_date]` | 1,018 | 3,529 | 28.8% | ⭐⭐⭐ 中等 |
| `dim_product[product_name]` | 102 | 200 | 51.0% | ⭐⭐ 一般 |
| `dim_customer[customer_name]` | 477 | 500 | 95.4% | ⭐ 差 |
| `fact_order_item[line_amount]` | **5,635** | 8,445 | **66.7%** | ⭐ 差 |
| `fact_order[order_id]` | 3,529 | 3,529 | 100% | ❌ 无法压缩 |

**结论一目了然**：

- `quantity`（4 个值）压缩率极高 → 分组、求和都飞快
- `line_amount`（66.7% 唯一值）几乎压不动 → 占内存大头
- `order_id`（100% 唯一）完全无法压缩 → **但正因为如此，`DISTINCTCOUNT(order_id)` 很贵**

> **优化启示**：
> 1. **金额类列尽量降低精度**（如果业务允许，去掉小数位能大幅减少唯一值）
> 2. **高基数列少做 DISTINCTCOUNT**
> 3. **能删的高基数列就删**（比如精确到秒的时间戳列）

## 三、四类计算该放哪一层？

同一个计算，可以在四个地方做。**放错层，性能差十倍。**

| 层级 | 什么时候算 | 优点 | 缺点 | 适合 |
|---|---|---|---|---|
| **SQL（源库）** | 查询时，数据库算 | 数据库有索引和并行；**不进模型** | 不随筛选变化 | 固定的、可预聚合的逻辑 |
| **Power Query** | 刷新时 | 一次算好，可折叠则数据库执行 | 占内存 | 清洗、拆列、合并、加固定标签 |
| **计算列** | 刷新时 | 每行一个值，可做分组轴 | **占内存、不随筛选变** | 分组标签（尽量少用） |
| **度量值** | 查询时 | 不占内存、随筛选变 | 每次交互都要算 | **所有聚合指标** |

### 3.1 决策顺序

```
能下推到 SQL 吗？（折叠能生效吗？）
  ├─ 能 → 放 SQL / Power Query 折叠步骤
  └─ 不能 → 值是否"每行固定不变"？
        ├─ 是（分组标签）→ 计算列 或 Power Query
        └─ 否（聚合指标）→ 度量值 ⭐ 绝大多数情况
```

### 3.2 典型误用

| ❌ 错误做法 | 问题 | ✅ 正确做法 |
|---|---|---|
| 加计算列 `行毛利率`，再 `AVERAGE` | 占内存 + 算法错误（ch05） | 度量值 `DIVIDE(SUM(利润), SUM(金额))` |
| 加计算列 `年份 = YEAR(order_date)` | 占内存（其实日期表已有 `year`） | 直接用 `dim_date[year]` |
| 在 Power Query 里做复杂聚合 | 刷新慢，且断折叠 | 让度量值在查询时算 |
| 度量值里 `FILTER(整张事实表, ...)` | 查询时逐行扫描 | 布尔筛选，或 `FILTER(维度表)` |

> **本库的正确做法**：`有效销售额` 用度量值（ch04），不加计算列。ch05 里那个 `行毛利率` 计算列**只是为了教学演示**，真实模型里应该删掉。

## 四、四类 DAX 性能杀手

### 4.1 杀手一：`FILTER(整张事实表, ...)`

```dax
-- ❌ 慢：遍历 8,445 行判断条件
大额订单数_慢 =
CALCULATE([有效订单数], FILTER('fact_order_item', 'fact_order_item'[line_amount] > 1000))

-- ✅ 快：布尔筛选（存储引擎优化）
大额订单数_快 =
CALCULATE([有效订单数], 'fact_order_item'[line_amount] > 1000)
```

**为什么快**：布尔筛选被翻译成对 `line_amount` 列的**一次范围扫描**（VertiPaq 有排序索引），不需要逐行判断。

> **规则**：`FILTER` 的第一参数**尽量放维度表**（行数少）。本库维度表最多 1,096 行，事实表 8,445 行 —— 差 8 倍。真实项目里可能差 1000 倍。

### 4.2 杀手二：迭代函数里套 CALCULATE

```dax
-- ❌ 很慢：8,445 行 × 每行一次上下文转换 + 一次查询
慢 = SUMX('fact_order_item', CALCULATE(SUM('fact_order_item'[line_amount])))

-- ✅ 快：直接聚合
快 = SUM('fact_order_item'[line_amount])
```

**为什么慢**：`CALCULATE` 在迭代里会为**每一行**触发一次上下文转换，等于发 8,445 次查询。

### 4.3 杀手三：高基数的 DISTINCTCOUNT

```dax
客户数 = DISTINCTCOUNT('fact_order'[customer_id])    -- 基数 500，还好
订单数 = DISTINCTCOUNT('fact_order'[order_id])       -- 基数 3,529，较贵
明细数 = COUNTROWS('fact_order_item')                -- 不去重，很快
```

**开销对比**：

| 写法 | 引擎做什么 | 相对开销 |
|---|---|---|
| `COUNTROWS(表)` | 直接读行数 | 1x（最快） |
| `COUNT(列)` | 扫一列，数非空 | 2x |
| `DISTINCTCOUNT(低基数列)` | 扫列 + 去重（字典已有序） | 3x |
| `DISTINCTCOUNT(高基数列)` | 扫列 + 建哈希表去重 | 10x+ |

> **优化**：如果一列是**表的主键且每行唯一**，用 `COUNTROWS` 替代 `DISTINCTCOUNT`。
> 本库 `fact_order` 一行一单，`order_id` 唯一 → `COUNTROWS('fact_order')` 比 `DISTINCTCOUNT([order_id])` 快。

### 4.4 杀手四：双向关系导致的额外计算

ch02 讲过：双向筛选让每次查询都要多算一遍反向传播，还可能产生扇出错误。

**检查方法**：模型视图里数双向箭头（线两端都有箭头）的数量。**正常模型应该是 0 个。**

## 五、用 DAX Studio 定位慢查询

### 5.1 是什么

**DAX Studio** 是免费的第三方工具（SQLBI 出品），能：

- 跑 DAX 查询并查看**执行时间**
- 看 **Server Timings**（服务器计时）：拆出 SE 时间和 FE 时间
- 看**物化行数**（中间结果有多大）
- 导出完整的查询计划

> 下载地址：<https://daxstudio.org/>（免费）

### 5.2 两个核心指标：SE 与 FE

一次 DAX 查询的时间分成两部分：

| | SE（Storage Engine，存储引擎） | FE（Formula Engine，公式引擎） |
|---|---|---|
| 谁在算 | VertiPaq（列式、多核并行、快） | 公式引擎（单线程为主、慢） |
| 什么时候 | `SUM`、`CALCULATE` 的简单筛选等 | 复杂迭代、上下文转换、逐行逻辑 |
| 占比健康值 | **> 90%** | **< 10%** |
| 慢的表现 | 数据量大、扫描行数多 | **FE 占比高 = DAX 写得差** |

**诊断口诀**：

> **SE 时间长** → 数据模型问题（数据量大、基数高、列太多）
> **FE 时间长** → DAX 写法问题（迭代、上下文转换、复杂逻辑）

### 5.3 怎么看（操作步骤）

1. 打开 DAX Studio，连接到你的 Power BI 文件（它会自动检测打开的 .pbix）
2. 粘贴一个查询：

```dax
EVALUATE
SUMMARIZECOLUMNS(
    'dim_region'[province_name],
    "有效销售额", [有效销售额],
    "毛利率", [毛利率]
)
```

3. 勾选顶部工具栏的 **Server Timings** 和 **Query Plan**
4. 点 **Run**
5. 在 Server Timings 面板看：

| 要看的列 | 含义 | 健康标准 |
|---|---|---|
| **Duration** | 总耗时 | 越小越好 |
| **SE Duration** | 存储引擎耗时 | 占比应 > 90% |
| **FE Duration** | 公式引擎耗时 | 占比应 < 10% |
| **SE Queries** | SE 查询次数 | **越少越好** |
| **SE Cache** | 缓存命中 | — |
| **Rows** | 返回行数 | — |
| **KB** | 结果大小 | — |

**关键警告信号**：

| 现象 | 说明 | 怎么办 |
|---|---|---|
| **SE Queries 很多**（几十上百） | 度量值被逐行调用（迭代里套 `CALCULATE` 的典型症状） | 检查 `SUMX`/`FILTER` 里的 `CALCULATE` |
| **FE 占比 > 50%** | 大量计算在公式引擎里逐行做 | 简化 DAX，改用聚合 |
| **物化行数巨大**（几百万） | 中间结果太大 | 减少中间表，用 `SUMMARIZECOLUMNS` 而非 `ADDCOLUMNS(SUMMARIZE(...))` |

> **说明**：本节讲的是**判断方法和健康标准**，具体毫秒数需要你在自己机器上跑（不同机器差异很大）。**重点是看 SE/FE 占比和 SE Queries 次数，而不是绝对值。**

### 5.4 一个可复现的对比实验

跑这两段，对比 Server Timings：

```dax
-- 实验 A：布尔筛选（应更快，SE Queries 少）
EVALUATE
SUMMARIZECOLUMNS(
    'dim_product'[category],
    "大额销售额", CALCULATE([有效销售额], 'fact_order_item'[line_amount] > 1000)
)

-- 实验 B：FILTER 整表（应更慢，SE Queries 多或 FE 高）
EVALUATE
SUMMARIZECOLUMNS(
    'dim_product'[category],
    "大额销售额", CALCULATE([有效销售额], FILTER('fact_order_item', 'fact_order_item'[line_amount] > 1000))
)
```

**你会看到**：A 比 B 快，且 B 的 FE 时间明显更高。

**在本库（8,445 行）差异可能只有几毫秒**，但把数据量放大到 800 万行，差异会变成"0.1 秒 vs 12 秒"。

> **这就是为什么要在小数据上养成好习惯** —— 小数据上看不出差别，你会以为"怎么写都行"，等数据涨上去就救不回来了。

## 六、模型优化 10 条清单

按顺序检查，收益从大到小：

| # | 优化项 | 做法 | 收益 |
|---:|---|---|---|
| 1 | **删掉不用的列** | 模型视图 / Power Query 里删除 | ⭐⭐⭐⭐⭐ 最直接 |
| 2 | **降低数值精度** | 金额如不需要小数，改成整数或定点小数 | ⭐⭐⭐⭐⭐ 大幅减少基数 |
| 3 | **拆开高基数的日期时间列** | `2024-06-15 14:32:07` 拆成日期列 + 时间列 | ⭐⭐⭐⭐⭐ 基数从百万降到千 |
| 4 | **减少计算列** | 能改成度量值/Power Query 的就改 | ⭐⭐⭐⭐ |
| 5 | **关闭自动日期/时间** | 选项 → 数据加载 → 取消勾选 | ⭐⭐⭐⭐ 每张日期表都省内存 |
| 6 | **保持单向筛选** | 不要开双向（除非明确需要） | ⭐⭐⭐⭐ |
| 7 | **用整数键代替文本键** | 关系用 ID 而非名称 | ⭐⭐⭐ |
| 8 | **避免 DISTINCTCOUNT 高基数列** | 或改用 `COUNTROWS` | ⭐⭐⭐ |
| 9 | **查询折叠** | ch03，会断的操作放最后 | ⭐⭐⭐（主要影响刷新） |
| 10 | **减少视觉对象数量** | 一页 ≤6 个图 | ⭐⭐（主要影响渲染） |

### 6.1 第 3 条详解：拆分日期时间列

这是**收益最高、最常被忽略**的一条。

| 列 | 基数 | 问题 |
|---|---:|---|
| `order_datetime`（精确到秒） | 可能上百万 | 每个值都唯一，完全无法压缩 |
| 拆成 `order_date`（日期） | 1,096 | 压缩好 |
| + `order_time`（时间） | 86,400 | 还是高，但可按需保留到"小时"（24 个值） |

**做法**（Power Query）：

```
拆分列 → 按分隔符（空格）→ 拆成日期列和时间列
时间列 → 提取 → 小时 → 只保留小时
```

结果：基数从上百万 → 1,096 + 24。

### 6.2 第 5 条：关掉自动日期/时间

ch02 提过，这里补充它的代价：

Power BI 默认给**每个日期类型的列**偷偷建一张隐藏日期表（含年/季/月/日）。

本库有多少日期列？`order_date`、`register_date`、`date_key` —— 至少 3 张隐藏表。每张约 1,096 行 × 若干列。

**真实项目里可能有 20 个日期列** → 20 张隐藏表 → 白白占内存、拖慢刷新。

**关掉**：文件 → 选项 → 当前文件 → 数据加载 → 取消「自动日期/时间」。

## 七、FDE 现场场景

### 场景 1：客户报表打开要 30 秒

**排查顺序**（从最可能到最不可能）：

| 步骤 | 检查 | 工具 |
|---:|---|---|
| 1 | 一页有多少个视觉对象？ | 目测，>10 个就减 |
| 2 | 度量值里有 `FILTER(事实表)` 吗？ | 看 DAX |
| 3 | 有迭代里套 `CALCULATE` 吗？ | 看 DAX |
| 4 | 高基数 `DISTINCTCOUNT` 有几个？ | 看 DAX |
| 5 | 有多少计算列？ | 模型视图 |
| 6 | 自动日期/时间关了吗？ | 选项 |
| 7 | 单页图表数 | 视觉对象数量 | 目测 |
| 8 | 数据模型多大？ | DAX Studio → View Metrics |

**最快的三板斧**（立竿见影）：

1. 关掉自动日期/时间（1 分钟，可能省 30% 内存）
2. 删掉不用的列（10 分钟）
3. 减少单页图表数（5 分钟）

### 场景 2：刷��要 40 分钟

**这是另一个问题** —— 刷新慢 ≠ 报表慢。

| 原因 | 排查 | 解决 |
|---|---|---|
| 查询折叠断了 | ch03：最后一步右键看"查看本机查询" | 把会断的操作放最后 |
| 拉了整张表又筛选 | 检查步骤顺序 | 先筛选后其他 |
| 列太多 | Power Query 看列数 | 删列 |
| 数据量真的很大 | 看行数 | **增量刷新**（ch11） |
| 计算列太多 | 模型视图 | 改度量值或下推到 SQL |

> **FDE 视角**：刷新时间是**业务方感知最强的性能指标**（他们每天打开都要等）。
> 交付前一定要实测刷新时间，并写进交付文档："本报表全量刷新约 X 分钟"。
> 如果超过 10 分钟，就该考虑增量刷新了。

### 场景 3：客户问"能不能算到秒级实时"

**典型误解**：业务方以为 Power BI 能像监控大屏一样实时刷新。

**现实**：

| 模式 | 数据新鲜度 | 代价 |
|---|---|---|
| 导入 + 定时刷新 | **最快 30 分钟**（Power BI Service 限制，Premium 可到 15 分钟甚至更短） | 低 |
| DirectQuery | 实时 | 慢、DAX 受限 |
| 混合（Hybrid Tables） | 近实时 + 历史导入 | Premium 功能，复杂 |

**沟通话术**：

> "目前是每天刷新 3 次（早8点、中午12点、下午6点）。如果您需要看实时数据，可以改用 DirectQuery，但报表会明显变慢，而且很多分析功能用不了。**一般业务分析其实不需要实时，每小时/每天刷新足够做决策。**"

**99% 的情况下**，业务方说"要实时"，实际需要的是"每天早上能看到昨天的数据"。**先问清楚再动手。**

| 你学到了 | 关键点 |
|---|---|
| VertiPaq | 列式存储 + **字典压缩**；基数决定内存和速度 |

| 杀手四 | 双向关系 → 正常模型应 0 个双向箭头 |

| 刷新 vs 报表 | 刷新慢查折叠和列数；报表慢查 DAX 和图表数 |

## 九、练习题

### 练习 1：算一算你的模型有多大（考：基数意识）

**题目**：根据真实基数数据，判断哪些列占内存最多，并按"优化优先级"排序。

**已知基数**：

| 列 | 不同值 | 行数 | 唯一值占比 |
|---|---:|---:|---:|
| `fact_order_item[quantity]` | 4 | 8,445 | 0.0% |
| `fact_order_item[discount_rate]` | 24 | 8,445 | 0.3% |
| `fact_order[status]` | 3 | 3,529 | 0.1% |
| `dim_product[category]` | 5 | 200 | 2.5% |
| `fact_order[order_date]` | 1,018 | 3,529 | 28.8% |
| `dim_customer[customer_name]` | 477 | 500 | 95.4% |
| `fact_order_item[line_amount]` | 5,635 | 8,445 | 66.7% |
| `fact_order[order_id]` | 3,529 | 3,529 | 100% |

**答案与解析**：

**占内存最多的三列**（按"唯一值个数 × 行数"估算）：

| 排名 | 列 | 原因 |
|---:|---|---|
| 1 | `fact_order_item[line_amount]` | 5,635 个唯一值 × 8,445 行，**完全压不动** |
| 2 | `fact_order[order_id]` | 3,529 个唯一值，100% 无法压缩 |
| 3 | `fact_order[order_date]` | 1,018 个唯一值（日期类型还好，VertiPaq 对日期有特殊优化） |

**优化优先级**：

| 优先级 | 做法 | 理由 |
|---:|---|---|
| 1 | **给 `line_amount` 降精度**（如改成整数或 1 位小数） | 唯一值占比 66.7% → 可能降到 20% 以下，收益最大 |
| 2 | **隐藏或删除 `order_id`**（如果不做 DISTINCTCOUNT） | 100% 唯一，完全无法压缩 |
| 3 | `customer_name`（477 唯一值）如果能用 ID 代替分组，改用 ID | 但显示时还是需要名称 |
| 4 | `quantity`、`discount_rate`、`status`、`category` | **不用管**，基数极低，压缩得很好 |

**关键认知**：

> **优化的重点永远是"高基数列"，低基数列（<100 个值）几乎不占内存，不用费心。**

**验证 SQL**（看唯一值占比）：

```sql
SELECT 'line_amount' AS 列, COUNT(DISTINCT line_amount) AS 唯一值,
       COUNT(*) AS 总行,
       ROUND(COUNT(DISTINCT line_amount)*100.0/COUNT(*),1) AS 唯一值占比pct
FROM fact_order_item
UNION ALL
SELECT 'quantity', COUNT(DISTINCT quantity), COUNT(*),
       ROUND(COUNT(DISTINCT quantity)*100.0/COUNT(*),1) FROM fact_order_item;
-- 预期：line_amount 5635 | 8445 | 66.7
--       quantity      4 | 8445 | 0.0
```

### 练习 2：改写四类慢 DAX（考：识别性能杀手）

**题目**：下面四个度量值都有性能问题，找出并改写。

```dax
-- ①
销售额A = SUMX('fact_order_item', CALCULATE(SUM('fact_order_item'[line_amount])))

-- ②
大额订单数 = CALCULATE([有效订单数], FILTER('fact_order_item', 'fact_order_item'[line_amount] > 1000))

-- ③
订单数 = DISTINCTCOUNT('fact_order'[order_id])

-- ④
销售额B = SUMX(FILTER('fact_order_item', 'fact_order_item'[line_amount] > 0), 'fact_order_item'[line_amount])
```

**答案与解析**：

| # | 问题 | 改写 |
|---|---|---|
| ① | **迭代里套 CALCULATE** → 8,445 次上下文转换 | `SUM('fact_order_item'[line_amount])` |
| ② | **`FILTER` 整张事实表** | `CALCULATE([有效订单数], 'fact_order_item'[line_amount] > 1000)` |
| ③ | 高基数 `DISTINCTCOUNT`（3,529 唯一值） | `COUNTROWS('fact_order')`（一行一单，等价且快） |
| ④ | 不必要的 `SUMX` + `FILTER`，`line_amount > 0` 对求和无影响（负数才需要过滤） | `SUM('fact_order_item'[line_amount])` |

**改写后**：

```dax
-- ①②③④ 的最优写法
销售额A = SUM('fact_order_item'[line_amount])

大额订单数 = CALCULATE([有效订单数], 'fact_order_item'[line_amount] > 1000)

订单数 = COUNTROWS('fact_order')

销售额B = SUM('fact_order_item'[line_amount])
```

**为什么 ③ 可以改**：

`fact_order` 的结构是**一行一张订单**，`order_id` 是主键（唯一、非空）。

所以 `DISTINCTCOUNT(order_id)` = `COUNTROWS('fact_order')` = 3,529。

但 `COUNTROWS` 直接读表的行数（元数据），**不需要扫描列**，快得多。

> **适用条件**：只有当"一列在表里唯一且非空"时才等价。如果 `order_id` 有重复或空值，两者就不同了 —— **改之前先用 SQL 验证唯一性**。

**验证 SQL**：

```sql
SELECT COUNT(*) AS 行数,
       COUNT(DISTINCT order_id) AS 去重数,
       COUNT(*) - COUNT(DISTINCT order_id) AS 差值
FROM fact_order;
-- 预期：3529 | 3529 | 0  ← 差值为 0 说明可以安全改写
```

### 练习 3：验证自动日期/时间的代价（考：优化项 5）

**题目**：做这个对比实验：

1. 打开「自动日期/时间」（选项 → 数据加载）
2. 保存文件，记录文件大小
3. 关闭「自动日期/时间」，再保存
4. 比较两次的文件大小

**预期结果**：

关闭后文件**明显变小**（本库可能从几 MB 降到更小，具体数字取决于你的模型）。

**解析**：

Power BI 为每个日期列偷偷建一张隐藏日期表。本库日期列有 `order_date`、`register_date`、`date_key` 至少 3 个 —— 关掉后省掉 3 张隐藏表。

**同时你会在字段列表里看到**：打开自动日期/时间时，每个日期字段下会多出一个层级（年/季/月/日）；关掉后这些消失。

> **注意**：关掉后，如果你之前用了这些自动层级做分组，图表会报错。所以**建议在建模初期就关掉**，而不是后期。

### 练习 4：判断该放哪一层（考：计算落点决策）

**题目**：以下 8 个计算，分别该放在 SQL / Power Query / 计算列 / 度量值 哪一层？

| # | 计算 | 放哪层 |
|---:|---|---|
| 1 | 有效销售额（需随筛选变化） | ？ |
| 2 | 把 `2024/6/15` 文本转成日期类型 | ？ |
| 3 | 给订单打"大额/小额"标签（按金额阈值） | ？ |
| 4 | 各品类毛利率 | ？ |
| 5 | 从 200 列的大表里删掉 170 个不用的列 | ？ |
| 6 | 客户姓名（姓 + 名拼接） | ？ |
| 7 | 去年同期销售额 | ？ |
| 8 | 把金额从"元"换算成"万元"（固定换算） | ？ |

**答案**：

| # | 计算 | 层 | 理由 |
|---:|---|---|---|
| 1 | 有效销售额 | **度量值** | 需随筛选变化 ⭐ |
| 2 | 文本转日期 | **Power Query** | 清洗，刷新时做一次 |
| 3 | 大额/小额标签 | **计算列**或 **Power Query** | 每行固定的分组标签 |
| 4 | 各品类毛利率 | **度量值** | 聚合指标，且需加权（ch05） |
| 5 | 删 170 列 | **Power Query** | 不进模型，收益最大 |
| 6 | 姓名拼接 | **Power Query**（优先）或计算列 | 每行固定；PQ 更好因为不占模型内存（其实都占，但 PQ 更早生效） |
| 7 | 去年同期 | **度量值** | 依赖日期表，必须查询时算 |
| 8 | 元→万元 | **度量值**（改格式即可） | 其实**连计算都不用**，设置显示格式"除以10000"就行 |

**第 8 条的额外提示**：

Power BI 的度量值格式支持**自定义显示单位**：选中度量值 → 度量工具 → 显示单位 → 选"万"或自定义。

> **能用显示格式解决的，不要新建度量值。** 比如"万元"只是一个显示问题，不该真的把数据除以 10000（那会让后续计算容易搞混单位）。

### 练习 5：制定你的优化检查清单（考：综合应用）

**题目**：假设你接手一个客户报表，它有三个症状。请给出排查顺序和每一步的具体动作。

症状：
- A. 打开报表要 25 秒
- B. 刷新要 40 分钟
- C. 文件有 480 MB

**答案与解析**：

**这是三个独立问题，要分开解决，别混在一起。**

#### 症状 A：打开慢（25 秒）—— 查询/渲染问题

| 顺序 | 动作 | 预期收益 |
|---:|---|---|
| 1 | 数一数单页视觉对象数量 | >10 个就拆页，**立竿见影** |
| 2 | 检查度量值有没有 `FILTER(事实表)` / 迭代套 CALCULATE | 改掉可能快 5-10 倍 |
| 3 | DAX Studio 看 SE/FE 占比 | FE>50% 说明 DAX 写得差 |
| 4 | 检查高基数 DISTINCTCOUNT 有几个 | 改成 COUNTROWS 或删除 |

#### 症状 B：刷新慢（40 分钟）—— 数据加载问题

| 顺序 | 动作 | 预期收益 |
|---:|---|---|
| 1 | **检查查询折叠**（每个查询最后一步右键看"查看本机查询"） | 断了的改顺序，**最大收益** |
| 2 | 删掉不用的列 | 传输量减少 |
| 3 | 检查计算列数量 | 改度量值或下推 SQL |
| 4 | 如果以上都做了还慢 → **增量刷新**（ch11） | 40 分钟 → 几分钟 |

> **A 和 B 的排查路径完全不同**：A 看 DAX 和图表，B 看 Power Query 和折叠。**很多人混淆这两者，在 DAX 上花半天却对刷新时间毫无帮助。**

#### 症状 C：文件 480 MB —— 模型体积问题

| 顺序 | 动作 | 预期收益 |
|---:|---|---|
| 1 | 关掉自动日期/时间 | 可能省 10-30% |
| 2 | **删掉不用的列**（尤其高基数列） | 最大收益 |
| 3 | 拆分日期时间列（精确到秒的拆成日期+小时） | 基数从百万降到千 |
| 4 | 减少计算列（改度量值） | 计算列是内存杀手 |
| 5 | 降低金额精度 | 减少唯一值 |

**用 DAX Studio 看具体是哪些列占内存**：

1. DAX Studio → **Advanced** → **View Metrics**
2. 看每列的 `Total Size` 和 `Cardinality`
3. 按大小排序，从最大的开始优化

> **这是最科学的方法** —— 不用猜，直接看数据告诉你哪列最大。
