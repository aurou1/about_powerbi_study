# ch11 企业级：发布 / 网关 / RLS / 增量刷新 🏢

> 本章目标：把本地报表**交付给其他人用**，并解决三个企业级问题：数据怎么自动更新、不同人怎么看不同数据、大表怎么快速刷新。

---

## 一、本章学习目标

学完本章你应该能：

1. 完成一次 **Desktop → Service 的完整发布**并配通刷新
2. 说清**网关**的作用和两种模式（个人 / 标准）
3. 配出**静态 RLS** 和**动态 RLS**，并自测验证
4. 为 `fact_order` 配置**增量刷新**
5. 用 App 把报表分发给终端用户

## 二、发布：从桌面到云端

### 2.1 概念澄清：三个"地方"

| 名称 | 是什么 | 存什么 |
|---|---|---|
| **Power BI Desktop** | 本机软件 | 你开发的 .pbix 文件 |
| **Power BI Service** | 网页版（app.powerbi.com） | 发布后的报表、语义模型、刷新计划、权限 |
| **工作区（Workspace）** | Service 里的"文件夹" | 一组相关的报表和模型 |

发布 = 把 .pbix 上传到 Service 的某个工作区。

### 2.2 发布步骤

1. Power BI Desktop → 主页 → **发布** → 发布到 Power BI
2. 选择目标工作区（默认"我的工作区"，但**生产环境应该用专用工作区**）
3. 等待上传完成，点"在 Power BI 中打开"

### 2.3 关键：发布后必须重新配数据源凭据

**这是第一次发布 100% 会踩的坑。**

发布完成后，云端报表点"刷新"，大概率报**凭据错误**。

**原因**：你在本机保存的 MySQL 密码**不会**自动同步到云端。云端是另一台机器、另一个环境，它不知道你的密码。

**解决方法**：

1. Service → 工作区 → 找到你发布的**语义模型**（Semantic model，图标像个数据库）
2. 点 ⋯ → **设置**
3. 展开「**数据源凭据**」→ 点「编辑凭据」
4. 身份验证方法选「**基本**」→ 填 MySQL 用户名密码
5. 如果提示需要网关，先配好网关（见第 3 节）

> ⚠️ **踩坑提醒**：如果数据源是**本机数据库**（localhost），光配凭据还不够 —— 云端连不到你的电脑，必须装**网关**。

### 2.4 工作区与许可证

| 工作区类型 | 要求 | 适合 |
|---|---|---|
| **我的工作区** | 免费账号就有 | 个人学习，**不适合共享** |
| **Pro 工作区** | 每人需要 Pro 许可证 | 小团队协作（≤几十人） |
| **Premium / Fabric 容量** | 需要容量许可证 | 大企业、大数据量、需要增量刷新/分页报表等高级功能 |

> **注意**：**增量刷新需要 Premium 或 PPU**（Premium Per User）。这是 ch11 第 7 节功能的前提，你的组织如果没有 Premium，只能用分区 + XMLA 等变通方案。

## 三、网关（Gateway）：连接云端和本地数据

### 3.1 为什么需要

```
云端 Power BI Service  ──✗──▶  你电脑上的 localhost:3306
        （公网）                    （内网，没有公网 IP）
```

云端服务器**无法直接访问**你本机或公司内网的数据库。网关就是中间的"桥"：

```
Service ──▶ 网关（装在你内网的一台机器上）──▶ 公司数据库
```

### 3.2 两种模式

| | **个人模式**（Personal） | **标准模式**（Standard / On-premises data gateway） |
|---|---|---|
| 装在哪 | 你自己的电脑 | 一台**常开的服务器**（推荐） |
| 谁能用 | **只有你** | 整个组织共享 |
| 支持数据源 | 有限（不支持部分高级源） | 全部 |
| 电脑关机 | **刷新失败** ❌ | 不受影响 ✅ |
| 适合 | 个人学习、临时验证 | **生产环境** |

> ⚠️ **重要**：**生产环境必须用标准模式，且装在服务器上。**
> 装在自己电脑上 = 你一关机所有报表刷新全部失败 —— 这是很多团队踩过的坑。

### 3.3 安装与配置（标准模式）

1. 在有权限访问数据库的**内网机器**上下载网关：
   <https://powerbi.microsoft.com/gateway/>
2. 安装时登录你的 Power BI 账号
3. 选择「**注册新网关**」→ 命名（如"公司数据网关"）→ 设置恢复密钥（**务必保存**）
4. 回到 Service → 设置 → **管理网关** → 看到刚注册的网关，状态应为"**联机**"
5. 点网关 → **添加数据源**：
   - 数据源名称：如 `MySQL_生产`
   - 数据源类型：MySQL
   - 服务器：`localhost`（相对网关机器而言！）
   - 数据库：`study_powerbi_demodata`
   - 身份验证：基本 → 填用户名密码
6. 回到语义模型设置 → **网关连接** → 选择这个网关

**关键点**：网关配置里的服务器地址，是**从网关机器看出去的地址**。网关装在你电脑上就填 `localhost`，装在服务器上就填数据库在那台服务器能访问到的地址。

## 四、计划刷新与失败告警

### 4.1 设置计划刷新

语义模型 → ⋯ → 设置 → **计划刷新**：

| 选项 | 说明 |
|---|---|
| 保持最新数据 | 开 |
| 刷新频率 | 每天 / 每周 |
| 时间 | 可设多个时间点（如 8:00、12:00、18:00） |
| 时区 | 注意选对（北京时间） |
| 发送刷新失败通知 | **务必勾选**，并填自己的邮箱 |

**免费版限制**：每天最多 8 次；**Pro** 每天 8 次；**Premium** 每天 48 次。

### 4.2 刷新失败的常见原因

| 报错 | 原因 | 解决 |
|---|---|---|
| 凭据无效 | 云端没配或密码改了 | 重新编辑凭据 |
| 找不到网关 / 网关脱机 | 网关机器关机了 | 用标准模式装在常开服务器 |
| 数据源未找到 | 网关里没加这个数据源 | 网关中添加数据源 |
| 列 X 不存在 | 源表结构变了（有人删了列） | 改 Power Query 或让 IT 恢复列 |
| 超时 | 刷新超过限制（默认 2 小时） | 优化（ch10）或用增量刷新 |

> **FDE 视角**：**刷新失败告警一定要开，并且发到你邮箱。**
> 我见过业务方用了三个月才发现"数据一直是上个月的" —— 因为没人收到失败通知，报表显示的是旧数据，看起来"完全正常"。
> **这是数据交付里最严重的静默故障。**

## 五、语义模型与报表分离（最佳实践）

Power BI 里，**数据集（现在叫语义模型）**和**报表**是分开的两个对象：

```
语义模型（Semantic model）= 数据 + 关系 + 度量值    ← 技术层
报表（Report）            = 图表和布局              ← 展示层
```

### 5.1 为什么要分离

| 好处 | 说明 |
|---|---|
| **多人协作** | 一个人维护模型，其他人基于模型做报表 |
| **口径统一** | 所有报表共用同一套度量值，不会出现"两个销售额" |
| **复用** | 一个模型可以支撑 20 张报表 |
| **权限分离** | 数据工程师管模型，业务分析师管图表 |

### 5.2 怎么做

1. 建一个 .pbix，**只放数据和度量值，不放任何图表** → 发布 → 这是「语义模型」
2. 再建一个 .pbix → **获取数据 → Power BI 语义模型**（实时连接）→ 选刚才那个模型 → 做图表 → 发布 → 这是「报表」

> **这是企业级 Power BI 项目的标准做法。** 小项目可以不做，但只要涉及多人协作，分离能省掉无数麻烦。

## 六、RLS 行级安全：让不同人看不同数据

### 6.1 场景

> "华东大区经理只能看华东的数据，华南经理只能看华南的数据。"

RLS（Row-Level Security）就是干这个的：**同��张报表，不同人看到不同的行。**

### 6.2 静态 RLS（简单但角色多）

**做法**：

1. Power BI Desktop → 建模 → **管理角色** → 新建
2. 角色名：`华东经理`
3. 在 `dim_region` 表上添加筛选器：

```dax
[zone] = "华东"
```

4. 保存 → 发布

**可以添加多个角色**：华东经理、华南经理、华北经理……

**自测**：

建模 → 通过以下身份查看 → 选「华东经理」→ 报表只显示华东数据。

**预期结果**（以华东经理身份查看）：

| 大区 | 销售额 |
|---|---:|
| 华东 | **3,138,680.06** |
| ~~华南~~ | 不显示 |
| ~~华北~~ | 不显示 |

**缺点**：有几个大区就要建几个角色。如果有 50 个销售员，就要建 50 个角色 —— 维护噩梦。

### 6.3 动态 RLS（推荐）

**核心思路**：建**一个**角色，用 `USERPRINCIPALNAME()` 拿到当前登录用户的邮箱，去一张「映射表」里查出他能看哪些数据。

**步骤**：

**① 建映射表**

在数据源里加一张表（本库没有，你可以用「输入数据」手工建一个查询）：

| user_email | province_name |
|---|---|
| zhangsan@company.com | 广东 |
| zhangsan@company.com | 广西 |
| lisi@company.com | 浙江 |
| lisi@company.com | 上海 |

表命名 `dim_user_region`。

**② 建关系**

```
dim_user_region[province_name] → dim_region[province_name]
```

**③ 建角色**

建模 → 管理角色 → 新建角色 `区域负责人`：

在 `dim_user_region` 表上添加筛选器：

```dax
[user_email] = USERPRINCIPALNAME()
```

**④ 发布并在 Service 里分配用户**

语义模型 → ⋯ → **安全性** → 在「区域负责人」角色里添加成员（填用户的 Power BI 账号邮箱）。

**⑤ 自测**

语义模型 → ⋯ → 安全性 → 角色右边的 ⋯ → **以身份测试** → 输入 `zhangsan@company.com` → 报表只显示广东+广西的数据。

### 6.4 两种 RLS 对比

| | 静态 RLS | 动态 RLS |
|---|---|---|
| 角色数量 | 每个区域一个 | **一个** |
| 维护成本 | 高（改一次要改多个角色） | 低（改映射表即可） |
| 适合 | 区域少（≤5）、权限简单 | **区域多、权限复杂（推荐）** |
| 依赖 | 无 | 需要用户用 Power BI 账号登录 |

> ⚠️ **踩坑提醒**：`USERPRINCIPALNAME()` 返回的是**用户的登录邮箱（UPN）**，不是显示名。如果映射表里填的是姓名，永远匹配不上 —— **这是动态 RLS 最常见的失败原因**。

### 6.5 RLS 的两个重要特性

**① RLS 对管理员不生效**

工作区的管理员/成员/参与者**看得到全部数据**（RLS 只作用于查看者 Viewer）。所以**自测一定要用"以身份测试"功能**，而不是自己打开看。

**② RLS 会影响性能**

每个用户查询时都要多一层筛选。复杂 RLS 规则（比如用 `CONTAINS` 或跨多张表）会明显变慢。

## 七、增量刷新（Increment��l Refresh）

### 7.1 问题

`fact_order` 现在 3,529 行，全量刷新只要几秒。但如果是 **3,000 万行**呢？

每次刷新都把 3,000 万行重新拉一遍：慢、占资源、容易超时。

**但其实**：历史数据（比如 2 年前的订单）**几乎不会变**，变的只有最近的数据。

### 7.2 增量刷新的思路

```
把表按日期切成"分区"：
┌─────────────┬─────────────┬─────────────┐
│  2023年      │  2024年      │  2025年1-11月│  2025年12月  │
│  归档，不刷   │  归档，不刷   │  归档，不刷   │  ← 只刷这个  │
└─────────────┴─────────────┴─────────────┴─────────────┘
```

每次刷新**只重新加载最近 N 天**的分区，历史分区原封不动。

### 7.3 前提条件

| 条件 | 说明 |
|---|---|
| **许可证** | 需要 **Premium / PPU / Fabric 容量**（Pro 不支持） |
| **日期列** | 事实表必须有日期列（`fact_order[order_date]` ✅） |
| **参数** | 需要在 Power Query 里建 `RangeStart` 和 `RangeEnd` 两个参数 |
| **查询折叠** | 筛选必须能折叠成 SQL（ch03） |

### 7.4 配置步骤

**① 在 Power Query 里建两个参数**

| 名称 | 类型 | 默认值 |
|---|---|---|
| `RangeStart` | 日期/时间 | `2023-01-01` |
| `RangeEnd` | 日期/时间 | `2025-12-31` |

> ⚠️ **参数名必须一字不差**（`RangeStart` / `RangeEnd`），且类型必须是「日期/时间」。

**② 在 `fact_order` 查询里加筛选步骤**

1. 选中 `order_date` 列 → 筛选 → 日期筛选 → **介于**
2. 起始日期选「参数」→ `RangeStart`
3. 结束日期选「参数」→ `RangeEnd`
4. 确定

**③ 验证折叠**

右键最后一步 → 「查看本机查询」应**可点击**。你会看到 SQL 里有 `WHERE order_date BETWEEN ... AND ...`。

> **如果这步折叠断了，增量刷新不会生效**（会退化成全量刷新）。

**④ 在 Desktop 里定义增量刷新策略**

右键 `fact_order` 表 → **增量刷新**：

| 设置 | 值 | 含义 |
|---|---|---|
| 存档数据起始时间 | **24 个月** | 保留最近的 24 个月数据 |
| 增量刷新数据起始时间 | **3 天** | 每次刷新只重新加载最近 3 天 |
| 检测数据更改 | 可选（按某个"最后修改时间"列） | 更精细的控制 |
| 仅刷新完整天 | 建议勾选 | 避免当天数据不完整 |

**⑤ 发布**

发布后，**第一次刷新会建所有分区**（可能很慢），之后每次只刷最近 3 天。

### 7.5 注意事项

| 注意 | 说明 |
|---|---|
| **首次刷新很慢** | 要建所有分区，耐心等 |
| **发布后不能随便改结构** | 改了结构需要重新全量刷新 |
| **历史分区不会更新** | 如果历史数据被修改（比如订单状态变更），**不会反映到报表**。需要手动全量刷新一次 |
| **参数名固定** | 必须是 `RangeStart` / `RangeEnd` |

> **FDE 视角**：增量刷新的"历史分区不更新"这个特性，一定要**提前告诉客户**。
> 我见过客户问"为什么三个月前的订单状态变了，报表上还是旧的" —— 因为它在归档分区里。
> **解决方案**：定期（比如每月一次）做全量刷新，或者启用"检测数据更改"（需要源表有 `last_modified` 时间戳列）。

## 八、发布成 App 分发给用户

工作区适合协作者，但给**终端用户**（只看报表的人）应该用 **App**。

### 8.1 为什么用 App

| | 工作区 | App |
|---|---|---|
| 适合 | 开发协作者 | **终端用户** |
| 界面 | 能看到所有对象和设置 | 简洁，只有报表 |
| 权限 | 复杂 | 简单（安装即可看） |
| 更新 | 实时 | 需要重新发布 App 才推送更新 |

### 8.2 步骤

1. 工作区 → 右上角「**创建应用**」（Create app）
2. 填写名称、描述、主题色
3. 选择要包含哪些报表
4. 设置**受众**（Audience）—— 可以按人群分组，分配不同报表
5. 发布 → 得到分享链接
6. 用户打开链接 → 安装 App → 自动添加到他的 Power BI 首页

> **更新流程**：改了报表后，要回到 App → **重新发布** → 选择"更新应用"，用户才会看到新版本。

## 九、FDE 现场场景

### 场景 1：客户 IT 不给装网关

**常见阻力**："我们不允许在服务器上装第三方软件。"

**应对方案**（按优先级）：

| 方案 | 说明 | 适合 |
|---|---|---|
| 1. 请 IT 参与安装 | 让客户 IT 自己操作，你在旁边指导 | 最理想 |
| 2. 用虚拟机 | 在客户已有的虚拟机里装 | IT 可控，容易接受 |
| 3. 数据定期导出 | 客户每天导出文件到固定位置，Power BI 读文件 | 无需网关，但非实时 |
| 4. 数据库迁到云 | 用云数据库（如 Azure SQL / 阿里云 RDS） | 无需网关，直连 |

**话术**：

> "网关是微软官方组件，很多企业都在用。如果您这边有安全顾虑，我们可以让贵司 IT 全程操作安装，我只提供步骤文档。或者我们也可以走文件导出的方案，只是数据会有一天延迟。"

**永远给客户备选方案**，不要让他们感觉"只能按你说的来"。

### 场景 2：上线后刷新失败，业务方来问

**标准排查流程**（建议存为团队文档）：

```
1. 看失败邮件通知（有没有？什么时候开始的？）
2. Service → 语义模型 → 刷新历史记录 → 看具体报错
3. 按报错分类：
   ├─ 凭据问题 → 重新编辑凭据
   ├─ 网关脱机 → 检查网关机器（是不是关机了/网络断了）
   ├─ 列不存在 → 源表结构变了，联系客户 IT
   ├─ 超时 → 优化或增量刷新
   └─ 数据类型错误 → 源数据有脏值
4. 修复后手动刷新一次验证
5. 回复业务方：说明原因 + 修复时间 + 数据已恢复
```

**关键**：**回复时要说清楚"数据从什么时候到什么时候是有问题的"**，让业务方知道要不要重新看之前的分析。

### 场景 3：客户要求"销售员只能看自己的客户"

这是典型的动态 RLS 需求，但有个隐藏问题：

**销售经理要能看到他手下所有销售员的客户**（层级权限）。

**解决**：映射表设计成**层级结构**：

| user_email | 可看的 sales_id |
|---|---|
| sales1@company.com | S001（自己） |
| manager1@company.com | S001, S002, S003（团队） |
| director@company.com | 全部 |

然后 RLS 规则用：

```dax
[sales_id] IN
    CALCULATETABLE(
        VALUES('dim_user_scope'[sales_id]),
        'dim_user_scope'[user_email] = USERPRINCIPALNAME()
    )
```

> **这类层级权限需求非常常见**，但需要在**需求阶段就问清楚**，不然后面改映射表结构会很痛苦。

| 发布 | Desktop → Service 工作区；**发布后必须重配凭据** |
| 网关 | 桥接云端↔内网数据库；**生产用标准模式装在服务器** |
| 计划刷新 | 设多个时间点 + **务必开失败告警**（防静默故障） |
| 模型报表分离 | 一个语义模型支撑多张报表，口径统一 |
| RLS 静态 | 每个区域一个角色，简单但难维护 |
| RLS 动态 | **一个角色 + 映射表** + `USERPRINCIPALNAME()` |
| RLS 验证 | 必须用「**以身份测试**」（管理员看得到全部） |
| 增量刷新 | 需 Premium；`RangeStart`/`RangeEnd` 参数；**首次刷新慢** |
| 增量刷新坑 | **历史分区不更新**，需定期全量刷新 |
| App | 给终端用户分发用，改了报表要"重新发布" |

### 练习 1：配静态 RLS 并自测（考：RLS 基础）

**题目**：建一个「华东经理」角色，限制 `dim_region[zone] = "华东"`，然后用"通过以下身份查看"自测。

**预期结果**：

| 维度 | 华东经理看到 |
|---|---:|
| 有效销售额 | **3,138,680.06** |
| 可见大区 | 仅华东 |
| 可见省份 | 浙江、上海、江苏、山东（4 个） |
| 订单数 | 1,013 |

**对照**（无 RLS 时）：

| 维度 | 全部数据 |
|---|---:|
| 有效销售额 | 7,195,492.73 |
| 可见大区 | 7 个 |
| 可见省份 | 10 个 |
| 订单数 | 2,366 |

**解析**：

RLS 在**数据模型层**生效（不是隐藏行，是真的筛选掉），所以：

- 所有度量值自动按华东重算
- 占比类度量值的分母也变了（如果用 `ALLSELECTED`，分母 = 3,138,680.06）
- KPI 卡片、图表、矩阵全部一致

**验证 SQL**：

```sql
SELECT COUNT(*) AS 订单数, ROUND(SUM(o.order_amount),2) AS 销售额
FROM fact_order o JOIN dim_region r ON o.region_id=r.region_id
WHERE o.status='已完成' AND r.zone='华东';
-- 预期：1013 | 3138680.06
```

**自测步骤**（关键）：

1. 建模 → 通过以下身份查看 → 选「华东经理」
2. 观察报表数字变成 3,138,680.06
3. **退出身份查看**（否则你会一直以为数据少了）

> ⚠️ **重要**：工作区**管理员不受 RLS 限制**。所以你自己打开报表看到的是全量数据，**必须用"通过以下身份查看"才能验证 RLS 是否生效**。

### 练习 2：设计动态 RLS 映射表（考：动态 RLS）

**题目**：公司有 3 个大区经理，每人负责一个大区。设计映射表并写出 RLS 规则。

**答案与解析**：

**映射表** `dim_user_region`：

| user_email | zone |
|---|---|
| huadong@company.com | 华东 |
| huanan@company.com | 华南 |
| huabei@company.com | 华北 |

**关系**：

```
dim_user_region[zone]  →  dim_region[zone]  （多对一，单向）
```

**RLS 规则**（在 `dim_user_region` 表上）：

```dax
[user_email] = USERPRINCIPALNAME()
```

**工作原理**（三步）：

1. 用户 `huadong@company.com` 打开报表
2. `USERPRINCIPALNAME()` 返回 `"huadong@company.com"`
3. RLS 筛选 `dim_user_region` → 只剩 zone="华东" 一行
4. 筛选沿关系到 `dim_region` → 只剩华东的省份
5. 再到 `fact_order` → 只剩华东的订单

**预期结果**（以 huadong@company.com 身份查看）：

| 维度 | 值 |
|---|---:|
| 有效销售额 | 3,138,680.06 |
| 可见省份 | 浙江、上海、江苏、山东 |

**常见失败原因排查**：

| 现象 | 原因 |
|---|---|
| 看到全部数据 | ①RLS 没发布 ②你是工作区管理员 ③没在 Service 里把用户加进角色 |
| 看到空白 | `USERPRINCIPALNAME()` 返回值与映射表不匹配（比如一个是邮箱，一个是姓名） |
| 报错 | 关系没建，或关系方向不对 |

**调试技巧**：

建一个临时度量值，把当前登录身份显示出来：

```dax
当前用户 = USERPRINCIPALNAME()
```

拖到卡片上，用"以身份测试"功能查看 —— 你就能确认它到底返回什么，**然后按这个格式去填映射表**。

> **这是排查动态 RLS 最有效的方法**，比猜来猜去快得多。

### 练习 3：增量刷新的参数配置（考：增量刷新）

**题目**：为 `fact_order` 配置增量刷新。说明需要建哪些参数、怎么筛选、如何验证折叠。

**答案与解析**：

**① 建参数**（Power Query → 管理参数）：

| 名称 | 类型 | 默认值 |
|---|---|---|
| `RangeStart` | **日期/时间** | 2023-01-01 00:00:00 |
| `RangeEnd` | **日期/时间** | 2025-12-31 00:00:00 |

> ⚠️ 名称必须**一字不差**，类型必须是**日期/时间**（不是"日期"）。

**② 加筛选步骤**（在 `fact_order` 查询）：

1. 选中 `order_date` 列
2. 筛选 → 日期/时间筛选 → **介于**
3. 起始：`RangeStart`（选"参数"）
4. 结束：`RangeEnd`（选"参数"）

**③ 验证折叠**（这一步不能省）：

右键最后一步 → 「**查看本机查询**」应可点击。点开应该看到类似：

```sql
select ... from `study_powerbi_demodata`.`fact_order`
where `order_date` between '2023-01-01' and '2025-12-31'
```

**如果「查看本机查询」是灰的** → 折叠断了 → 增量刷新**不生效**（会退化成全量拉数）。

**④ 定义策略**（右键表 → 增量刷新）：

| 设置 | 建议值 |
|---|---|
| 存档数据 | 24 个月 |
| 增量刷新 | 3 天 |
| 仅刷新完整天 | 勾选 |

**⑤ 预期效果**：

| 阶段 | 行为 |
|---|---|
| 首次刷新 | 建所有分区（**慢**，要拉全量） |
| 之后每次 | 只刷最近 3 天（**快**） |

**验证 SQL**（理解分区范围）：

```sql
-- 最近 3 天有多少订单（这就是每次增量刷新要处理的数据量）
SELECT COUNT(*) FROM fact_order
WHERE order_date >= DATE_SUB((SELECT MAX(order_date) FROM fact_order), INTERVAL 3 DAY);
-- 本库数据止于 2025-12-31，最近 3 天订单数很少
```

> **注意**：本库只有 3,529 行，增量刷新的收益体现不出来。
> **这个练习的价值在于掌握配置方法** —— 等你在生产环境遇到千万行表时，这套步骤能救你的报表。

### 练习 4：诊断刷新失败（考：运维能力）

**题目**：周一早上，业务方说"报表数据还是上周五的"。你登录 Service 看到刷新历史记录里有 3 次失败。给出排查步骤和可能的三种原因。

**答案与解析**：

**排查步骤**：

```
1. 语义模型 → ⋯ → 刷新历史记录 → 看 3 次失败的报错信息
2. 按报错分类处理
3. 手动"立即刷新"验证
4. 修复后通知业务方
```

**三种最常见的原因**：

| # | 原因 | 报错特征 | 解决 |
|---:|---|---|---|
| 1 | **网关机器关机** | "网关脱机"、"无法连接到网关" | 用标准模式装在**常开服务器**；或个人模式改用标准模式 |
| 2 | **凭据失效** | "凭据无效"、"身份验证失败" | 语义模型设置 → 数据源凭据 → 重新编辑（密码可能改了或过期了） |
| 3 | **源表结构变了** | "找不到列 XX"、"列 XX 不存在" | 客户 IT 改了表结构（删列/改名）；改 Power Query 适配，或请 IT 恢复 |

**其他可能**：

| 原因 | 特征 |
|---|---|
| 刷新超时 | "已超过刷新时间限制"（默认 2 小时）→ 优化或增量刷新 |
| 数据类型错误 | "无法将值 XX 转换为类型 数字" → 源数据有脏值 |
| 存储容量满 | "已达到存储限制" → 清理或升级许可证 |

**这个场景最重要的一点**：

> **业务方发现"数据是旧的"，说明你没有开刷新失败告警。**
> 修复完故障后，**第一件事是开启告警**：
> 语义模型 → 设置 → 计划刷新 → 勾选「**刷新失败时向我发送电子邮件通知**」。
>
> 否则下次还会是业务方先发现问题 —— 那会严重损害他们对报表的信任。

### 练习 5：设计权限方案（考：综合）

**题目**：客户有这些角色和权限需求，设计 RLS 方案。

| 角色 | 能看什么 |
|---|---|
| 华东销售员 A | 只看**自己**的客户订单 |
| 华东销售经理 B | 看**华东团队**所有销售员的订单 |
| 全国总监 C | 看**全部**数据 |
| 财务 D | 只看**已完成**订单（不看取消/退款） |

**答案与解析**：

**方案：一张映射表 + 两个 RLS 规则**

**映射表** `dim_user_scope`：

| user_email | scope_type | scope_value |
|---|---|---|
| a@company.com | 销售员 | S001 |
| b@company.com | 大区 | 华东 |
| c@company.com | 全部 | ALL |
| d@company.com | 全部 | ALL |

**本库缺一个字段**：`fact_order` 里没有 `sales_id`（销售员）。要支持"销售员"维度，需要在数据源里加这一列 —— **这是数据局限，需要跟客户 IT 提需求**。

**RLS 规则设计**：

| 需求 | 规则 |
|---|---|
| 销售员/大区/全国 | 用映射表 + `USERPRINCIPALNAME()`（动态 RLS） |
| 财务只看已完成 | 在 `fact_order` 表上加规则：`[status] = "已完成"` |

**财务角色的特殊处理**：

财务的需求是**行级过滤**（只看 status='已完成' 的行），这正好是 RLS 能做的：

```dax
-- 在 fact_order 表上
[status] = "已完成"
```

但要注意：**RLS 规则之间是"与"关系**，所以如果要同时限制地区和状态，两个规则会叠加。

**更灵活的做法**：把"可见状态"也放进映射表：

| user_email | scope_type | scope_value | visible_status |
|---|---|---|---|
| d@company.com | 全部 | ALL | 已完成 |

**给你的提醒**：

> 1. **RLS 只能过滤行，不能过滤列**。如果财务"不能看成本价"，RLS 做不到 —— 需要用**对象级安全（OLS）**（Premium 功能）或单独做一个不含成本字段的报表。
> 2. **权限需求要在建模前问清楚**。本例缺 `sales_id` 列，如果一开始就问到，可以让客户在数据里就带上，省去后面返工。
> 3. **"看全部"的人也要在映射表里登记**（scope_value = 'ALL'），否则他们会被 RLS 筛成空白。
