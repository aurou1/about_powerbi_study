# ch12 综合实战：交付《客户销售分析》报表 🎯

> 本章目标：把前 11 章串成一次**完整的端到端交付** —— 从需求澄清到验收。
> 这一章没有新知识点，考的是**怎么把知识组织成一次专业交付**。

---

## 一、本章学习目标

完成本章你应该能：

1. 用「需求澄清 5 问」把模糊需求变成明确口径
2. 先跑 SQL 基准，再建模、建度量值、做报表（**顺序不能反**）
3. 交付一份**三页报表**（总览 / 客户分层 / 品类毛利）
4. 用 SQL 对拍验证每一个关键数字
5. 写出一份能让客户签字的**交付文档**

---

## 二、第一步：需求澄清 5 问（最重要的一步）

**新手和老手最大的差距，往往不在技术，而在需求阶段。**

业务方说："我要一份销售分析报表。" —— 这句话信息量约等于零。

你必须问清这 5 件事：

| # | 问什么 | 为什么 | 本例答案 |
|---:|---|---|---|
| 1 | **谁看？** | 决定粒度和权限 | 销售总监 + 3 个大区经理 |
| 2 | **看什么？** | 决定指标和维度 | 销售额、利润、毛利率、客单价；按省、品类、客户、时间 |
| 3 | **多久更新？** | 决定刷新策略和网关 | 每天早 8 点 |
| 4 | **口径是什么？** | 决定度量值算法 | 销售额 = 已完成订单金额（不含取消/退款） |
| 5 | **权限怎么分？** | 决定 RLS | 大区经理只看自己大区 |

**把这 5 个答案写进邮件发给客户确认，拿到"对，就这样做"再动手。**

> **FDE 视角**：这 5 问能挡掉 80% 的返工。
> 我见过太多项目，做完报表才发现"哦我们销售额是含税的""哦取消单也要算进去" —— 然后整个模型推倒重来。
> **花 30 分钟问清楚，能省 3 天返工。**

### 2.1 口径确认的技巧：给数字，不给概念

❌ 错误问法："销售额要不要含取消订单？"（业务方不知道怎么答）

✅ 正确问法：

> "按**已完成订单**算，2024 年销售额是 **253.5 万**；如果**含取消和退款**，是 380 万左右。您系统里看的是哪个数？"

**给具体数字，业务方立刻能对上。**

## 三、第二步：SQL 先跑基准（顺序不能反）

**在打开 Power BI 之前，先用 SQL 把所有关键数字算出来。**

为什么？因为 SQL 是你的**独立验证工具**。如果先在 Power BI 里做，你会不自觉地"让数字看起来对" —— 而 SQL 不会迁就你。

### 3.1 本项目的 6 个基准数字

```sql
-- 基准 1：2024 年四大核心指标
SELECT
    COUNT(*) AS 有效订单数,
    ROUND(SUM(order_amount),2) AS 有效销售额,
    ROUND(SUM(order_profit),2) AS 有效利润,
    ROUND(SUM(order_profit)/SUM(order_amount)*100,2) AS 毛利率pct,
    ROUND(SUM(order_amount)/COUNT(*),2) AS 客单价
FROM fact_order
WHERE status='已完成' AND YEAR(order_date)=2024;
```

**预期结果**：

| 指标 | 值 |
|---|---:|
| 有效订单数 | **831** |
| 有效销售额 | **2,535,109.95** |
| 有效利润 | **585,867.19** |
| 毛利率 | **23.11%** |
| 客单价 | **3,050.67** |

**把这 5 个数字抄在纸上。** Power BI 里做出来必须一模一样。

```sql
-- 基准 2：2024 各省份（有效）
SELECT r.province_name AS 省,
       COUNT(*) AS 订单数,
       ROUND(SUM(o.order_amount),2) AS 销售额,
       ROUND(SUM(o.order_profit),2) AS 利润,
       ROUND(SUM(o.order_profit)/SUM(o.order_amount)*100,2) AS 毛利率pct
FROM fact_order o JOIN dim_region r ON o.region_id=r.region_id
WHERE o.status='已完成' AND YEAR(o.order_date)=2024
GROUP BY r.province_name ORDER BY 销售额 DESC;
```

```sql
-- 基准 3：2024 各品类（有效，用明细表）
SELECT p.category AS 品类,
       ROUND(SUM(i.line_amount),2) AS 销售额,
       ROUND(SUM(i.line_profit),2) AS 利润,
       ROUND(SUM(i.line_profit)/SUM(i.line_amount)*100,2) AS 毛利率pct
FROM fact_order_item i
JOIN dim_product p ON i.product_id=p.product_id
JOIN fact_order o ON i.order_id=o.order_id
WHERE o.status='已完成' AND YEAR(o.order_date)=2024
GROUP BY p.category ORDER BY 销售额 DESC;
```

```sql
-- 基准 4：2024 月度趋势（有效）
SELECT MONTH(order_date) AS 月,
       COUNT(*) AS 订单数,
       ROUND(SUM(order_amount),2) AS 销售额
FROM fact_order
WHERE status='已完成' AND YEAR(order_date)=2024
GROUP BY MONTH(order_date) ORDER BY 月;
```

**预期**：1月 238,217.59 → 6月 316,127.25 → 11月 323,919.78 → 12月 342,525.66（峰值）

```sql
-- 基准 5：2024 各客户等级（有效）
SELECT d.tier AS 等级,
       COUNT(DISTINCT o.order_id) AS 订单数,
       ROUND(SUM(o.order_amount),2) AS 销售额,
       ROUND(SUM(o.order_amount)/COUNT(DISTINCT o.order_id),2) AS 客单价
FROM fact_order o JOIN dim_customer d ON o.customer_id=d.customer_id
WHERE o.status='已完成' AND YEAR(o.order_date)=2024
GROUP BY d.tier ORDER BY 销售额 DESC;
```

```sql
-- 基准 6：2024 TOP10 客户（有效）
SELECT d.customer_name AS 客户, d.tier AS 等级,
       COUNT(DISTINCT o.order_id) AS 订单数,
       ROUND(SUM(o.order_amount),2) AS 销售额
FROM fact_order o JOIN dim_customer d ON o.customer_id=d.customer_id
WHERE o.status='已完成' AND YEAR(o.order_date)=2024
GROUP BY d.customer_id, d.customer_name, d.tier
ORDER BY 销售额 DESC LIMIT 10;
```

## 五、第四步：度量值体系

按 ch04 + ch06 + ch07 + ch08 建的度量值，本项目需要这些：

### 5.1 基础层

```dax
有效销售额 = CALCULATE(SUM('fact_order_item'[line_amount]), 'fact_order'[status] = "已完成")
有效利润   = CALCULATE(SUM('fact_order_item'[line_profit]), 'fact_order'[status] = "已完成")
有效订单数 = CALCULATE(DISTINCTCOUNT('fact_order'[order_id]), 'fact_order'[status] = "已完成")
有效销量   = CALCULATE(SUM('fact_order_item'[quantity]), 'fact_order'[status] = "已完成")
```

### 5.2 效率层

```dax
客单价   = DIVIDE([有效销售额], [有效订单数])
毛利率   = DIVIDE([有效利润], [有效销售额])
单件利润 = DIVIDE([有效利润], [有效销量])
```

### 5.3 时间智能层

```dax
销售额YTD      = CALCULATE([有效销售额], DATESYTD('dim_date'[date_key]))
销售额_去年同期 = CALCULATE([有效销售额], SAMEPERIODLASTYEAR('dim_date'[date_key]))
销售额同比% =
VAR 今年 = [有效销售额]
VAR 去年 = [销售额_去年同期]
RETURN DIVIDE(今年 - 去年, 去年)

销售额_上月   = CALCULATE([有效销售额], DATEADD('dim_date'[date_key], -1, MONTH))
销售额环比% =
VAR 本月 = [有效销售额]
VAR 上月 = [销售额_上月]
RETURN DIVIDE(本月 - 上月, 上月)
```

### 5.4 排名与占比层

```dax
省份排名 = RANKX(ALL('dim_region'[province_name]), [有效销售额], , DESC, DENSE)

省份占比_ALL = DIVIDE([有效销售额], CALCULATE([有效销售额], ALL('dim_region')))

省份占比_所选 =
DIVIDE([有效销售额], CALCULATE([有效销售额], ALLSELECTED('dim_region')))

客户排名 = RANKX(ALL('dim_customer'[customer_name]), [有效销售额], , DESC, DENSE)
```

## 六、第五步：三页报表

### 6.1 页面 1：销售总览

```
┌──────────────────────────────────────────────┐
│  客户销售分析看板        数据截止：2025-12-31 │
│  [年份:2023|2024|2025]  [大区▾]  [品类▾]      │
├────────┬────────┬────────┬───────────────────┤
│ 销售额  │ 利润   │ 毛利率  │ 客单价             │
│253.5万 │ 58.6万 │ 23.11% │ 3,050.67           │
├─────────────────────┬────────────────────────┤
│  月度趋势 + 同比折线   │  各省销售额条形（降序） │
├─────────────────────┼────────────────────────┤
│  省份排名矩阵（含占比） │  TOP10 客户条形        │
└─────────────────────┴────────────────────────┘
```

**关键设置**：

- 4 个 KPI 卡片 → 交互设为「**无**」（不被图表点击影响）
- 月度折线：轴 = `dim_date[month]`，值 = `[有效销售额]`，图例 = `dim_date[year]`
- 各省条形：轴 = `province_name`，值 = `[有效销售额]`，按值降序
- 省份矩阵：行 = `province_name`，值 = 销售额 / 排名 / 占比
- TOP10：轴 = `customer_name`，前 N 筛选 = 10

### 6.2 页面 2：客户分层

```
┌──────────────────────────────────────────────┐
│  客户分层分析                                  │
├──────────────────┬───────────────────────────┤
│ 等级 × 销售额矩阵  │  等级分布饼图（4 类）      │
│ 普通/银卡/金卡/钻石 │                           │
├──────────────────┼───────────────────────────┤
│  客户散点图        │  等级客单价对比            │
│  X=订单数 Y=销售额 │                           │
├──────────────────┴───────────────────────────┤
│  TOP 20 客户明细表（含排名、等级、客单价）       │
└──────────────────────────────────────────────┘
```

**本页要传达的洞察**（用真实数据）：

| 等级 | 人数 | 订单数 | 有效销售额 | 客单价 |
|---|---:|---:|---:|---:|
| 普通 | 241 | 637 | 2,029,219.58 | 3,185.59 |
| 银卡 | 149 | 610 | 1,920,208.56 | 3,147.88 |
| 金卡 | 83 | 653 | 1,952,447.38 | 2,989.97 |
| 钻石 | 27 | 466 | 1,293,617.21 | 2,776.00 |

**三个反直觉的发现**：

1. **钻石客户客单价最低（2,776.00）** —— 因为折扣率最高（20%）
2. **27 个钻石客户贡献 129 万**（占 18.0%），人均贡献是普通客户的 **17.7 倍**（1,293,617.21÷27 vs 2,029,219.58÷241）
3. **普通客户虽然人多（241），订单却只有 637 单** —— 人均 2.6 单，而钻石客户人均 17.3 单

> 这些洞察不是"数据"，是**能驱动决策的结论**。做报表要敢于把它们写在页面上（用文本框标注）。

### 6.3 页面 3：品类毛利

```
┌──────────────────────────────────────────────┐
│  品类盈利分析                                  │
├──────────────────────────────────────────────┤
│  品类矩阵：销售额 | 利润 | 毛利率（色阶）| 占比 │
├────────────────────┬─────────────────────────┤
│  销售额 vs 毛利率散点 │  品类月度趋势（多选）    │
├────────────────────┼─────────────────────────┤
│  TOP10 商品（按利润） │  亏损订单占比卡片       │
└────────────────────┴─────────────────────────┘
```

**本页要传达的核心洞察**（这是整个项目最有价值的一页）：

| 品类 | 销售额 | 利润 | 毛利率 |
|---|---:|---:|---:|
| 数码 | **2,612,383.09**（最高） | **30,291.28**（最低） | **1.16%** |
| 美妆 | 1,381,720.47 | **683,559.33**（最高） | **49.47%** |

**结论**：

> **数码品类占了 36.3% 的销售额，却只贡献 1.8% 的利润（30,291.28 ÷ 1,706,864.78）。**
> **美妆品类销售额只有数码的一半，利润却是数码的 22.6 倍。**

**散点图的威力**：X 轴 = 销售额，Y 轴 = 毛利率，气泡大小 = 利润。

你会看到数码在**右下角**（高销售额、低毛利率），美妆在**左上角** —— 一眼看出"规模大 ≠ 赚钱"。

**建议动作**（写在页面上）：

1. 数码品类的定价/折扣策略需要检讨（20% 的钻石折扣在 12% 吊牌毛利下必然亏损）
2. 有效订单中有 **489 行（8.6%）是亏损的**，最低毛利率 -14.29%
3. 考虑对低毛利品类设置折扣上限

## 八、第七步：交付文档

**这是很多人会跳过、但客户最看重的一步。**

### 8.1 交付文档模板

```markdown
# 《客户销售分析报表》交付说明

## 一、报表访问
- 链接：[Power BI App 链接]
- 权限：需安装 App 后可见（已为 XX 人开通）
- 数据截止：2025-12-31

## 二、数据口径（重要）
| 指标 | 定义 | 说明 |
|---|---|---|
| 有效销售额 | status='已完成' 的订单金额合计 | **不含已取消、退款订单** |
| 有效利润 | 同上订单的利润合计 | |
| 毛利率 | 有效利润 ÷ 有效销售额 | **加权口径**，非各单平均 |
| 客单价 | 有效销售额 ÷ 有效订单数 | |

**注意**：报表中的"销售额"均指有效销售额。全部订单（含取消退款）
金额为 10,689,549.70，有效销售额为 7,195,492.73，请勿混淆。

## 三、数据更新
- 刷新时间：每日 08:00（自动）
- 刷新耗时：约 X 分钟
- 数据源：MySQL study_powerbi_demodata（经公司数据网关）
- 失败告警：已配置，失败时通知 XXX@company.com

## 四、已知限制
1. 数据范围：2023-01-01 ~ 2025-12-31，日期表覆盖至 2025-12-31
2. 无跨省下单场景（客户所属省 = 订单收货省）
3. 商品价格固定，无随时间变化的价格历史
4. 无库存、渠道、退货数据

## 五、联系人
- 报表开发：XXX
- 业务答疑：XXX
```

### 8.2 交付文档的三个要素

| 要素 | 为什么重要 |
|---|---|
| **口径定义** | 三个月后有人问"这个数怎么算的"，有据可查 |
| **已知限制** | 提前说明，避免被当成 bug |
| **数据截止时间** | 让用户知道数据新鲜度 |

> **FDE 视角**：**交付文档就是你的免责声明。**
> 我见过太多纠纷："报表数字不对" → "是按确认过的口径算的" → "我没确认过" → 扯皮。
> 有了文档和确认邮件，这类问题五分钟就能解决。

## 九、完整交付流程回顾

```
① 需求澄清 5 问 ──▶ 邮件确认（留下证据）
        ↓
② SQL 跑基准 6 组数字 ──▶ 抄在纸上
        ↓

        ↓

        ↓
⑤ 三页报表：总览 / 客户分层 / 品类毛利
        ↓
⑥ 对拍验证：10 项数字逐一核对
        ↓
⑦ 发布：Service + 网关 + 计划刷新 + RLS
        ↓
⑧ 交付文档：口径 / 刷新 / 限制 / 联系人
        ↓
⑨ 验收：陪业务方走一遍，记录反馈
```

**每一步都不能跳。** 特别是 ②（SQL 基准）和 ⑥（对拍）—— 它们是"数字正确"的唯一保障。

## 十一、练习题

### 练习 1：独立完成 SQL 基准（考：实战第一步）

**题目**：不看答案，写出 2024 年的 5 个核心指标的 SQL，并跑出结果。

**答案**：

```sql
SELECT COUNT(*) AS 有效订单数,
       ROUND(SUM(order_amount),2) AS 有效销售额,
       ROUND(SUM(order_profit),2) AS 有效利润,
       ROUND(SUM(order_profit)/SUM(order_amount)*100,2) AS 毛利率pct,
       ROUND(SUM(order_amount)/COUNT(*),2) AS 客单价
FROM fact_order
WHERE status='已完成' AND YEAR(order_date)=2024;
```

**预期结果**：

| 指标 | 值 |
|---|---:|
| 有效订单数 | **831** |
| 有效销售额 | **2,535,109.95** |
| 有效利润 | **585,867.19** |
| 毛利率 | **23.11%** |
| 客单价 | **3,050.67** |

**三个易错点**：

| 错误 | 后果 |
|---|---|
| 忘了 `status='已完成'` | 销售额变成约 380 万（虚高 50%） |
| 客单价 JOIN 了明细表 | 变成 9,192.99（虚高 3 倍，见 ch04 第 9 节） |
| 毛利率用 `AVG(毛利率列)` | 变成 28.41% 而非 23.72%（见 ch05） |

### 练习 2：发现并验证核心洞察（考：从数据到结论）

**题目**：从品类数据里找出"最值得向业务方汇报的一条结论"，并用数字支撑它。

**答案**：

**结论**：**数码品类是"规模陷阱" —— 占三分之一销售额，却几乎不赚钱。**

**支撑数字**：

| 指标 | 数值 |
|---|---:|
| 数码销售额 | 2,612,383.09 |
| 数码占全网销售额比 | **36.31%** |
| 数码利润 | 30,291.28 |
| 数码占总利润比 | **1.78%**（30,291.28 ÷ 1,706,864.78） |
| 数码毛利率 | **1.16%** |
| 美妆毛利率（对比） | **49.47%** |
| 美妆利润（对比） | 683,559.33（数码的 **22.6 倍**） |

**验证 SQL**：

```sql
SELECT p.category AS 品类,
       ROUND(SUM(i.line_amount),2) AS 销售额,
       ROUND(SUM(i.line_amount)*100/(SELECT SUM(i2.line_amount)
             FROM fact_order_item i2 JOIN fact_order o2 ON i2.order_id=o2.order_id
             WHERE o2.status='已完成'),2) AS 销售额占比pct,
       ROUND(SUM(i.line_profit),2) AS 利润,
       ROUND(SUM(i.line_profit)*100/(SELECT SUM(i3.line_profit)
             FROM fact_order_item i3 JOIN fact_order o3 ON i3.order_id=o3.order_id
             WHERE o3.status='已完成'),2) AS 利润占比pct,
       ROUND(SUM(i.line_profit)/SUM(i.line_amount)*100,2) AS 毛利率pct
FROM fact_order_item i
JOIN dim_product p ON i.product_id=p.product_id
JOIN fact_order o ON i.order_id=o.order_id
WHERE o.status='已完成'
GROUP BY p.category ORDER BY 销售额 DESC;
```

**为什么会这样？（根因分析）**

| 因素 | 数值 |
|---|---|
| 数码吊牌毛利率 | 12.00%（5 个品类里最低） |
| 钻石客户折扣 | 20%（最高） |
| 随机抖动 | ±3% |
| **最坏情况** | 12% - 20% - 3% = **-11%（亏损）** |

实证：有效订单中有 **489 行（8.6%）利润为负**，最低毛利率 **-14.29%**。

**给业务方的建议**：

> 对数码品类设置折扣上限（建议 ≤8%），或提高数码的定价毛利空间。
> 按当前结构，数码卖得越多，摊薄的整体毛利率越严重。

> **FDE 视角**：这才是报表该产出的东西。
> "2024 年销售额 253 万"是**数据**；
> "数码品类占了 36% 销售额却只贡献 1.8% 利润，建议限制折扣"是**洞察**。
> **客户为洞察付钱，不为数据付钱。**

### 练习 3：写交付文档的口径段（考：文档能力）

**题目**：写一段"数据口径"说明，让业务方三个月后还能看懂。

**参考答案**：

```markdown
## 数据口径

| 指标 | 计算公式 | 说明 |
|---|---|---|
| 有效销售额 | SUM(line_amount) WHERE status='已完成' | 不含已取消、已退款订单 |
| 有效利润 | SUM(line_profit) WHERE status='已完成' | 同上 |
| 毛利率 | 有效利润 ÷ 有效销售额 | **加权口径**（总利润÷总销售额），
                                        非各订单毛利率的平均 |
| 客单价 | 有效销售额 ÷ 有效订单数 | 分母为订单数，非商品行数 |
| 订单数 | COUNT(DISTINCT order_id) | 一单一行，不重复计 |

### 常见混淆

- 全部订单金额（含取消/退款）：10,689,549.70
- **有效订单金额（报表口径）：7,195,492.73**
- 两者相差 3,494,056.97（约 47%）

若与业务系统数字不一致，请先确认对方使用的是哪一种口径。
```

**好文档的三个特征**：

1. **给出公式**（不是"销售额"三个字）
2. **预先列出容易混淆的地方**（含数字对比）
3. **给出排查指引**（"如果不一致，先确认口径"）

> **这一步的价值**：三个月后业务方质疑数字时，你只需把文档发过去，不用重新解释一遍。

### 练习 4：设计验收流程（考：交付闭环）

**题目**：报表做完了，怎么组织验收？

**答案**：

**验收三步法**：

**① 自测（交付前）**

- 10 项数字对拍（本章第 7 节）
- 用 RLS 身份测试每个角色
- 检查所有切片器、按钮、钻取是否正常
- 在**手机端**打开看一眼（移动端布局）

**② 演示（陪业务方走一遍）**

不要只发链接，要**约 30 分钟会议**，当着业务方的面：

| 步骤 | 做什么 |
|---|---|
| 1 | 打开报表，让他自己点（观察他的第一反应） |
| 2 | 问他"你想看的第一个数字是什么"，现场找给他看 |
| 3 | 演示核心洞察（数码毛利那段） |
| 4 | 演示筛选、下钻、导出 |
| 5 | **当场问："这个数跟你系统里对得上吗？"** |

> 第 5 步最关键 —— **让业务方当场对数字**。如果当场对不上，你立刻能改；如果等他事后发现，就变成"你报表有问题"的投诉。

**③ 收集反馈并迭代**

准备一个反馈表：

| # | 反馈 | 类型 | 处理 |
|---:|---|---|---|
| 1 | "能不能加个去年对比？" | 新需求 | 评估工作量 |
| 2 | "这个数跟我们系统差 2 万" | 口径问题 | **优先处理** |
| 3 | "图表颜色不好看" | 视觉 | 低优先级 |

**区分"口径问题"和"新需求"**：

- **口径问题 → 立刻改**（这直接影响信任）
- **新需求 → 排期**（可以放到二期）

### 练习 5：复盘整个项目（考：全局思维）

**题目**：回顾 ch01-ch12，说出每个阶段最容易犯的一个错误，以及怎么避免。

**答案**：

| 章 | 最容易犯的错 | 怎么避免 |
|---:|---|---|
| ch01 导入 | 导入后**不数行数** | 6 张表行数必须核对：10/200/500/1096/3529/8445 |
| ch02 建模 | **忘记标记日期表** | 建模后立刻标记，并看到日历图标 |
| ch03 清洗 | **折叠断裂不自知** | 每步右键看"查看本机查询" |
| ch04 度量值 | **同时求和两张表金额** | 隐藏原始金额列，只用度量值 |
| ch05 上下文 | **对比率列求平均** | 率一律 `SUM(分子)/SUM(分母)` |
| ch06 CALCULATE | **RANKX 忘记 ALL** | 第一参数必须 `ALL(列)` |
| ch07 迭代 | **`FILTER` 整张事实表** | 用布尔筛选或 `FILTER(维度表)` |
| ch08 时间智能 | **日期表没覆盖到未来** | 上线前延长到明年年底 |
| ch09 可视化 | **KPI 卡片被图表点击影响** | 交互设为"无" |
| ch10 性能 | **开自动日期/时间** | 建模初期就关掉 |
| ch11 发布 | **发布后不配凭据** | 发布后立刻配数据源凭据 + 网关 |
| ch12 交付 | **不做 SQL 对拍** | 先跑 SQL 基准，交付前 10 项核对 |

**贯穿始终的三条铁律**：

1. **数字必须能独立验证**（SQL 对拍）
2. **口径必须写下来**（交付文档）
3. **先问清楚再做**（需求 5 问）

> **最后一句**：
> Power BI 的工具技能，两三周能学会。
> **但"让数字可信"的能力，需要刻意练习** —— 而这才是客户真正付费的东西。
