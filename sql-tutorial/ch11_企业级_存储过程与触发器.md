# ch11 企业级：存储过程与触发器 🏭

> 本章目标：把「月报逻辑」封装成存储过程一键调用，用触发器自动留审计痕迹。
> 学完你能把重复 SQL 存进数据库复用，并让关键改动「自动留痕」。

## 一、本章学习目标

1. 用 `CREATE PROCEDURE` 写带参数的**存储过程**，`CALL` 调用
2. 用 `CREATE TRIGGER` 在表发生改动时**自动执行**一段逻辑（审计）
3. 理解存储过程 / 触发器的适用场景与风险
4. 会清理：`DROP PROCEDURE` / `DROP TRIGGER`
5. 锁定：月报过程 `sp_monthly_sales(2024)` 返回 12 行（12 月 342,525.66 / 113 单）；触发器把状态变更写进审计表

## 二、为什么要学存储过程和触发器

前 10 章的 SQL 都是「你手动敲、跑完即丢」。但企业里有两类需求适合**存进数据库**：

- **重复逻辑**：每月跑一次月报、每天算一次库存。与其每次手写，不如封装成存储过程，`CALL` 一下就出
- **强制留痕**：订单状态一改，必须自动记一笔「谁、从什么改成什么」。靠人记得写审计 SQL 不靠谱，用触发器**自动**做

> ⚠️ **风险提示**：存储过程 / 触发器是「库里的逻辑」，藏在数据库里、不透明。生产环境滥用会让排错变难（你改一行，不知道哪个触发器偷偷跑了）。FDE 现场：**能放应用层（Python/报表）的逻辑，优先放应用层；只有「必须复用」或「必须强制」的才进库**。

---

## 三、概念：存储过程

存储过程 = 一段**存进数据库的命名 SQL**，可带输入参数，用 `CALL` 执行。

```sql
DELIMITER $$                      -- 临时改语句结束符，避免过程体内的 ; 提前结束
CREATE PROCEDURE 名字(IN 参数 类型)
BEGIN
  ...SQL...
END $$
DELIMITER ;                       -- 改回 ;
```

调用：`CALL 名字(参数值);`

## 四、实操：月报存储过程

### 4.1 定义 `sp_monthly_sales`

```sql
DELIMITER $$
CREATE PROCEDURE sp_monthly_sales(IN p_year INT)
BEGIN
  SELECT d.month,
         ROUND(SUM(oi.line_amount),2)                    AS 月销售额,
         COUNT(DISTINCT o.order_id)                      AS 订单数
  FROM fact_order o
  JOIN fact_order_item oi ON o.order_id = oi.order_id
  JOIN dim_date d       ON o.order_date = d.date_key
  WHERE o.status = '已完成' AND d.year = p_year
  GROUP BY d.month
  ORDER BY d.month;
END $$
DELIMITER ;
```

### 4.2 调用（2024 年）

```sql
CALL sp_monthly_sales(2024);
```

**预期结果（12 行）**：

| 月 | 月销售额 | 订单数 |
|---|---:|---:|
| 1 | 238,217.59 | 76 |
| 2 | 176,572.22 | 53 |
| 3 | 151,444.50 | 41 |
| 4 | 164,071.45 | 57 |
| 5 | 172,763.94 | 64 |
| 6 | 316,127.25 | 107 |
| 7 | 160,830.68 | 49 |
| 8 | 175,090.40 | 60 |
| 9 | 171,828.80 | 62 |
| 10 | 141,717.68 | 42 |
| 11 | 323,919.78 | 107 |
| 12 | 342,525.66 | 113 |

> 想看 2025 年？`CALL sp_monthly_sales(2025);` 同理——参数化让一份逻辑服务任意年份。

### 4.3 清理

```sql
DROP PROCEDURE IF EXISTS sp_monthly_sales;
```

## 五、实操：审计触发器

### 5.1 建审计表 + 触发器

```sql
CREATE TABLE order_audit (
  audit_id    INT AUTO_INCREMENT PRIMARY KEY,
  order_id    INT,
  old_status  VARCHAR(10),
  new_status  VARCHAR(10),
  changed_at  DATETIME DEFAULT CURRENT_TIMESTAMP
);

DELIMITER $$
CREATE TRIGGER trg_order_status
AFTER UPDATE ON fact_order
FOR EACH ROW
BEGIN
  IF OLD.status <> NEW.status THEN
    INSERT INTO order_audit(order_id, old_status, new_status)
    VALUES (OLD.order_id, OLD.status, NEW.status);
  END IF;
END $$
DELIMITER ;
```

**触发器逻辑**：每当 `fact_order` 被 UPDATE，若 `status` 变了，自动往 `order_audit` 插一行「旧值 → 新值」。

### 5.2 验证：改状态，触发器自动留痕

```sql
UPDATE fact_order SET status = '退款' WHERE order_id = 1;
SELECT * FROM order_audit;
-- 预期：1 行 → (audit_id=1, order_id=1, old_status='已完成', new_status='退款', changed_at=当前时间)

UPDATE fact_order SET status = '已完成' WHERE order_id = 1;   -- 改回，保持库干净
SELECT * FROM order_audit;
-- 预期：又多 1 行（已完成 → 退款 的反向）

DROP TRIGGER IF EXISTS trg_order_status;
DROP TABLE IF EXISTS order_audit;                            -- 收尾清理
```

**验证结果**：每次状态变更，审计表自动多一行，记录「从什么到什么」。这就是企业里「谁改了订单、改成了啥」的强制证据链。

## 六、FDE 现场场景：合规要求「所有状态变更必须留痕」

客户（尤其金融/医疗）合规部门要求：**任何订单状态改动都要可审计**。你用触发器一次性满足——以后无论谁、无论什么客户端改状态，审计行自动生成，没人能绕过。比「每次记得手写审计 SQL」可靠一百倍。

> **核心心法**：触发器适合「强制、隐形、与业务无关」的副作用（审计、时间戳、校验）；不适合放核心业务逻辑（那样排错时你找不到逻辑在哪）。

## 七、本章小结

| 你学到了 | 关键点 |
|---|---|
| 存储过程 | `CREATE PROCEDURE ... (IN p 类型) BEGIN...END`，`CALL` 调用，参数化复用 |
| 月报过程 | `sp_monthly_sales(2024)` → 12 行（12 月 342,525.66 / 113 单） |
| 触发器 | `CREATE TRIGGER ... AFTER UPDATE` 自动执行；`OLD./NEW.` 取改前改后 |
| 审计 | 状态变更自动写 `order_audit`（order_id + 旧/新状态 + 时间） |
| 清理 | `DROP PROCEDURE` / `DROP TRIGGER`（演示完不留痕） |
| 风险 | 库内逻辑不透明，能放应用层就别进库 |

## 八、练习题

### 练习 1：调用月报过程（考：CALL）

**题目**：`CALL sp_monthly_sales(2024);` 返回几行？12 月数字？

**预期结果**：**12 行**；12 月 月销售额 **342,525.66** / 订单数 **113**。

**解析**：参数化过程一份逻辑服务任意年份，避免重复手写月报 SQL。

---

### 练习 2：参数化复用（考：IN 参数）

**题目**：用同一份过程查 2025 年月报，该怎么写？

**预期结果**：`CALL sp_monthly_sales(2025);`（返回 2025 年 12 行）。

**解析**：`p_year` 入参让逻辑按年切换，无需改过程体。

---

### 练习 3：触发器审计（考：自动留痕）

**题目**：把 `order_id=1` 状态改成「退款」，看审计表。

**预期结果**：`order_audit` 增加 1 行：`order_id=1, old='已完成', new='退款'`。

**解析**：`AFTER UPDATE` 触发器检测到 `OLD.status <> NEW.status`，自动插审计行。

---

### 练习 4：存储过程 vs 应用层（考：选型，概念题）

**题目**：月报逻辑放存储过程还是放 Python 脚本？

**预期答案**：两者都行。重复、稳定、需数据库权限的 → 存储过程；要灵活编排、易调试、和报表联动的 → 应用层。**FDE 经验：能放应用层优先放应用层**，库内逻辑不透明、难排错。

**解析**：见第二节风险提示。

---

### 练习 5：清理对象（考：不留痕）

**题目**：演示完怎么清理过程和触发器？

**预期结果**：`DROP PROCEDURE IF EXISTS sp_monthly_sales;` 和 `DROP TRIGGER IF EXISTS trg_order_status;`（触发器若建了审计表，再 `DROP TABLE order_audit;`）。

**解析**：演示库是固定种子，练完必须清理，否则破坏可复现前提。
