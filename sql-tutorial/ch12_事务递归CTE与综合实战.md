## 二、事务：原子性的最后一道闸

ch09 学过事务基本三命令。这里强调**原子性**——一次业务动作往往要改多处，必须「全成功或全回滚」：

```sql
BEGIN;
UPDATE fact_order SET status = '退款' WHERE order_id = 1;   -- 步骤1
UPDATE fact_order SET status = '退款' WHERE order_id = 2;   -- 步骤2
-- 若步骤2 报错（如外键/约束），执行：
ROLLBACK;          -- 步骤1 也一起撤销，库回到 BEGIN 前
-- 若都成功：
COMMIT;
```

**原子性**：步骤 1、2 是一个整体。任一步失败，`ROLLBACK` 让两步都不生效——不会出现「只改了一半」的中间状态。ch09 已实测：插入客户 500→501 后 `ROLLBACK` → 500，库不变。

> 真实场景：转账 = 「A 减钱 + B 加钱」两步。没有事务，A 减了 B 没加，钱就丢了。事务是金融/库存系统的命根子。

### 🔍 原理深挖 1：ACID 四性——事务的四个承诺

```
原子性 Atomicity    → 全做或全不做(Rollback 实现)
一致性 Consistency  → 事务前后数据都满足业务规则(余额不为负…由约束+代码保证)
隔离性 Isolation    → 两个并发事务互不干扰(靠锁+MVCC, 见下)
持久性 Durability   → COMMIT 后数据不丢(靠 redo log: 先写日志再落盘)
```

### 🔍 原理深挖 2：并发事务会出哪些乱子？（脏读/不可重复读/幻读）

两个事务同时跑，若毫无隔离会互相看到"不该看"的中间状态：

```
脏读     事务A 改了数据还没 COMMIT，事务B 读到了 → A 回滚, B 读到废数据
不可重复读 事务A 两次读同一行, 中间被事务B UPDATE+COMMIT → 两次结果不同
幻读     事务A 按条件查了 N 行, 事务B 插了 1 行新数据满足条件并 COMMIT
         → A 再查变 N+1 行, 多出来的行像"幻觉"

图形（脏读）:
事务A: BEGIN → UPDATE 余额 100→50 (未提交)
事务B:                    SELECT 余额 → 50  ← 读到没提交的!
事务A: ROLLBACK → 余额回到 100
  → B 刚才拿 50 做的决策 = 基于不存在的中间态
```

### 🔍 原理深挖 3：四种隔离级别（背下来）

隔离级别 = 允许哪种乱子出现。**级别越高越安全，但并发性能越差**：

```
隔离级别                    脏读  不可重复读  幻读
─────────────────────────────────────────────
READ UNCOMMITTED(读未提交)  可能  可能      可能    ← 几乎不用
READ COMMITTED(读已提交)    不会  可能      可能    ← Oracle默认
REPEATABLE READ(可重复读)   不会  不会      可能*   ← ★MySQL默认
SERIALIZABLE(串行化)        不会  不会      不会    ← 最安全最慢
* 注意: InnoDB 在 RR 级别用"间隙锁"把幻读也基本挡住了
```

```sql
-- 查看/设置当前会话隔离级别
SELECT @@transaction_isolation;              -- 默认 REPEATABLE-READ
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
```

### 🔍 原理深挖 4：MVCC——为什么 SELECT 不阻塞写入

`REPEATABLE READ` 下，InnoDB 靠 **MVCC（多版本并发控制）** 让「读」和「写」互不阻塞：

```
原理: 每一行存多个历史版本(带事务版本号), 每个事务看到的是
      "自己开始那一刻的快照"

图形:
时间线:  t1(事务A: 读, 快照@t1)   t2(事务B: UPDATE余额 100→50, COMMIT)
A 在 t1 之后每次 SELECT 余额 → 仍看到 100（自己快照里的旧版本）
B 提交的新版本(50) → A 看不到, 要等 A 结束才开始新快照

→ 这就是"可重复读"的实现: A 两次读一致, 因为都读快照, 不看 B 的改动
→ 脏读/不可重复读被 MVCC 天然挡掉; 幻读靠间隙锁补刀
```

> 本库默认 `REPEATABLE READ`——这也是为什么你一个长事务里多次 `SELECT SUM` 结果稳定（读的是同一快照）。生产里若不在乎"同一事务内两次读必须一致"（如纯报表），可降 `READ COMMITTED` 换更高并发——但默认别乱动。

### 🔍 原理深挖 5：锁——写与写怎么互斥

```
MVCC 管"读读不阻塞、读写不阻塞", 但两个事务同时"写同一行"必须排队:

共享锁 S(读锁): 多个事务可同时持 S 锁读同一行
排他锁 X(写锁): 只有一个事务能持 X 锁写, 其它读写都等

UPDATE 某行 → 自动加 X 锁 → 另一个事务 UPDATE 同一行 → 阻塞等待 → 直到 COMMIT

死锁: A 锁了行1 等行2; B 锁了行2 等行1 → 互相等 → MySQL 检测到自动回滚一方:
  ERROR 1213: Deadlock found when trying to get lock
生产预防: 多个事务按"同一顺序"操作行(先1后2), 死锁就很少发生
```

## 三、递归 CTE：算「2025 年有多少天没开单」

### 3.1 为什么需要递归

本库 `dim_date` 只有到 2025-12-31。但「2025 年每天是否开单」要**生成 365 个连续日期**再逐个判断——这正好用**递归 CTE**（`WITH RECURSIVE`）造一个日期序列。

### 3.2 语法与原理

```sql
WITH RECURSIVE 日期序列(dt) AS (
  SELECT '2025-01-01'                       -- 锚点（起始行）
  UNION ALL
  SELECT dt + INTERVAL 1 DAY               -- 递归（在上一行基础上 +1 天）
  FROM 日期序列
  WHERE dt < '2025-12-31'                   -- 递归终止条件
)
SELECT COUNT(*)                                              AS 总天数,
       SUM(CASE WHEN dt NOT IN (
              SELECT DISTINCT order_date FROM fact_order
              WHERE order_date BETWEEN '2025-01-01' AND '2025-12-31'
         ) THEN 1 ELSE 0 END)                                AS 无订单天数
FROM 日期序列;
```

**执行过程**：

1. **锚点**：先放一行 `2025-01-01`
2. **递归**：不断「上一行 +1 天」，直到 `dt < '2025-12-31'` 不满足（即到 12-31 为止）
3. 最终得到 **365 行**连续日期

### 3.3 验证结果

**预期结果**：`总天数 = 365`，`无订单天数 = 24`。

即 2025 年 365 天里，**有订单的天数 = 341**（也等于 `SELECT COUNT(DISTINCT order_date) FROM fact_order WHERE order_date BETWEEN '2025-01-01' AND '2025-12-31'` 的 341），**零开单 24 天**。这 24 天就是运营该补量、该做活动的空白期。

> ⚠️ **递归 CTE 必须有终止条件**（`WHERE dt < ...`），否则无限递归把库跑挂。

## 四、★ 综合实战：客户价值分析（可交付报表）

把全教程技能组合：有效客户消费汇总 → 全国排名 → 消费分四档 → 顶部展示，并与基准对拍。

```sql
WITH 客户消费 AS (
  SELECT c.customer_id, c.customer_name, c.tier,
         ROUND(SUM(oi.line_amount),2) AS 消费额
  FROM fact_order o
  JOIN fact_order_item oi ON o.order_id = oi.order_id
  JOIN dim_customer   c  ON o.customer_id = c.customer_id
  WHERE o.status = '已完成'
  GROUP BY c.customer_id
),
客户分层 AS (
  SELECT *,
         RANK()   OVER (ORDER BY 消费额 DESC)              AS 全国排名,
         NTILE(4) OVER (ORDER BY 消费额 DESC)             AS 消费档位
  FROM 客户消费
)
SELECT 客户排名, 消费档位, customer_name, tier, 消费额
FROM 客户分层
ORDER BY 全国排名
LIMIT 5;
```

**预期结果（TOP5）**：

| 全国排名 | 消费档位 | 客户 | 等级 | 消费额 |
|---:|---:|---|---|---:|
| 1 | 1 | 梁诗 | 钻石 | 70,022.89 |
| 2 | 1 | 唐宇伟 | 钻石 | 67,890.55 |
| 3 | 1 | 马晨博 | 钻石 | 66,012.90 |
| 4 | 1 | 吴涛 | 钻石 | 65,767.42 |
| 5 | 1 | 彭艳鑫 | 钻石 | 61,699.01 |

**对拍基准**（任何拆分汇总都应回归这两个数，否则算错了）：

```sql
SELECT ROUND(SUM(oi.line_profit)/SUM(oi.line_amount)*100,2) AS 整体毛利率,
       ROUND(SUM(oi.line_profit)/SUM(oi.quantity),2)        AS 单件利润,
       ROUND(SUM(oi.line_amount),2)                         AS 有效销售额
FROM fact_order_item oi JOIN fact_order o ON oi.order_id=o.order_id
WHERE o.status='已完成';
-- 预期：毛利率 23.72% | 单件利润 197.87 | 有效销售额 7,195,492.73
```

> **交付心法**：综合报表 = CTE 分层（清晰）+ 窗口函数（排名/分档）+ 基准对拍（可信）。TOP5 客户全是钻石，消费档位 1 组——和 ch06/ch07 结论一致，说明这份综合结果没翻车。

客户一句话需求：「帮我看看最有价值的客户，还有今年哪些天没开单。」

这就是一个 FDE 从「听到需求」到「交付可信任报表」的完整链路。
