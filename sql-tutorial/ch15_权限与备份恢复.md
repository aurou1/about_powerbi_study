# ch15 用户、权限与备份恢复

> 学习目标：从"单机 root 随便跑"走向"生产规矩"——**最小权限原则**：给报表/ETL/同事建不同账号，各管一摊；再学会用 `mysqldump` 备份、恢复、验证——这是 FDE 给客户交付后最常被问的两件事：「报表账号怎么开」「库能不能备份」。

---

## 一、为什么不能永远用 root

```
root = 超级管理员, 能删任何库任何表 —— 真实业务里灾难的源头:

场景1: 你给客户演示连的是 root → 手滑 UPDATE 忘加 WHERE → 全表状态改错
场景2: 同事离职, 他用的 root 密码还在到处传 → 谁也拦不住
场景3: 审计问"谁改过这张表" → 都是 root, 查不出来

生产铁律（最小权限原则）:
  给每个"使用场景"开独立账号, 只给够用的权限
  ├─ 报表/只读   → SELECT only (report_ro)
  ├─ ETL/写入     → SELECT/INSERT/UPDATE/DELETE (etl_rw)
  ├─ 运维/DBA     → 全权限但只有少数人有 (root 等价)
  └─ 应用服务     → 只给它自己那几张表的权限
```
> 权限设计三问：**① 这个账号要连哪个库？② 要做什么（查/写/建表）？③ 会不会被偷用？** 答完再授权。

---

## 二、账号与授权实操（跟着做，真跑过）

```sql
-- ① 建一个只读账号（报表专用）
CREATE USER 'report_ro'@'localhost' IDENTIFIED BY 'Report@2026';
--   账号=report_ro, 只允许从本机(localhost)连, 密码 Report@2026

-- ② 授权: 只能 SELECT 教学库的所有表
GRANT SELECT ON study_powerbi_demodata.* TO 'report_ro'@'localhost';

-- ③ 让授权立即生效（8.0 里 GRANT 自动生效, 老版本要跑）
FLUSH PRIVILEGES;
```
**实跑验证（换 report_ro 连库）：**
```
✅ SELECT COUNT(*) FROM fact_order;        → 3529（能查）
❌ UPDATE fact_order SET status='已完成';    → ERROR 1142:
   UPDATE command denied to user 'report_ro'@'localhost'
   for table 'fact_order'                    ← 写操作被权限墙挡住!
```
> 只读账号就是 ch01「FDE 现场：客户只给你一个只读账号」的答案——**账号本身保证了"你只能查、不可能改坏"**，比人自律可靠。

### 看账号到底有什么权限

```sql
SHOW GRANTS FOR 'report_ro'@'localhost';
-- 实跑:
-- GRANT USAGE ON *.* TO `report_ro`@`localhost`
-- GRANT SELECT ON `study_powerbi_demodata`.* TO `report_ro`@`localhost`
```
> `USAGE` 是"能连上但啥也干不了"的空权限，真正的权限在第二条：整个教学库可 SELECT。

## 三、权限的粒度：库级 / 表级 / 列级

```
GRANT 权限 ON 范围 TO 账号;

范围从大到小:
  *.*                         全部库全部表（超级账号才给）
  study_powerbi_demodata.*    某个库全部表（报表常用）
  study_powerbi_demodata.fact_order   某张表
  列级(如只给看 customer_name) 生产少见, 太碎

常用权限清单:
  SELECT / INSERT / UPDATE / DELETE   数据四操作（给 ETL）
  CREATE / ALTER / DROP               结构操作（只给 DBA）
  ALL PRIVILEGES                      全部（= root 级别, 慎给）
```
```sql
-- ETL 账号: 能读写数据, 但不能改表结构
CREATE USER 'etl_rw'@'localhost' IDENTIFIED BY 'Etl@2026';
GRANT SELECT, INSERT, UPDATE, DELETE ON study_powerbi_demodata.* TO 'etl_rw'@'localhost';

-- 表级: 某账号只能看订单表, 连客户表都看不到
GRANT SELECT ON study_powerbi_demodata.fact_order TO 'report_ro'@'localhost';
```
> **表级授权的意义**：客户/供应商数据的可见范围按需收口——`dim_customer` 含客户名，不是每个报表账号都需要。

## 四、改密、回收、删除

```sql
-- 改密码
ALTER USER 'report_ro'@'localhost' IDENTIFIED BY 'NewPass@2026';

-- 回收某权限（只读账号突然能 UPDATE 了? 撤掉）
REVOKE UPDATE ON study_powerbi_demodata.* FROM 'report_ro'@'localhost';

-- 直接删账号（人走了 / 不用了）
DROP USER 'report_ro'@'localhost';

-- 查当前是谁
SELECT CURRENT_USER();
```
> 密码纪律：生产账号密码**永远不写进 SQL 脚本/Git**，用环境变量或密钥管理；本教程演示密码仅用于本地练习。

## 五、备份：mysqldump 一行命令

本机 mysqldump 在 MySQL 安装目录 bin 下（phpStudy 路径），命令行执行：

```bash
# Windows 命令行 / Git Bash 都可:
D:/XPMB/phpstudy_pro/Extensions/MySQL8.0.12/bin/mysqldump.exe \
  -uroot -proot \
  --default-character-set=utf8mb4 \      # 中文不乱码
  --single-transaction \                 # 不锁表, 备份期间业务可继续写
  study_powerbi_demodata > 备份文件.sql
```
**本机实跑输出：**
```
备份完成: 文件 760,170 字节 ≈ 742 KB
（含 6 张表的结构 + 全部 13,780 行数据）
```
```
备份出来的 SQL 长什么样（开头几行）:
-- MySQL dump 10.13 Distrib 8.0.12
-- Host: localhost    Database: study_powerbi_demodata
...
CREATE TABLE `dim_region` (...);        ← 结构
INSERT INTO `dim_region` VALUES (1,'广东','华南'),...;   ← 数据
```
> 备份文件本质 = **一串能重建库的 SQL 语句**。这就是为什么"备份"和"恢复"是同一枚硬币：备份是把库翻译成 SQL，恢复是把 SQL 再执行一遍。

### 只备份结构 / 只备份某张表

```bash
# 只要表结构不要数据（比如要把表结构给同事建一样的库）
mysqldump -uroot -proot --no-data study_powerbi_demodata > 结构.sql

# 只备份一张表
mysqldump -uroot -proot study_powerbi_demodata fact_order > 订单表.sql
```

## 六、恢复：把 SQL 灌回去 + 验证

```bash
# 先建一个空库
mysql -uroot -proot -e "CREATE DATABASE study_restore_test CHARACTER SET utf8mb4"
# 把备份灌进去
mysql -uroot -proot study_restore_test < 备份文件.sql
```
**本机实跑恢复验证（关键一步：数行数）：**
```
表              恢复后行数
dim_region      10
dim_product     200
dim_customer    500
dim_date        1096
fact_order      3529
fact_order_item 8445
合计            13,780  ✅ 和原库一字不差
```
> 恢复后**必须验证**：`SELECT COUNT(*)` 对拍、抽几条看数据对不对——备份没验证等于没备份。

## 七、备份策略：多久备一次

```
恢复点目标(RPO): 最多能丢多久的数据?
  ┌─ 每天凌晨全量备份 + binlog → 最多丢 1 天, 可恢复到任意时刻
  ├─ 每周全量 + 每天增量     → 折中方案
  └─ 从不备份                → 灾难时等于公司数据清零

一句话给客户讲清楚:
  全量备份(mysqldump) 解决"昨天之前"
  binlog(二进制日志)  解决"昨天之后到现在"——记录每次写操作,
                       出事时可以"重放"到崩溃前一秒
```
> FDE 交付建议：**上线第一天就配自动备份 + 每月做一次"恢复演练"**（真删一个测试库、真恢复、真数行数）。没演练过的备份，出事后大概率恢复不了。

## 八、小结

1. 生产不用 root：按场景开账号（只读/读写/管理），**最小权限原则**
2. `CREATE USER` 建号 → `GRANT SELECT ON 库.*` 授权 → `FLUSH PRIVILEGES` 生效
3. 权限粒度：库级 `库.*` / 表级 `库.表`；只读账号写操作被拒报 **1142**
4. `SHOW GRANTS` 查权限、`REVOKE` 回收、`ALTER USER` 改密、`DROP USER` 删除
5. `mysqldump` 备份（`--single-transaction` 不锁表、`utf8mb4` 防中文乱码）
6. 恢复 = 建空库 + `mysql 库 < 备份.sql`；**恢复后必须数行数验证**
7. 备份策略：全量 + binlog；每月做恢复演练——没验证的备份等于没有

## 九、练习 5 题

### 练习 1：给同事开一个"只读报表"账号

同事要连教学库出报表，但他不该能改任何数据。写出建号+授权的完整 SQL。

**答案：**
```sql
CREATE USER 'colleague_ro'@'localhost' IDENTIFIED BY 'ViewOnly@2026';
GRANT SELECT ON study_powerbi_demodata.* TO 'colleague_ro'@'localhost';
FLUSH PRIVILEGES;
```
**解析**：三件套——建号（带强密码）、`GRANT SELECT` 只给读、`FLUSH` 让授权生效。他若手滑跑 `DELETE`，MySQL 会直接报 1142 拒绝，而不是等他发现数据没了。

### 练习 2：把误授的 UPDATE 收回来

不小心给只读账号授了 UPDATE，怎么撤销而不影响它的 SELECT？

**答案：** `REVOKE UPDATE ON study_powerbi_demodata.* FROM 'colleague_ro'@'localhost';`
**解析**：`REVOKE` 只撤指定权限，其它授权保留。之后 `SHOW GRANTS` 确认只剩 `SELECT`。**授权宁缺毋滥、撤权只撤一项**——比"删号重建"安全且不打断业务。

### 练习 3：只给"订单相关"三张表的读权限

某个外包分析人员只需 `fact_order`、`fact_order_item`、`dim_product`，连 `dim_customer`（含客户名）都不该看。写出授权。

**答案：**
```sql
GRANT SELECT ON study_powerbi_demodata.fact_order      TO 'outsider_ro'@'localhost';
GRANT SELECT ON study_powerbi_demodata.fact_order_item TO 'outsider_ro'@'localhost';
GRANT SELECT ON study_powerbi_demodata.dim_product     TO 'outsider_ro'@'localhost';
```
**解析**：表级授权逐张给，`dim_customer`/`dim_region` 自然不可见。他查客户表会报错 1142——**数据最小可见范围**：外包/跨部门只看业务必需的表，客户隐私字段（姓名/城市）不外泄。

### 练习 4：写一条"只备份表结构"的命令

你要把表结构发给同事，让他在自己机器建出**一模一样的空表**（不要数据）。命令是？

**答案：**
```bash
D:/XPMB/phpstudy_pro/Extensions/MySQL8.0.12/bin/mysqldump.exe \
  -uroot -proot --no-data study_powerbi_demodata > 表结构.sql
```
**解析**：`--no-data`（等价 `-d`）= 只导出 CREATE TABLE，不导 INSERT。同事拿到后执行 `mysql -uroot -proot 他的库 < 表结构.sql` 即可得到 6 张结构一致的空表——**比手工敲 DDL 快且零笔误**（ch13 讲过表结构要原样保留主外键）。

### 练习 5：备份 + 恢复 + 验证全流程

写出一套"备份 → 恢复到测试库 → 验证行数"的完整命令序列。

**答案：**
```bash
# 1. 备份
D:/XPMB/phpstudy_pro/Extensions/MySQL8.0.12/bin/mysqldump.exe \
  -uroot -proot --default-character-set=utf8mb4 --single-transaction \
  study_powerbi_demodata > /tmp/backup_$(date +%F).sql

# 2. 建恢复目标库
mysql -uroot -proot -e "CREATE DATABASE restore_test CHARACTER SET utf8mb4"

# 3. 灌回去
mysql -uroot -proot restore_test < /tmp/backup_$(date +%F).sql

# 4. 验证（数行数对拍）
mysql -uroot -proot -e "SELECT SUM(cnt) FROM (
  SELECT COUNT(*) cnt FROM restore_test.fact_order UNION ALL
  SELECT COUNT(*) FROM restore_test.fact_order_item UNION ALL
  SELECT COUNT(*) FROM restore_test.dim_customer UNION ALL
  SELECT COUNT(*) FROM restore_test.dim_product UNION ALL
  SELECT COUNT(*) FROM restore_test.dim_region UNION ALL
  SELECT COUNT(*) FROM restore_test.dim_date) t"
# 预期: 13780
```
**解析**：恢复演练四步缺一不可，尤其第 4 步——**数行数对拍 13,780** 是对"备份有没有用"的唯一裁决。把这套流程写进定时任务 + 每月手动跑一次，就是 FDE 能给客户的"数据安全交付"。
